# 可视化沟通与确认规范

可视化对齐意图是人与 Agent 协作的首要沟通原则，适用于意图对齐、方案选择、变更审阅和验收。Agent 负责把待判断内容组织为用户可直接查看或操作的 Preview／Review UI，降低阅读理解负担；本原则不改变安全、权限及任务边界，不以任何 Skill、角色或产品、架构、测试工作流的启动为前提。

## 呈现与确认

结论先行，分层确认。每次确认只围绕一个核心决策，禁止长篇铺陈。默认不展开实现细节、完整推导或长篇方案；用户明确要求，或某项细节直接影响当前决策时，只展开相关内容。

可视化同样遵循分层呈现：默认只展示支持当前判断的重点，不以大图、长表或完整原型堆积信息。详细材料可作为可选入口，核心判断不得依赖用户阅读全部材料。

每次需要用户判断时，按以下顺序执行：

1. 先给结论及必要理由：方案选择给推荐，Review 或验收给实际结果。影响选择的重要代价、风险、边界和未验证项必须简要说明，不得后置；证据不足时明确结论尚未确定。
2. 按[内容视图选择](#内容视图选择)，在请求判断的同一条消息中展示简明视图或提供可直接访问的入口，支持上述结论。简单判断可用清晰的对照表；仅有长篇文字、源码、未渲染的图表定义或要求用户自行查找文件不满足要求。
3. 指明需要用户判断的具体事项；方向确认后推进必要细节，已授权范围内自主处理，只有实质新决策才再次确认。文档落盘仍须具有写入授权。

Preview 展示候选内容、需要选择时的选项及可观察后果；Review 沿同一场景展示实际结果、差异、证据和未验证项。沿用已有用例、时序步骤或矩阵行，使预期与结果能够直接对照。以下表格规定各类确认的呈现内容，具体视图按待判断问题选择：

| 确认对象 | Preview | Review |
|---|---|---|
| 意图与范围 | 对照视图展示当前理解的目标、场景、范围、预期结果及待澄清差异 | 对照用户结论标明已对齐内容与剩余问题 |
| 产品交互与体验 | 中保真 HTML 可操作地走通用例及异常路径 | 在约定环境操作实际集成版本，对照原型和指标；尚未集成时只审阅原型，标明未做实际验收 |
| 架构 | 在所选视图中展示相关职责、边界、协作或状态及其后果 | 将实际证据标到同一视图的对应元素，区分符合、偏差、未验证 |
| 测试 | 测试计划覆盖矩阵展示场景、边界和候选数据集 | 验收报告沿用计划场景 ID 和判断点展示通过、失败、未测、阻塞与证据，引用计划中的预期 |
| 规则与文档 | 前后对照或差异审阅视图展示拟定条款、适用范围和行为影响 | 对照实际落盘内容，展示差异、关联引用检查结果及遗留项 |

规则与文档涉及产品、架构或测试决策时，按实际判断问题选用对应视图；已有视图足以支持判断时直接复用。

Review 按实际用户场景分别展示操作结果、后续动作是否可继续及未验证项；技术事件附在对应步骤供追溯。本仓库维护任务按实际规则、文档或工具取证，不为满足视图虚构产品页面或架构。

## 内容视图选择

Agent 根据本次需要用户判断的问题选图，不按任务名称机械套用，不要求全套视图。选用足以支持判断的最少视图；只有不同问题无法由同一视图清楚表达时才组合使用。同一事实复用已有视图或权威正文，不重复维护。下表示例仅说明表达方式，不构成项目需求或设计决定。

| 需要用户判断的问题 | 适用内容视图 | 示例 |
|---|---|---|
| 对目标、范围或候选方案的理解是否一致？ | 对照表 | 纳入与排除范围、方案差异及各自可观察后果 |
| 谁使用系统，要达成什么目标？ | UML 用例图 | 用户提交任务，管理员管理权限，标明参与者与系统边界 |
| 用户如何操作，会看到什么？ | 可操作 HTML 原型 | 提交表单后进入等待，再呈现成功或失败重试路径 |
| 参与者按什么顺序协作，谁决定，失败后怎么办？ | 时序图 | 用户取消任务，服务确认取消，执行器停止，界面更新；标明超时、迟到结果与恢复处理 |
| 各组件负责什么，谁拥有状态，允许哪些依赖？ | 组件图＋职责表 | 页面负责呈现，任务服务拥有任务状态，执行器负责执行 |
| 服务运行在哪里，跨越哪些网络与信任边界？ | 部署图 | 浏览器、API 服务与数据库的部署位置、连接及信任边界 |
| 流程有哪些条件分支、并行步骤与汇合条件？ | 活动图 | 审批通过后并行检查库存与支付，满足条件后汇合发货 |
| 对象有哪些状态，什么条件允许转换？ | 状态机图 | 任务从待执行进入执行中，再进入成功、失败或取消，标明转换条件 |
| 数据实体之间是什么关系？ | ER 图 | 一个订单包含多个订单项，每个订单项关联一个商品 |
| 覆盖哪些场景与数据，验证结果如何？ | 覆盖矩阵 | 正常、超时、取消与权限不足场景对应数据集、结果与证据 |
| 条款改了什么，适用范围与行为有何变化？ | 前后对照／差异视图 | 修改前后条款与行为影响，并标注关联检查结果 |

时序图侧重参与者间的消息与先后关系，活动图侧重流程分支与汇合，状态机图侧重单个对象的状态转换；组件图表达逻辑职责，部署图表达运行位置，不从逻辑组件推定独立进程。本规范只约束沟通呈现，不新增或替代正式文档的内容要求；实际编写 SDD 架构文档时再按[架构表达与判定](governance.md#架构表达与判定)及[蓝图模板](../assets/blueprint.md)处理。

## 证据与状态

入口须对应本次审阅内容或版本；不能直接查看、访问未核验或证据缺失时明确标识，并保留待确认状态。产品原型的版本与访问要求遵循[HTML 原型交付](prototype.md)。

原型、模拟数据与模拟结果必须标明。用户明确确认后才记录已确认；设计确认、实验通过、局部自验、部署成功和实际产品验收分别记录。可视化呈现不能替代真实验证证据，也不扩大执行授权。
