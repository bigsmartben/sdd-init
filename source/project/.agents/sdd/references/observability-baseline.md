# 可观测性架构规范

本规范细化[架构规范](architecture-rules.md)中的观测数据与日志契约、观测影响与故障隔离。目标仓库依据已确认的设计、契约及实际运行路径，将适用约束映射为项目 Code Review Rules；Review 按本轮变更及其影响范围检查项目规则。具体职责、采集方式、隔离程度与故障策略由项目确认。

## 职责与隔离

按用途区分辅助遥测、审计记录、权威业务记录及运行控制信号，明确生产者、消费者、权威性、权限与完成判据。同一数据可以服务多种用途，但每种用途的保证须明确，不强制对应独立模块或存储。日志、指标、链路的技术形式不决定业务归属；计费用量或业务事件被确认为权威记录时，遵循其业务提交、一致性、去重及恢复契约。

普通观测副本不能未经设计确认成为业务权威或裁决依据。采集组件不得超出契约修改业务输入输出、状态，消耗或关闭业务仍需的流和资源；观测采集或导出重试不得隐式重放业务。项目可通过明确授权的接口使用观测或评测结果进行运行控制或业务决策，须明确数据可信度、时效、控制权限及失效行为。运行控制职责见[业务与运行保障分工](architecture-rules.md#业务与运行保障分工)。

项目确认同步或异步采集、业务是否等待保存、资源与生命周期的隔离目标和程度，以及延迟、内存、CPU 或 I/O 等适用开销预算。普通辅助遥测在允许损失且业务连续性优先时，可采用异步、降级和故障隔离；这是有条件的建议，不能未经确认成为门禁。审计或权威记录可按已确认要求在保存失败时拒绝操作。任何策略均须定义故障传播、超时、缓冲饱和及恢复时的业务行为，不能以“完全不影响业务”代替可检查的边界。

## 数据保存与日志契约

项目按用途和授权明确必记事实、禁存内容及保留范围，并约束实际采集、缓冲、重试与归档路径。日志排除凭证和 API Key，调试级别不得改变必记或禁存要求。业务和测试资产仅按授权用途保存。例如，观测禁止保存原始音频时，各写入路径须拒收原始音频及其等价编码。

日志契约明确必记事件、触发条件、必需字段、事件身份与类型、版本化结构及实际阶段。生产方与消费方按契约解释格式、编码、字段、结果和未知值，跨语言时检查各端兼容性。使用链路时明确 trace/span，重试关联同一事实。敏感字段按契约脱敏，保留实际结果语义。

## 采集、持久化与故障处理

明确事实接入点、采集及导出接口、传输边界和错误处理。按项目契约区分采集、队列受理、传输确认与保存完成，明确失败、缺失及未知的含义。项目要求持久化时，以契约规定的完成判据和回执为准，通过实际回读验证。按保存政策核对存储、轮转触发、保留和清理。

按项目确认的策略处理缓冲容量、饱和、超时、退出、重试和恢复，暴露采集或保存故障及覆盖缺口。采样、聚合和过载丢弃须有明确条件及可识别的缺失信息，不得未经约定静默丢弃或将失败记为成功。持久化失败时分别验证业务继续、降级或拒绝操作的行为是否符合策略，以及记录是否完整；记录完整性不能由业务成功推定。

规则须明确对象、条件、检查方法、通过判据和检查时机。沿实际调用链及故障路径验证导出失败、缓冲饱和、存储不可用等适用场景，并核对结果、资源预算及恢复效果。例如，已确认异步诊断日志策略的项目可检查队列满时的丢弃计数、业务继续及开销预算；已确认关键审计保存失败即拒绝操作的项目则检查拒绝结果和业务副作用边界。示例不代替项目决定。
