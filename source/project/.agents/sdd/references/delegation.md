# 执行与协作

Main 的能力选择、协调与验收按[职责与交接](sdd-repository-governance.md#职责与交接)。本文约定委派双方的执行义务。“调度方”是实际发出工单的 Agent，可为 Main 或技能 Agent。加载 Skill 的执行者承担其专业流程。术语见[定义](sdd-repository-governance.md#术语与职责)，各角色的职责如下。

| 角色 | 能力入口 |
|---|---|
| sdd-product-manager | 产品调研、需求与验收规格、中保真 HTML 原型 |
| sdd-architect | 架构风险、方案取舍、顶层设计与架构遵循检查 |
| sdd-coder | [实施与局部自验](implementation.md) |
| sdd-devops | [交付与运行](delivery.md) |
| sdd-doc-consistency | [只读文档一致性核对](#文档交接) |
| review-prompt | 运行时提示词审查、候选对比、按授权修订及专项复验 |

## 技能 Agent 的启动与接续

- Skill 可原生加载到当前上下文，由 Main 承担相同义务并在当前任务推进；仅需隔离或协作时启动技能 Agent，按[最小交接](#最小交接)给定入口。接单者读取 Skill 和适用资料，Main 按需保留接续标识与产物引用。具备执行能力且满足适用独立性要求时，可直接执行；Plan 的需要与时点由本职规则确定。
- **委派写明实际调用者标识和回执接收方。** 只向实际调用者回报，只向直接下位派单或补输入。技能 Agent 的调用者是 Main，角色的调用者是 Main 或派单技能 Agent。同层问题、结果和协作交调用者转接；禁止同层直发消息、委派、追加输入或通过共享文件传指令。共享产物可按工单读取，新输入由调度方传递、接单方独立核验。
- 技能 Agent 按完整阶段接单并组织阶段内操作，角色按完整专业任务或可交付批次接单。补查、确认后续做、修正和复验沿用原执行者；无法接续时交接现有工单、状态和有效证据。授权与用户决定由 Main 按[阶段授权](sdd-repository-governance.md#阶段授权与推进)处理，状态按[运行接续](sdd-repository-governance.md#运行状态与接续)核对。
- 集成测试发现实现缺陷时，将影响项和接续条件交 Main，保留原测试 Agent；Main 按授权单独启动 Bugfix，回收修复版本、影响项和证据后续派原测试 Agent，相关架构检查所需输入也由 Main 分发。
- 使用实际 Harness 接口。若支持 `collaboration.spawn_agent` 及相应参数，使用 `fork_turns="none"` 和 `message`。多层委派、能力、授权或指定独立性确有缺口时回报影响及恢复条件，仍按原完成条件验收。

### 角色的模型与推理强度

- 启动专业角色或合格替代前，Main 按本次工单的复杂度、不确定性、误判代价和完成条件，从当前 Harness 支持的选项中权衡能力、耗时和 token 消耗，选定具体模型 ID 和兼容的推理强度。用户明确指定的设置优先。sdd-workflow 的角色定义、适配配置和调度规则均不预设模型或推理档位。
- 技能 Agent 需要派单时，先将任务信息和可用启动选项交 Main，收到具体设置后再启动。工单复杂度或风险实质变化时，由 Main 决定是否调整。实际派单者在支持的启动参数中显式传入模型 ID 和推理强度，例如 `collaboration.spawn_agent` 的 `model` 和 `reasoning_effort`。即使选定值恰好与父会话相同，也显式传参。
- 某项设置无法应用时，派单者先报告受限项。Main 判断该项默认值是否满足工单，能应用的设置仍显式传入。采用默认值时说明受限原因及可核对的实际设置。若无法满足用户指定的设置或工单必需能力，报告影响和恢复条件。
- 派单者依据启动记录核对请求的模型 ID 和推理强度。宿主提供生效值时一并核对，发现偏差交 Main 处理。宿主只提供请求参数时，回报已请求的值及生效值未能核实的情况。

## 委派与独立性

按工单能力及输入输出契约选择执行者；角色不可用时，由合格替代或具备能力的调度方在职责内按同一契约承接，缺能力则回报。项目或用户要求独立审查、验收时核对实际独立性。明确共享文件归属，保留他人修改。并行执行方式遵循 Harness 原生机制。角色按下述独立执行约定接单。

### 角色独立执行

角色可直接受理合格工单，在授权内使用适用的项目正文、共享规则、模板和工具完成本职产物及写后检查。角色禁止加载工作流 Skill、依赖其内部规则或委派其他角色。按[任务回执](task-receipt.md)向任务调用者交付结果、证据、缺口和接续条件。

## 实施交接

可先以明确的 `investigate` 或 `prepare` 模式安排获授权调查或准备；`implement`、`fix`、`refactor` 须先达到下述工单就绪且实施授权覆盖所选模式。需求、缺陷与 Review 工单按场景引用可执行的[验收计划与方案](sdd-repository-governance.md#验收计划与方案)；只规格、评估、审查或验收止于用户限定终点。

### 工单就绪

实施工单的最小可核对契约包含：

| 字段 | 必须回答 |
| --- | --- |
| 目标 | 本轮要改变或证明什么 |
| 范围与排除 | 包含的模块、行为和明确不在范围内的内容 |
| 原工单编号 | 可回溯的需求工单、原 Issue、原 Review CHK 或本轮任务标识 |
| 通过判据 | 每个在范围结果可观察、可运行或可核对的通过条件 |
| 授权终点 | 调查、准备、实施、修复、重构、复验或仅测试中的实际终点；未授权阶段不隐含 |
| 写入边界 | 允许写哪些代码、测试、配置、Plan／Task 或文档；只改测试时明确禁止产品改动 |
| 完成条件 | 达到何种产物、检查结果和证据后停止，哪些 Gate 明确不在本轮 |

按场景还需补齐：需求实施引用适用 Spec／AC；缺陷引用原 Issue、已验证归因及反证边界；Review 整改引用原 CHK 和须保持行为；涉及验收的工单给出验收入口、版本／环境前置、操作或检查步骤以及可用的已有证据。调查、准备模式只需覆盖其实际终点，但仍须说明问题、边界、授权与停止条件。

缺项不得靠实施者猜测。工单无法继续时：可由实际调用者补充的输入标为 `needs-input`；依赖外部环境、权限、人工决定或能力而暂时不可行的标为 `blocked`；已交付部分且剩余缺口明确的标为 `partial`，并在各自回执中列出缺口影响、承接者和恢复条件。技能 Agent 只能在阶段权限内补齐并接续；跨阶段、用户决定或超授权交 Main，直派工单也由 Main 处理。只暂停受影响项及依赖，其他获授权且就绪项继续。

## 文档交接

调度方按正文归属安排写入，本职执行者按[文档写入规则](document-writing.md)归并已确认内容和证据、完成写后检查。权威冲突、已确认结论变更及另需授权或裁决的修复交 Main。

文档一致性审查必须在实际只读权限会话中执行；子角色继承写权限时另开只读会话。向调用者返回发现、建议与待核实项，获授权的阶段内修复仍按正文归属安排。

## 交付与运维交接

按[最小交接](#最小交接)和[交付与运行规则](delivery.md)给定[协作场景与任务类型](delivery.md#场景识别与工作流)、仓库、环境、版本或确定方式、对象、任务范围、前置状态、操作与恢复授权、适用确认／告知、写入边界及完成条件。交接完整专业场景，而非逐条命令；由角色自主调查、制定方案、配置／执行并复验。加载交付 Skill 的 Agent 核对场景结果，不重复角色实施过程。Main 直接承接或按替代规则执行时落实同一契约，不强制三层调用。

| 工作 | 当前执行能力与输入 | 回执重点 |
| --- | --- | --- |
| 交付与运维工作流配置、仓库交付、流水线、发布或运行运维 | 由 `sdd-devops` 接收完整场景、授权终点、版本、项目入口和恢复边界，优先沿用既有流程，自主配置／执行并复验；不可用时按委派替代规则处理 | 场景终点、配置与实际运行的区别、平台及运行回执、源提交、制品、运行版本、环境状态和恢复结果 |
| 运行检查或发布结果核验 | 技能 Agent 或合格执行者依据目标状态、版本关联、健康与约定冒烟检查 | 实测结果、版本、覆盖、证据及异常 |
| 运行指南、发布依据或证据引用疑似矛盾 | 按需安排 `sdd-doc-consistency` 或合格执行者，提供指定范围、疑点和权威依据供只读核对 | 位置、权威依据、影响及缺口 |

部署评估、待确认事项、待选路径、权限与发布证据缺口沿原调用链回报，附依据、影响和恢复条件。Main 告知用户、取得决定并交回原执行者；执行者按[执行前确认与部署评估](delivery.md#执行前确认与部署评估)核对适用性后续做。同一工单复查、修正及复验，结果含实际版本、覆盖、操作回执和恢复效果；跨阶段事项交 Main。

## 最小交接

工单提供专业目标、有效事实与上下文、约束和授权边界、交付与完成条件、必要证据要求。按需补充范围与排除项、写入边界、版本环境及待决事项；可引用有效正文，未落盘确认或授权附必要原意。接续只补变化、被替代要求与缺项，不复制背景或替执行者规划源码追踪、实现与测试步骤。契约不要求固定 JSON 或冗长工单。

| 执行范围 | 按需补充的输入 | 返回重点 |
|---|---|---|
| 产品 | 用户目标、适用约束、调研或反馈、已有 Spec／AC | 产品结论、可观察行为和验收依据、原型与确认状态 |
| 架构 | 待决问题、已确认需求、现有 Blueprint／契约、影响范围及可核验事实 | 设计与取舍、关键假设证据、受影响的约束、经确认的变更和待决项 |
| 架构审查与复核 | 已确认架构、适用规则、原检查项、目标版本和可复用证据 | 原检查项编号、约束、实际路径、偏差、技术整改目标、复核结论和证据 |
| 实施 | 工单就绪字段、执行模式、适用的 Spec／AC、Issue 或 Review CHK、验收入口和环境、必要代码上下文 | 最小分档 Plan／Task、实际改动、版本与工作树指纹、检查命令和结果、覆盖判据、待验项；归因反证附原编号 |
| 交付与运维 | 授权终点、目标、入口、版本、已有平台和环境状态、适用发布证据和恢复授权 | 实际终点、对象、版本和运行证据、待选路径、恢复结果或接续条件 |
| 文档一致性 | 文档范围、主题或疑点、已有索引及权威依据 | 证据位置、问题、影响、建议和待核实项 |

验证工单引用适用需求、原 Issue／检查项、版本环境及可复用证据，回收逐项结果和缺口。归因反证或修复后失败在获授权 Bugfix 内沿原编号接续；复验、复核沿用原判据。集成测试资产与环境准备按 [sdd-test-loop](../../skills/sdd-test-loop/SKILL.md#本轮闭环)，产品代码缺陷、需决定的设计或正文冲突附证据交 Main。

调度方按[证据与复用](sdd-repository-governance.md#证据与复用)核对[任务回执](task-receipt.md)，在阶段权限内补查、修正及复验，再按[阶段回执](sdd-repository-governance.md#阶段回执)交付；新决策、授权缺口或跨阶段事项交 Main。
