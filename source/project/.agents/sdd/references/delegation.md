# 执行与协作

主任务启动技能 Agent，技能 Agent 调度阶段内的专业角色。本文的“调度方”指实际发出当前工单的 Agent，包括直接承接工单的 Main。目标项目通过 `.codex/config.toml` 注册以下角色。专业职责和默认模型查注册所指向的角色定义。

| 角色 | 职责 | 默认模型 |
|---|---|---|
| sdd-product-manager | 产品调研、需求与验收规格、中保真 HTML 原型 | gpt-6-astra |
| sdd-architect | 架构风险、方案取舍、顶层设计与架构遵循检查 | gpt-6-astra |
| sdd-coder | [实施与局部自验](implementation.md)，维护代码、测试和同一份 Plan／Task | gpt-6.1-sol |
| sdd-devops | [交付与运行](delivery.md)，包含仓库、流水线、发布、环境、流量、排障及恢复 | gpt-6.1-terra |
| sdd-doc-consistency | 只读核对文档冲突、冗余和引用，返回证据与建议 | gpt-6.1-terra |

## 技能 Agent 的启动与接续

- 新阶段由 Main 启动独立技能 Agent。使用 `collaboration.spawn_agent` 时显式传 `fork_turns="none"`，用 `message` 交接所选入口和[最小交接](#最小交接)所需信息。接单 Agent 读取该 Skill 和适用资料。Main 记录可接续的 Agent 标识及权威产物引用。
- **每次委派写明实际调用者标识及回执接收方。** Agent 只向实际调用者回报，只向自己直接调度的下位执行者派单或补输入。技能 Agent 的调用者是 Main；专业角色的调用者是派单的技能 Agent 或 Main。遇到兄弟 Agent 的问题、结果或协作请求，交实际调用者转接。禁止向同层 Agent 直接发消息、委派、追加输入或以共享文件传指令。共享产物可以按工单读取；新输入由调度方传递，接单方独立核验。
- 阶段内的补查、确认后的续做、失败修正及复验沿用原技能 Agent。集成测试发现实现缺陷时将受影响项和接续条件交 Main。Main 保存原测试 Agent，按实际授权单独启动 Bugfix。Bugfix 将修复版本、受影响项和证据引用回交 Main，由 Main 续派原测试 Agent；相关架构检查需要这些输入时也由 Main 分发。原 Agent 无法接续时，Main 用同一阶段的现有工单、状态和有效证据交接给新的技能 Agent。
- 技能 Agent 按整个阶段接单，专业角色按完整的专业任务或可交付批次接单。阶段内局部操作由技能 Agent 组织完成。按[最小交接](#最小交接)引用权威正文和已有确认，接续只补增量。阶段授权和用户决定由 Main [按治理协调](sdd-repository-governance.md#阶段授权与推进)，接续时按[运行状态与接续](sdd-repository-governance.md#运行状态与接续)核对状态。
- 多层委派受客户端配置约束。Main 无法启动独立技能 Agent 时，按[阶段授权与推进](sdd-repository-governance.md#阶段授权与推进)报告受影响阶段和恢复条件。仅专业角色不可用时，按[委派与独立性](#委派与独立性)处理。

## 委派与独立性

Skill 按本阶段所需能力和[最小交接](#最小交接)显式委派。Skill 以能力和输入输出契约组织工作，角色标识、内部指令和特定角色是否在场均不构成前置条件。角色独立接收工单，在授权内使用适用的项目正文、共享规则、模板和工具完成本职产物及写后检查。角色不加载工作流 Skill、不依赖其内部规则、不互相委派，向任务调用者返回[回执](task-receipt.md)。

复杂专业工作在可委派时按完整批次安排。对应角色不可用时，可换合格执行者，或由具备能力的调度方按同一契约直接承接；简单任务也可直接完成。确实缺少必要能力时记录缺口及恢复条件。明确共享文件归属，保留其他执行者的修改。有实际收益且互不干扰的工作可并行。复验及复核优先复用原执行者；项目或用户对独立审查、验收有要求时核对实际执行者是否独立。

用户指定的模型和推理强度优先。否则调度方按子任务复杂度选择推理强度，启动接口支持时显式传入。使用支持该设置的 `collaboration.spawn_agent` 时以 `fork_turns="none"` 配合 `reasoning_effort`，通过 `message` 传递最小上下文。启动接口不能设置模型或强度时按实际配置报告。

## 实施交接

调度方按[最小交接](#最小交接)先安排已授权的调查及 Plan 准备，在工单就绪、实施获授权且阶段确认已满足时安排实施。已有需求、缺陷和 Review 工单直接引用可执行的[验收计划与方案](sdd-repository-governance.md#验收计划与方案)。已确认的架构变更或获授权的探索可按各自目标、范围、完成条件和必要依据交办。输入缺口只暂停受影响项及其依赖，由调度方补齐并接续。只规格、只评估、只审查和只验收按用户限定终点交付。

执行者发现必要依据、判据或授权缺失时，按[任务回执](task-receipt.md)先交任务调用者，写明缺项、影响和恢复条件。阶段内由技能 Agent 在职责与授权范围内补齐并接续原工单。涉及跨阶段、需用户决定或超出授权时，由技能 Agent 交 Main 协调。直接委派的工单由受理回执的 Main 处理。受影响项及其依赖按[阶段授权与推进](sdd-repository-governance.md#阶段授权与推进)暂停，其余已就绪且获授权的工作继续。

## 文档交接

已确认的领域正文及任务执行证据由获授权的本职执行者按[文档写入规则](document-writing.md)归并并做写后检查。纯文档任务由调度方按归属安排。权威依据冲突及已确认结论变更交 Main 协调。

调度方在实际权限为只读的会话中安排文档一致性审查。若子角色继承父会话的工作区写权限，使用独立只读会话启动审查角色。角色向任务调用者返回审查发现、建议及待核实项。已获授权且属于阶段职责的修复按正文归属安排，需另行授权或裁决的事项交 Main。各流程按自身要求完成写后检查。

## 交付与运维交接

按[最小交接](#最小交接)传递授权、边界与可访问的资料引用。交付阶段沿用主任务 → 技能 Agent → 专业角色。Main 直接承接局部操作时，沿用适用的执行前确认与核验。

| 交接方向 | 交付内容与责任 |
| --- | --- |
| Main → 技能 Agent | 给出用户目标、仓库及环境、版本或确定方式、授权终点、操作与恢复边界、已确认或已告知事项、依据与完成条件。收到需用户处理的事项后负责呈现和取回结论，将反馈交回原技能 Agent；直接委派角色时交回原角色。 |
| 技能 Agent → 角色 | 按[交付与运行规则](delivery.md)核对本轮输入和依赖，交办完整的专业任务或组合批次，给出对象、版本、步骤范围、前置状态、证据引用、适用确认、写入边界和每项完成条件。接续只补反馈及受影响步骤。 |
| 专业角色 → 任务调用者 | 提供评估、待决问题及依据。执行后按[任务回执](task-receipt.md)提供实测对象、版本、覆盖、操作回执、证据、未完成项及恢复条件。按同一工单复查、修正和复验。 |
| 技能 Agent → Main | 提交待告知的部署评估和待用户确认的事项，说明判断依据、影响及可执行的接续条件。核对本轮终点和覆盖后汇总实际状态、版本、证据、恢复结果与跨阶段事项，供 Main 核对整体交付和协调接续。 |

| 工作 | 当前执行能力与输入 | 回执重点 |
| --- | --- | --- |
| 仓库交付、流水线、发布或运行运维 | 通常由 `sdd-devops` 接收授权操作、版本、项目入口和恢复边界，自主制定方案、执行并复验 | 平台及运行回执、源提交、制品、运行版本、环境状态和恢复结果 |
| 运行检查或发布结果核验 | 技能 Agent 或合格执行者依据目标状态、版本关联、健康与约定冒烟检查 | 实测结果、版本、覆盖、证据及异常 |
| 运行指南、发布依据或证据引用疑似矛盾 | 按需安排 `sdd-doc-consistency` 或合格执行者，提供指定范围、疑点和权威依据供只读核对 | 位置、权威依据、影响及缺口 |

按[委派与独立性](#委派与独立性)选择角色或直接承接。部署评估和待确认事项沿原调用链上报，由 Main 告知用户并取得必要决定。告知或确认结果沿原调用链回传，执行者按[执行前确认与部署评估](delivery.md#执行前确认与部署评估)核对适用范围后接续。待选路径、权限缺口及发布证据缺口随事实和恢复条件回报，跨阶段事项由 Main 协调。

## 最小交接

技能 Agent 与专业角色的委派至少给出任务目标、范围与排除项、授权终点、写入边界、必要输入和完成条件，以及会影响执行的已知待决事项。给出目标版本及必要的环境信息，写入边界和完成条件可用有效引用明确。未落盘的确认结论及授权附必要原意。接续时引用已有记录，只传本轮变化、被替代的要求和需处理的缺项，完整背景和权威正文留在原位置。

| 执行范围 | 按需补充的输入 | 返回重点 |
|---|---|---|
| 产品 | 用户目标、适用约束、调研或反馈、已有 Spec／AC | 产品结论、可观察行为和验收依据、原型与确认状态 |
| 架构 | 待决问题、已确认需求、现有 Blueprint／契约、影响范围及可核验事实 | 设计与取舍、关键假设证据、受影响的约束、经确认的变更和待决项 |
| 架构审查与复核 | 已确认架构、适用规则、原检查项、目标版本和可复用证据 | 原检查项编号、约束、实际路径、偏差、技术整改目标、复核结论和证据 |
| 实施 | 工单编号、通过判据、适用的验收计划与方案、必要代码上下文 | Plan／Task、改动、版本、局部证据、待验项。归因反证附原编号 |
| 交付与运维 | 授权终点、目标、入口、版本、已有平台和环境状态、适用发布证据和恢复授权 | 实际终点、对象、版本和运行证据、待选路径、恢复结果或接续条件 |
| 文档一致性 | 文档范围、主题或疑点、已有索引及权威依据 | 证据位置、问题、影响、建议和待核实项 |

集成测试、点对点验收、缺陷归因及复验和架构 Review 由调度方在对应阶段安排。提供适用的需求、原 Issue 或原检查项、版本环境和可复用证据，接收逐项结果及缺口。缺陷归因反证或修复后失败沿原编号在已授权的 Bugfix 范围内接续。复验和复核沿用原判据。集成测试的测试资产和环境准备按 [sdd-test-loop](../../skills/sdd-test-loop/SKILL.md#本轮闭环) 执行。集成测试发现的产品代码缺陷、需另行决定的设计与正文冲突，随证据交 Main 协调。

续派按[证据与复用](sdd-repository-governance.md#证据与复用)沿用仍适用的证据。调度方回收并核对[任务回执](task-receipt.md)，按[阶段回执](sdd-repository-governance.md#阶段回执)汇总本轮结果。

Skill 在本阶段职责及授权内根据回执安排补查、修正和复验，向 Main 交付阶段回执。跨阶段事项、新决策及授权缺口由 Main 协调。
