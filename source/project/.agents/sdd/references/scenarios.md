# 六类场景提示

讨论时按需选用影响当前结论的问题。正式写入时按内容层级及权威归属定位正文，同一任务可涉及多个实体。确认后的结果归入对应实体。

| 场景 | 参考输入与关键问题 | 固化去向 |
| --- | --- | --- |
| 新需求／产品定义 | 谁在何种场景遇到什么问题？现状与期望、目标、规则、范围、异常、适用原型及可验证结果是什么？ | 高位用例、体验与验收维度归 Blueprint；具体行为及 AC 归 Spec |
| 验收反馈／缺陷 | 哪个版本、环境与操作？预期和实际如何不同，怎样复现、影响谁、有何证据、怎样验证修复？区分实现偏差与已确认的需求变更。 | Issue 维护问题事实、依据和处理历史，Plan／Task 维护修复方案并引用归因证据，Test Report 记录批次证据。确认需求变化后更新 Spec |
| 需求变更 | 当前需求及变更原因是什么？改什么、保留什么，影响哪些行为、原型与验收项？ | 按变更层级更新 Blueprint 或 Spec，必要时更新原型引用 |
| 架构设计／变更 | 需求、现有架构和实现事实是什么？职责、接口、状态归属、依赖、约束及取舍如何确定？ | 职责、边界与不变量归 Blueprint；接口语义归契约，交互顺序及异常分支归时序 |
| 重构要求 | 实现与已确认架构有哪些偏差？目标、范围、须保持的行为和直接影响是什么？ | Architecture Review Record 维护原检查项、行为基线、复核与证据引用。方案与局部自验归同一 Plan／Task |
| 实施 Plan | 工单明确了什么目标、范围与完成判据？当前实现是什么？改哪里、分哪些步骤、有什么依赖、如何验证、有哪些实际风险？ | Plan（Task 清单）归当前任务或已有计划载体 |
