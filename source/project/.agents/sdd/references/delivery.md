# DevOps 交付与运行

## 场景识别与工作流

结合用户目标与授权终点、项目协作约定、任务类型和环境风险确定本轮场景。调度方交接已确认的上下文，专业执行者从项目资料与实际配置补齐必要事实；不凭仓库所有者、参与人数或某个平台推断已获授权。

- **个人开发。** 按项目约定减少不必要交接，但不默认免评审、审批或生产确认，也不默认自动合并和发布。
- **团队开发。** 沿用既有角色、分支、评审、审批和环境策略，不额外强加人工节点；团队约定可以包含自动化。
- **任务类型。** CI 关注集成、测试、检查、构建与反馈；CD 关注制品交付、版本发布或部署，区分可交付与实际部署的终点；Ops 关注环境、服务、流量及恢复；DevOps 关注贯穿开发、交付与运行的协作和自动化机制。类型可以组合，不要求互斥分类或为简单任务建立分类文档。

先区分建立／调整工作流与执行已有流程。优先复用适用入口，只有缺失、不适用或用户要求调整时才建立或修改。工作流按本轮目标明确必要依赖、执行责任、门禁、完成条件及失败恢复，不预设每个任务都经过提交、审查、修复、集成、部署和发布。独立请求不扩展到未授权的后续阶段。

通用规则保持平台无关，实际执行仍须识别目标平台。平台事件、云端 Agent 接入、权限、触发器、运行参数及自动化状态控制在目标项目的配置和必要脚本中实现，不反向固化为通用 Skill 或角色规则，也不为此新建通用流程引擎。专业执行者核实平台支持的接口、账号能力和审批限制；能力或权限不足时报告缺口，不能靠虚构接口、绕过审批或换用未确认服务交付。配置完成后由实际执行器持续运行，调用者只跟进本轮授权终点，不作为常驻控制器。

## 执行前确认与部署评估

确认与告知的传递见[交付与运维交接](delegation.md#交付与运维交接)。

- **生产操作。** 先用已获准读取的本地配置、运行指南和已保存证据判明环境、目标及触发链。读取这些既有材料可用于部署评估或发布缺证判断。访问生产实时状态源、生产 API、控制台或运维入口前，须核对覆盖实际对象、版本、所用操作及影响的明确人工确认。边界按数据源和效果判断，覆盖只读状态、监控、日志、在线制品查询和排障，也覆盖通过文件、数据库或其他入口直接读取同一实时数据源。采用本地替身验证生产门禁时，执行器及其正在使用的状态、在线制品和观测数据也按该约定受限。以独立存档和运行指南完成可核对的评估；无法判定是存档或实时来源时，先确认来源属性或等待适用授权。间接触发生产操作的推送、合并、打标签和流水线也须先确认。已有确认覆盖时沿用；只确认查询时，限于相应查询。实质变化时先重新确认受影响部分。入口的生产影响无法判明时暂停该入口，继续获授权的独立取证。
- **部署评估。** 首次部署、版本更新、部署回滚等部署类动作，在执行或触发前列出目标环境、服务或实例、目标版本或版本确定方式、适用的配置、路由和数据变更。说明对服务可用性、用户流量、依赖和数据的影响，以及适用的中断风险、回滚条件。间接部署的评估也须在首次触发前给出。
- **告知与接续。** 按上述交接向实际调用者返回部署评估及待确认事项，经 Main 告知用户并回收适用的确认。沿用已告知的有效评估，目标或影响实质变化时更新受影响部分并写入回执。已授权的非生产部署在有依据确认评估已告知且其余前置条件满足后继续。生产部署还须有覆盖本次评估及操作范围的人工确认。

## 执行与复验

1. **明确边界。** 从工单、已有确认及项目约定确定适用的仓库、环境、版本、操作范围、终点和恢复授权。沿用既有发布策略、灰度范围、回滚及数据处置决定。目标无法消歧、涉及用户、数据或服务的必要选择、目标或影响实质变化、认证或权限缺口，随依据和影响列入回执。执行工具、命令、顺序、诊断和授权内重试由执行者决定。
2. **探测实际状态。** 先利用本地配置和已有资料识别环境及自动入口的连带效果，再按[生产操作的确认边界](#执行前确认与部署评估)核对工具与认证、连接上下文、目标实例、依赖、数据、已有操作和并发变化。复用本任务已有的分支、平台对象和服务实例，保护无关工作区、暂存改动、其他项目资源和持久化数据。
3. **核对前置条件。** 确定可执行步骤与缺口，落实适用的[执行前确认及部署评估](#执行前确认与部署评估)。正式发布按[正式发布依据](release-evidence.md)核对项目要求、候选版本和适用证据，同时核验制品来源及环境、依赖和数据兼容性。独立操作适用自身的前置条件。若发布依据从获准读取的本地证据已能判定不足，先记录缺口，继续其他已就绪且获授权的独立操作。
4. **执行并回读。** 按实际依赖执行独立或已授权的组合操作，保留步骤回执。每次写入前核对目标、实际版本或对象状态及差异，并发变化时重评估受影响步骤，优先用平台版本约束。按[场景终点](#场景输入与终点)从实际状态取得版本、制品、健康、日志、路由和约定冒烟证据。
5. **处理失败。** 失败、超时或结果不明先回读实际状态，再诊断。核对重试、修复或恢复所需的授权及适用的[执行前确认与部署评估](#执行前确认与部署评估)，再修正流水线、部署、环境配置或运维脚本并复验，或按已授权策略恢复。应用缺陷可先按上述条件恢复服务，在回执中记录缺陷、实测证据和恢复结果。待审批或无法继续时记录已完成步骤、影响及恢复条件，暂停受影响项及其依赖，继续其他已就绪且获授权的工作。

## 提交后的路径

- 用户已指定终点或后续路径时，在授权内直接完成。明确只提交时，返回分支和 SHA 即结束。
- 请求提交或交付本地改动而后续路径未指定时，先完成授权内的本地提交。回执列出分支、SHA、适用选项及已知目标分支或环境。选项包含结束。
- 收到选择后，从先前的提交接续，核对当前分支和目标状态并复用已完成步骤。发现新增无关改动时保持原交付范围，实际范围或目标需要变更时仅确认受影响的选择。

## 组合路径

独立任务到自身终点即结束。组合请求已明确授权且相应前置条件已满足时，接续各步骤。推送、合并、打标签或触发流水线前，核对自动构建、部署、发布、切流及其他连带效果，按[执行前确认与部署评估](#执行前确认与部署评估)选择作用域相符的入口。涉及正式发布时，先满足适用授权和发布依据，再触发会自动发布的操作。

依赖 Git 结果时，先回读已推送的远端 SHA，或等平台确认合并后核验实际目标提交。依赖流水线、发布或制品时，关联源 SHA、运行或发布标识及制品版本，按项目入口使用已核验版本，避免把无关工作区改动带入构建。切流依赖部署时，核对目标版本、运行就绪及适用冒烟结果，再按授权调整流量。

“推送并部署 dev”按实际远端 SHA 部署对应版本。若推送自动触发部署，部署评估在推送前告知。若部署是独立步骤，在部署前告知。已确认的操作按各自前置条件连续完成。

## 结果与证据

按[任务回执](task-receipt.md)向任务调用者返回实际达到的终点、操作回执、源提交、制品或运行版本、环境、访问与证据入口、未完成项和恢复条件。按需给出实测覆盖、健康、冒烟、路由、故障影响及恢复效果。排队和待审批按当前状态报告。其他职责的发现写明证据与接续条件，后续执行者仅在工单已指定时记录。

需要正式记录时按[文档写入规则](document-writing.md#按对象读取与语义核对)更新已有记录。优先使用项目模板，首次建档且无项目模板时使用 [Delivery Record](../assets/delivery_record_template.md)。
