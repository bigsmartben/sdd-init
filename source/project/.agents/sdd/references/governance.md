# SDD 实体与执行治理

## Skill 场景与对象分工

SDD Skill 由 Agent 根据用户任务意图与 Task Contract 自主选择和接续，无需用户显式输入 sdd-* 指令，默认 Main 执行。选择流程不扩大目标、写入、测试、外部操作或 Git 交付的授权范围；纯讨论不落盘，文档完成不自动授权实施。Skill 表示工作职责，不对应固定 Agent；实际工作的模型分工、推理强度与协作边界按 [执行约定](delegation.md) 执行。

| Skill | 场景与职责 | 判断依据 / 作用对象 | 结果 |
|---|---|---|---|
| sdd-init | 安装、升级能力，补齐缺失骨架 | 仓库 Skill、工具、模板、治理入口及必要配置 | 可用安装及冲突说明 |
| sdd-doc | 已确认结论落盘、文档一致性 | 确认来源 → Blueprint / Spec / Status | 准确实体内容与引用 |
| sdd-imp | 实施、局部自验、修复、记录状态 | Spec + Blueprint → 授权代码/测试及 Status | 本轮 AC/ARC 实现覆盖与局部自验证据 |
| sdd-review-loop | 架构符合性检查及授权内整改复核 | Blueprint/ARC → 实现、跨能力关系及 Status | Review Gate 与快照证据 |
| sdd-test-loop | 需求行为验收及授权内修复重测 | Spec/AC → 实际行为、测试及 Status | Test Gate 与快照证据 |
| sdd-commit | 执行指定 Git 交付终点 | 授权差异、提交、分支、远端、PR/MR | 已核验的交付回执 |

设计讨论由用户当前对话完成；sdd-doc 只承接已确认结论。各执行流程提供状态事实与证据，Status 落盘按模型分工由 terra 执行，无需另建文档流程。Review 检查架构落地，Test 检查需求行为，二者不相互替代；执行 Loop 不等于已获得独立审查证据，独立性按实际执行者判断。

## 权威实体

| 实体 | 权威内容 | 写入者 |
|---|---|---|
| Blueprint | 项目全局架构、概念所有权、边界及已确认 ARC | Main / 当前执行者|
| Spec | 一个能力唯一现行需求、场景、AC、边界与质量要求 | Main / 当前执行者|
| Status | 当前迭代进度、真实证据、阻塞与恢复点 | Main / 当前执行者|

默认路径是 `architecture/blueprint.md`、`specs/<capability>/spec.md` 和同目录 `status.md`。已有权威路径优先；不要建立另一份 latest/v2/final 或第四种批次实体。代码是实现事实；模板、候选规则库及历史讨论不是已批准契约。

## 架构表达与判定

架构至少说明以下视图；可按项目规模合并章节、引用已有正文，不要求增加文件层级：

| 视图 | 必须说明的内容 |
|---|---|
| 目标与取舍 | 场景与质量目标、方案选择理由、代价及适用条件 |
| 概念与关系 | 核心概念、关系和不能混同的边界 |
| 模块与能力 | 职责、I/O、协作接口、允许及禁止的依赖 |
| 状态与权限 | 权威状态所有者、请求者、决策者、写入者、副作用执行者及完成事实 |
| 运行与工程 | 执行位置、信任边界、宿主与装配、源码与构建映射 |
| 交互与失败 | 正常顺序、并行、取消、迟到、失败、未知及恢复边界 |

这些是表达要求；模块数量、平面、目录、技术模式及部署方式由项目确认，不把单个项目的选择推广为通用约束。只落盘已确认内容，缺失的实质设计列为待决策，不为满足视图补造方案。

总览维护职责、状态所有权与不变量，所属专题维护接口、必要机制及异常语义；同一条款只有一个现行正文。跨文档摘要必须指向权威条款，不增加条件或缩小范围。ARC 及已有条款标识不随章节、文件移动改变；迁移核对关键约束的完整承接及有效引用，不只检查链接是否存在。历史决定归修订沿革，当前实现与进度归 Status / 任务。

遵循判定区分“架构语义 → 当前实现映射 → 所需证据”。目录、包名及类名用于定位，不能替代职责、状态所有权、权限和调用链检查；迁移更新映射，不隐式改变规则。跨模块请求、受理、执行、交付、应用及呈现分别取证，不相互代替。

变更按语义影响分级，项目在其遵循规范维护适用判据：L0 为实现变化且外部契约与架构语义不变；L1 为已确认边界内的契约扩展，须同步生产者、消费者及异常语义；L2 为职责、状态权威、决策权限、信任边界、依赖方向或关键不变量的改变，须按项目门禁确认。提示词或目录改动同样按影响判断；纯正文迁移且语义不变不升级为架构决策。文档授权不自动授权同步代码，未实施部分如实留待办。

## 文档写入

用户指定的讨论模型、强度和技能优先。已确认内容可来自当前对话、用户指定的独立对话或文档；任务包含文档写入时，Agent 自主选择 sdd-doc，由 terra 归并与落盘，Main 负责契约和来源核对。已授权流程的状态事实由原执行者提供，文档写入同样使用 terra；纯讨论不触发落盘。

先定位实体与能力归属；相同语义原位归并，维护稳定术语、FR/AC/ARC 编号和引用。同类不等于相同：前提、对象、边界或验收不同的需求不能为去重而合并丢失。跨实体用引用连接，不复制竞争权威正文。确认替代时更新旧表述；取舍不明只报告具体冲突。源结论不明确或缺失时请求所需内容，不自行补设计。

根据模板写入已经确认的内容，保持其含义和验收强度；不重新评审合理性、不为填模板发明需求。既有章节原位更新；目标实体确实不存在且创建意图与归属明确时可按模板创建，首次 Status 为 NOT_STARTED/UNVERIFIED。初始化器负责安装能力与初始骨架，不是后续文档生成必须重新运行的入口。

执行者提供代码快照、命令/报告、结果、覆盖范围和完成结论；当前执行者检查证据字段、引用与时效后记录。缺少事实、证据过期或结果有冲突时保持 UNVERIFIED/BLOCKED，不自行推定 PASS/COMPLETED。`govern.py` 的 start/record/attest/finish 是当前执行者可用的机械工具，不替代语义验证。更新内容后重新核对受影响证据，不能通过改 Status 规避过期检查。

## 测试范围约束

所有 SDD 流程在编写或执行测试计划、测试用例、验收条件、验证报告及通过门禁时，均排除 UI 内容与视觉设计。禁止新增或执行以文案措辞、布局、配色、字体、图标、间距、视觉还原度为目标的测试、验收项或门禁，包括以这些内容为目标的截图比对。

界面触发的提交操作、权限控制、状态流转、数据处理及错误处理等业务契约仍可验证。是否使用界面、浏览器或截图作为验证手段，不决定其是否属于视觉测试；按实际断言目标判断。

既有 Spec/AC 含上述排除内容时，报告契约冲突，在对应 Status 如实保留未验证/阻塞状态，等待获授权的文档调整；不得执行该项视觉验证、静默跳过、记为 PASS，或据此宣称全部 AC 通过。混合业务与视觉要求的 AC 可以记录业务部分的实际证据，但不得以部分通过替代整条通过。其他既有有效证据保留其事实与快照，不改写历史记录；本条不授权修改 Spec、删除测试或降低业务验收要求。

## 实施和独立审查

任务包含实施或修复时，Agent 自主选择 `sdd-imp`，简单且已授权的任务由 Main 直接完成；Plan 按实际取舍和风险需要使用，Goal 仅在用户明确要求或更高优先级指令要求时创建。已获授权内不重复设审批，明确要求先审计划时仍遵守。委派后各执行者按模型分工完成对应工作并返回证据，Main 协调实施、局部自验与修复闭环，按明确归属维护 Status 并核对关键差异；出现缺口、矛盾、失败或快照变化时才深入检查受影响局部。实现完成需要本轮 AC/ARC 的实现覆盖、局部自验、最新快照证据和无阻塞。COMPLETED 表示本轮实施完成，不表示完整业务或系统验收通过。独立的 Review/Test Gate 不是实施完成的默认前置条件；已知失败必须处理。

实施自验默认定向单元测试，单测无法证明本轮局部接口交互时才补充最小契约或集成测试，并说明原因。禁止 imp 执行完整业务流程验证、系统整体效果验证及全量业务回归；AC/ARC、跨 Spec 影响分析和专项门禁均不触发扩大范围。此类验证由 Agent 按任务契约与已有授权选择 `sdd-test-loop` 或专项验收承担，不作为 imp 完成的前提。证据注明实际局部覆盖和待验收范围，不把局部通过推定为完整或组合验收通过。

Agent 按任务目标、风险与已有授权选择 Review/Test Loop，无需用户点名；不因实施完成而固定追加两个 Gate，也不将流程接续当作扩大验收范围的授权。架构审查对照已确认 Blueprint 检查真实实现；需求验收对照 Spec 检查真实行为。多 Spec 分别记录并核验相关跨能力关系；不从每份单独 PASS 推导组合 PASS。修复限授权范围，由当前执行者修复后复核；已要求独立审查时回原独立审查者复核。契约缺口报告给用户，不降低要求以获得 PASS。

## 交付

任务包含 Git 交付时，Agent 自主选择 `sdd-commit`，默认 Main 执行。本地 commit 及必要检查在明确任务范围内自主执行；新分支、push、PR/MR 创建或更新、merge 按该 Skill 的具体计划确认。已批准且未变化的动作不重复询问。交付不能反向将未完成的需求标成完成，也不强制追加两个独立 Loop。

## 强制架构基线

所有项目遵循[运维与可观测基线](observability-baseline.md)。它与待选规则库区分；项目 Blueprint 引用并映射稳定 ARC，Spec 与专题细化，Status 记录证据。已有正文的漏项/冲突不由初始化覆盖，不因漏引用豁免；由 Agent 在文档授权范围内选择 sdd-doc 归并，Review 按基线检查并闭环。安装与机械校验不证明遵循。
