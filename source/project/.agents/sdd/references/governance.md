# SDD 实体与执行治理

后续任务遵循[工程资产、项目决策职责与可视化对齐](../../governance/repository.md)，由[项目索引](../../../docs/index.md)解析实际路径与模板。

## 职责与交接

讨论负责形成需求、架构和方案决定。sdd-doc 负责整理已确认对话内容、写入对应文档，并在每次写入内解决完整性、一致性、重复和格式问题。sdd-imp 负责实现、修复与必要局部自验。sdd-review-loop 在 sdd-doc 已保证蓝图及关联文档一致的前提下，检查蓝图与真实实现的一致性。

复用已有文档写入检查结果；架构 Review 遇到文档冲突时交回 sdd-doc，设计未决时交回讨论，实现偏差交回 sdd-imp。各流程产出实际结论与证据，正式文档由 sdd-doc 归并。交接沿用已有授权与明确归属。

## Skill 场景与对象分工

SDD Skill 由 Agent 根据用户任务意图与 Task Contract 自主选择和接续，无需用户显式输入 sdd-* 指令，默认 Main 执行。选择流程不扩大目标、写入、测试、外部操作或 Git 交付的授权范围；纯讨论不落盘，文档完成不自动授权实施。Skill 表示工作职责，不对应固定 Agent；实际工作的模型分工、推理强度与协作边界按 [执行约定](delegation.md) 执行。

| Skill | 场景与职责 | 判断依据 / 作用对象 | 结果 |
|---|---|---|---|
| sdd-init | 安装、升级能力，补齐缺失骨架 | 仓库 Skill、工具、模板、治理入口及必要配置 | 可用安装及冲突说明 |
| sdd-doc | 对话结论整理、落盘及写入一致性检查 | 确认来源及现行权威 → 授权文档 | 准确实体内容、引用及集中问题声明 |
| sdd-imp | 实施、局部自验与修复 | Spec + Blueprint → 授权代码/测试及验证证据 | 本轮 AC/ARC 实现覆盖与局部自验证据 |
| sdd-review-loop | 蓝图与实现一致性检查及整改后复核 | Blueprint/ARC → 实现及跨能力关系 | Review Gate 与快照证据 |
| sdd-test-loop | 需求行为验收及整改后复验 | Spec/AC → 实际行为及测试 | Test Gate 与快照证据 |
| sdd-commit | 执行指定 Git 交付终点 | 授权差异、提交、分支、远端、PR/MR | 已核验的交付回执 |

设计讨论由用户当前对话完成；sdd-doc 只承接已确认结论。各执行流程提供状态事实与证据，Status 由 sdd-doc 统一落盘。Review 检查架构落地，Test 检查需求行为，二者不相互替代；执行 Loop 不等于已获得独立审查证据，独立性按实际执行者判断。

## 权威实体

| 实体 | 权威内容 | 写入者 |
|---|---|---|
| Blueprint | 全产品用户用例、终端、体验与关键验收，以及架构、概念所有权、边界及已确认 ARC | sdd-doc|
| 能力需求 | 已确认目标、行为、边界与 AC；按项目索引定位 Issue、Spec 或既有需求正文 | sdd-doc|
| Status | 当前迭代进度、真实证据、阻塞与恢复点 | sdd-doc|

新项目默认落点见[项目资产规则](../../governance/repository.md)，例如 `docs/blueprint.md`；已有项目沿用索引映射。从目标项目 `docs/index.md` 定位需求、Blueprint、接口契约及已有状态记录。Spec 表示能力需求的逻辑角色，可由 Issue 或项目已有正文承担；不得因使用模板另建竞争正文。初始化不创建需求或状态正文。代码是实现事实；模板、候选规则库及历史讨论不是已批准契约。

## 架构表达与判定

架构至少说明以下视图；可按项目规模合并章节、引用已有正文，不要求增加文件层级：

| 视图 | 必须说明的内容 |
|---|---|
| 目标与取舍 | 引用产品用例及 BDD 验收场景，说明架构响应、方案选择理由、代价及适用条件；质量标准不另立正文 |
| 概念与关系 | 核心概念、关系和不能混同的边界 |
| 模块与能力 | 职责、I/O、协作接口、允许及禁止的依赖 |
| 状态与权限 | 权威状态所有者、请求者、决策者、写入者、副作用执行者及完成事实 |
| 运行与工程 | 执行位置、信任边界、宿主与装配、源码与构建映射入口（明细归既有工程文档） |
| 交互与失败 | 正常顺序、并行、取消、迟到、失败、未知及恢复边界 |

这些是表达要求；模块数量、平面、目录、技术模式及部署方式由项目确认，不把单个项目的选择推广为通用约束。只落盘已确认内容，缺失的实质设计列为待决策，不为满足视图补造方案。

蓝图可按项目需要以部署视角表达宿主、运行时、存储、服务及信任边界，以组件视角表达逻辑职责、公开接口与依赖；逻辑组件不推定独立进程。总时序表达模块或公开接口间的关键交互、竞争和异常，不复制接口契约或展开内部类算法。活动图按复杂分支、并行汇合或数据加工的实际收益使用并区分控制流与对象流；状态机和 ER 按需使用，内部类图默认不要求。厂商、迁移和检索细节归所属章节，按任务按需读取，不作为普遍前置。

模块契约参考[模块契约模板](../assets/module-design.md)，总时序参考[跨模块时序模板](../assets/sequence-flows.md)，实际落点按[项目资产规则](../../governance/repository.md)及项目索引确定。全产品用户用例、终端、关键体验和关键 BDD 验收可由蓝图产品视角索引，详细需求与 AC 保留在项目已确认的需求正文。概念所有权、模块职责与必要数据权威合并于组件与职责，部署与宿主装配合并于部署与运行边界；蓝图协作部分只索引产品场景到契约/总时序。产品级质量标准归关键 PAC 或明确详细 AC 引用，架构部分按 PUC/PAC 引用并记录策略、取舍与不变量，不重复产品验收正文。

总览维护职责、状态所有权与不变量，所属专题维护接口、必要机制及异常语义；同一条款只有一个现行正文。跨文档摘要必须指向权威条款，不增加条件或缩小范围。ARC 及已有条款标识不随章节、文件移动改变；迁移核对关键约束的完整承接及有效引用，不只检查链接是否存在。当前实现与进度归 Status / 任务。

遵循判定区分“架构语义 → 当前实现映射 → 所需证据”。目录、包名及类名用于定位，不能替代职责、状态所有权、权限和调用链检查；迁移更新映射，不隐式改变规则。跨模块请求、受理、执行、交付、应用及呈现分别取证，不相互代替。

变更按语义影响分级，项目在其遵循规范维护适用判据：L0 为实现变化且外部契约与架构语义不变；L1 为已确认边界内的契约扩展，须同步生产者、消费者及异常语义；L2 为职责、状态权威、决策权限、信任边界、依赖方向或关键不变量的改变，须按项目门禁确认。提示词或目录改动同样按影响判断；纯正文迁移且语义不变不升级为架构决策。文档授权不自动授权同步代码，未实施部分如实留待办。

## 文档写入检查

文档写入交由 sdd-doc；执行写入时读取[文档写入规则](document-writing.md)。其他流程只提供确认结论和真实证据。

## 按任务意图定位正文

从 `docs/index.md` 按当前问题进入实际权威章节。已有正文时直接链接到相关章节；尚无产物时链接适用模板，并明确它是编写入口。设计依据与指定版本的验证证据分开导航，缺少版本、场景或可复查证据就标为未验证。

在使用处保留必要的引用：需求链接适用原型；蓝图维护职责与不变量，引用驱动决定的需求，按需链接关键时序；时序就近引用需求、蓝图条款与必要接口；契约引用所属模块或不变量。实验记录关联问题与复现入口，测试计划引用被验证的要求，验收报告沿用计划的场景编号并关联实际证据。

正文变化在原处改写。仅当权威入口新增、移动或被替代时，才更新索引及直接受影响的引用。引用按当前任务需要维护，无需反向登记。

## 测试范围约束

产品经理可在约定运行环境操作实际集成版本，对照中保真 HTML 原型和非功能指标完成可视化验收。结构、业务状态、交互、权限、错误路径及指标按已确认测试范围验证；纯视觉样式和像素还原不设自动化门禁。按断言目标判断，浏览器或截图仅是手段。

产品原型确认、局部自验、运行检查与集成验收分别取证。混合条款按取得的证据说明覆盖范围，未验证项如实标识，局部证据不能推导整项通过。既有 AC、Status 和 Gate 保留其事实与快照。

## 实施和独立审查

任务包含实施或修复时，Agent 自主选择 `sdd-imp`，简单且已授权的任务由 Main 直接完成；Plan 按实际取舍和风险需要使用，Goal 仅在用户明确要求或更高优先级指令要求时创建。已获授权内不重复设审批，明确要求先审计划时仍遵守。委派后各执行者按模型分工完成对应工作并返回证据，Main 协调实施、局部自验与修复闭环，将状态证据交给 sdd-doc 并核对关键差异；出现缺口、矛盾、失败或快照变化时才深入检查受影响局部。实现完成需要本轮 AC/ARC 的实现覆盖、局部自验、最新快照证据和无阻塞。COMPLETED 表示本轮实施完成，不表示完整业务或系统验收通过。独立的 Review/Test Gate 不是实施完成的默认前置条件；已知失败必须处理。

实施自验默认定向单元测试，单测无法证明本轮局部接口交互时才补充最小契约或集成测试，并说明原因。禁止 imp 执行完整业务流程验证、系统整体效果验证及全量业务回归；AC/ARC、跨 Spec 影响分析和专项门禁均不触发扩大范围。此类验证由 Agent 按任务契约与已有授权选择 `sdd-test-loop` 或专项验收承担，不作为 imp 完成的前提。证据注明实际局部覆盖和待验收范围，不把局部通过推定为完整或组合验收通过。

Agent 按任务目标、风险与已有授权选择 Review/Test Loop，无需用户点名；不因实施完成而固定追加两个 Gate，也不将流程接续当作扩大验收范围的授权。架构审查对照已确认 Blueprint 检查真实实现；需求验收对照 Spec 检查真实行为。多 Spec 分别记录并核验相关跨能力关系；不从每份单独 PASS 推导组合 PASS。实现修复交由 sdd-imp 在授权范围完成，随后返回对应审查或验收复核；已要求独立审查时回原独立审查者复核。契约缺口报告给用户，不降低要求以获得 PASS。

## 交付

任务包含 Git 交付时，Agent 自主选择 `sdd-commit`，默认 Main 执行。本地 commit 及必要检查在明确任务范围内自主执行；新分支、push、PR/MR 创建或更新、merge 按该 Skill 的具体计划确认。已批准且未变化的动作不重复询问。交付不能反向将未完成的需求标成完成，也不强制追加两个独立 Loop。

## 强制架构基线

所有项目遵循[运维与可观测基线](observability-baseline.md)。它与待选规则库区分；项目 Blueprint 引用并映射稳定 ARC，Spec 与专题细化，Status 记录证据。已有正文的漏项/冲突不由初始化覆盖，不因漏引用豁免；由 Agent 在文档授权范围内选择 sdd-doc 归并，Review 按基线检查并闭环。安装与机械校验不证明遵循。
