# SDD 协作约定

普通 Chat 讨论，sdd-doc 固化，sdd-imp 实施，sdd-accept 准备人工验收。Skill 根据明确用户意图选择，不是精确口令。已有清楚结论和授权可直接使用，无需每项工作走完整链路、修改所有实体或另开聊天。

| 用户意图 | 工作与边界 |
| --- | --- |
| 讨论问题、方案、重构或反馈 | 读取必要资料，在聊天中形成结论和待决项；未要求写入时不改文件或远端正文 |
| 将确认内容写到指定位置 | sdd-doc 固化文档及按要求制作原型，不顺带改产品代码 |
| 开始实现、修复或重构 | sdd-imp 修改代码并局部自验，不擅自改变需求或架构，不自动部署验收 |
| 将指定版本准备好供验收 | sdd-accept 拉取、部署、检查入口、提供操作文档，由用户人工操作反馈，不自动修代码 |
| 安装或升级 SDD 资源 | sdd-init 按实际授权安装资源，不代表设计或验收通过 |
| 提交或交付 Git 变更 | sdd-commit 按授权终点执行，不从普通实施推定 push 或 merge 授权 |

“认可”“对”通常只确认结论；同时有写入或实施要求就执行。“落地”按上下文理解，仅在确实影响工作归属时澄清。实质缺口只阻塞受影响部分，模板提示不作为重复审批点。

## 实体与来源

- Issue 是需求正文，包含问题、目标、业务规则、范围、验收条件及适用原型引用。
- Blueprint 保存已确认的职责、接口、状态归属、依赖和不变量；已有路径优先，新文件可按项目需要放在 architecture/blueprint.md，不在安装时自动创建架构决定。
- Draft PR 保存本次实施 Plan、实际差异和结果，引用 Issue 与适用 Blueprint。长期架构决定归 Blueprint，不新建 plan.md 或独立 Spec。
- README 提供定位与导航，AGENTS 提供简洁维护约定。进度与证据可按需要记在现有 PR／任务记录，不复制需求或创建新状态系统。

沿用项目业务事实、术语和已确认决定；同义内容原位归并但不丢失不同条件、范围和验收。模板、候选与实现现状不自动成为已确认决定。普通文档与工具维护不虚构产品原型或架构。

实体模板见 assets 下的 issue.md、blueprint.md、draft-pr.md；[六类场景提示](scenarios.md)按需使用，不机械问完或要求填满。用户决定讨论模型与推理强度，见[协作说明](delegation.md)。

## 测试范围约束

允许信息架构、结构布局、交互和业务状态符合性检查；排除纯视觉样式与像素还原检查。浏览器或截图是手段，按实际验证目标判断。原型模拟、局部自验、部署健康检查和正式系统人工验收分别取证，不以一项成功代替另一项。

验收反馈回到讨论，按需要更新 Issue／Blueprint／Draft PR；明确要求修复后才进入实施。事实、猜测、未验证和失败分别记录，不自动关闭 Issue 或把部署成功写成验收通过。

## 存量工具与参考资源

旧 govern.py 的 start/record/attest/check/finish/commit 及 spec.md、status.md 模板仅服务既有本地 Spec/Status 格式，不支持从 GitHub Issue 读取需求，不作为新流程前置或完成判断。它们可能重建 Status 或按全能力检查；使用前核对现有记录和影响，未经单独迁移范围不运行来替代新流程。新流程直接使用 Issue、适用 Blueprint 和 PR，保留存量事实，不批量迁移。

[观测参考](observability-baseline.md)和架构候选、示例资源仅在项目实际适用且已有决定支持时使用；分发资源本身不确认业务需求、架构或选型。安装、构建与检查通过不代表目标项目升级或验收通过。
