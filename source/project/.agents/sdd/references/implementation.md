# 实施与局部自验

Coder 按实际工单和单一执行模式完成专业任务。各模式的完整边界如下；调用者未给模式时，可从明确工单动词识别，但不得将调查、准备或失败自动升级为写实现。

## 执行模式

| 模式 | 输入前提 | 允许动作 | 禁止动作 | 停止／交付条件 |
| --- | --- | --- | --- | --- |
| `investigate` | 明确问题与目标、读取和运行边界、已知版本／环境或可取得方式、停止条件 | 读取相关源码和证据；运行获授权的非破坏检查、复现或技术比较；按授权写调查记录 | 修改产品、测试代码或配置；选择修复；实施方案执行；把假设当已验证归因 | 返回事实、可复现入口、证据、结论／反证、局限与接续条件；即使问题明确也只回报可行下一模式 |
| `prepare` | 明确目标、范围、授权终点、实施记录写入边界和可用依据 | 读取直接相关材料；编写或调整获授权的工单、Plan／Task、依赖与检查入口；标记缺项 | 修改产品或测试实现；运行实施；以准备完成代替工单就绪或实施完成 | 交付可评审或可接续的准备产物、待补输入、就绪结论和后续所需授权 |
| `implement` | [工单就绪](delegation.md#工单就绪)、明确实施授权及可执行判据 | 在写入边界内修改产品代码、测试和必要配置；维护分档 Plan；执行局部检查 | 超出范围或写入边界；缺判据猜实现；自行决定需求验收、集成、架构复核或发布通过 | 达到任务完成条件、局部检查有证据；回传未覆盖或待验 Gate，失败保留 |
| `fix` | 原 Issue、要恢复行为、已验证原因及证据、修复边界与复验判据、实施授权 | 沿原编号修复根因；补必要测试和配置；运行定向复验与必要局部回归 | 未验证归因就改代码；归因反证后继续原方向；改变需求或越界修复；自行关 Issue | 修复版本满足工单的局部判据；反证、无法复现或失败时停止该方向，沿原编号保留证据并回报恢复条件 |
| `refactor` | 原目标或 Review CHK、技术边界、须保持行为及基线、局部与后续验收入口、实施授权 | 在授权范围内调整结构、职责、接口内部实现及测试；维持已确认外部行为 | 改变需求、架构结论或公开契约；自行判定架构 Review／业务保持通过；把无关技术债并入 | 局部结构检查和行为保持检查有证据；将同一 CHK、待复核项及版本交回指定复核承接者 |

模式切换只来自调用者的明确授权；同一执行者可在下一回合接单新模式，但本回合不得用“发现了实现、已有方案、检查失败”自动扩权。只获授权修改测试资产时只改测试，仍可记录被测产品与证据，不得同步修产品。

## 实施依据

按工单目标、适用判据及相关代码和测试确定读取范围。项目索引只用于定位所需材料。涉及 Blueprint 或 ARC 时，只读取工单直接引用且本轮适用的已确认条款，索引链接本身不构成工单引用。Code Review Rules 的检查和架构符合性判断归架构审查，Coder 不自行判 Gate。复用已确认 HTML 原型时读取[原型规则](prototype.md#正式实现中的复用)。

## Plan 分档

在当前 Task 记录或既有计划载体维护一份 Plan，按实际复杂度只选最小分档；不要为单文件任务复制完整模板。

- **轻量**：单一局部改动、通常单文件或无真实依赖，只列一个 Task 的目标／完成判据、范围／模式与写入边界、检查入口、状态及结果。调查、准备也可只用当前回执加必要记录。
- **完整**：多文件、多个交付结果、共享前置或直接依赖，使用 [Plan 模板](../assets/plan_template.md)的完整 Task 字段和 DAG。修改同一文件或同一可变共享状态的 Task 必须串行；无数据、文件或状态冲突的 Task 可并行。异步依赖只有在依赖 Task 的明确完成条件满足并移交实际证据后才解锁，等待期间不得猜测其结果。
- **长程**：跨轮、需暂停恢复或存在未稳定外部依赖，在完整 Plan 上增加恢复点，记录有效授权／确认状态、已完成 Task、有效证据、待决项、下一就绪项及证据失效条件；变化后按失效条件重评，不重建重复台账。

Task 的直接依赖必须无环。依据、判据、版本、环境、工作树或实现变化时，只失效实际受影响 Task 和证据，保留编号及仍适用结果。

## 执行与验证

1. 核对模式和工单就绪。`implement`、`fix`、`refactor` 缺任何最小字段时只返回 `needs-input`／`blocked`，或在已有产物时返回 `partial`，不得开始写产品或测试代码。`investigate` 和 `prepare` 只能核对当前终点，不自行补齐实施授权。
2. 选取最小 Plan 分档并记录 Task。需求实施按直接适用的 Spec／AC 拆分；缺陷、Review 与其他工单按原编号映射。开工前记录足以执行的方案和影响顺序的未知项，跨职责取舍只列选项与证据，不擅自决定。
3. 按依赖就绪项执行。涉及 TDD 时先按约定运行检查并保留预期基线失败；仅测试授权不得触碰产品。局部自验以定向单测、构建、类型或运行检查为主，命令和结果须可重现。
4. 每个 Task 完成或交接时核对版本、工作树、环境、检查结果和覆盖。失败状态与原始证据不得在修复后删除；失败后的成功复验引用同一 Task，并说明前后版本。未满足的前置使依赖项阻塞并给恢复条件，其他已授权且就绪项继续。
5. 交付前核对实际改动、版本指纹、检查命令／结果、覆盖判据和缺口。局部自验只证明本轮实际覆盖，不构成需求验收、集成 Test Gate、架构复核、发布 Gate 或线上通过。约定后续验收时只交付入口、准备条件和待验判据。

缺陷模式在归因反证、不可比较版本或复验失败时保留原 Issue 编号和实际证据，停止当前修复方向；其他不受影响的授权任务继续。`refactor` 仍须由相应执行者按原 `CHK` 完成架构复核和行为保持验收。缺失测试以场景依据和测试写入边界为输入，沿用已确认判据，在回执记录被测产品偏差；产品修复仍需另行授权。

按[任务回执](task-receipt.md)向任务调用者返回结果；证据适用性按[证据与复用](sdd-repository-governance.md#证据与复用)核对。
