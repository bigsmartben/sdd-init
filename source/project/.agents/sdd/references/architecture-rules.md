# 架构规范

本规范受[仓库治理](sdd-repository-governance.md)约束，定义可落实到系统与代码并可审查的通用约束与专项约束。本规范作为架构 Review 的输入，不作为需求／架构讨论、Blueprint 写入或 imp 实施的前置约束。架构规则的检查、偏差判断和整改目标由 Review 承担；imp 仅交付明确的上游任务，不承担规则读取或符合性判定。Blueprint／项目设计表达已确认的实际模块、协作与部署，框架与脚手架提供代码、配置和生成能力，Review／测试证据证明实际遵循。

Review 在审查证据中关联适用约束与已有稳定 ARC／项目条款；尚未确认的环境、参数和技术选型列为待决，不由模板或示例补定。工程资产分类、用途、归属、默认落点与维护统一见[仓库治理](sdd-repository-governance.md#工程资产边界)，本规范不重复定义。

## 通用约束

系统与模块须按已确认职责实现；公开接口、内部实现、允许及禁止的依赖方向、状态权威和运行边界应与设计一致。请求、决策、写入和副作用由对应职责承担，跨模块协作通过已确认接口进行，不以目录或包名相同代替职责与依赖语义一致。

### 业务实体持久化

业务代码中，所有业务实体的持久化必须写入数据库；日志、普通文件或仅驻留内存的缓存不能替代业务实体落库。业务状态的权威归属仍由业务领域承担，观测记录不作为业务持久化存储。数据库类型、数据模型、写入时机、持久化完成的判定条件及失败后的业务行为由项目设计明确，具体事务、重试和恢复机制由项目选择。

### 业务与运维可靠性职责分离

业务领域负责业务规则、权威业务状态与业务流程。运维／基础设施领域统一承载技术流控（限流、背压、熔断）、链路追踪、指标监控、运行诊断，以及进程唤醒、保活、重启和故障恢复。业务通过明确接口使用必要的基础设施能力，不在业务模块重复实现这些机制。此处划分模块技术职责，资产归属仍按[工程资产边界](sdd-repository-governance.md#工程资产边界)确定。

按职责语义判断归属：套餐调用额度等业务配额属于业务规则，唤醒词识别等产品能力属于业务功能；不能因名称类似技术限流或进程唤醒而归入运维。

观测能力保持非侵入，遵循下方可观测性架构规范。技术流控与进程生命周期管理属于运行控制能力，通过已确认的接口、权限与策略作用于运行过程；其允许的控制行为及故障后果由项目契约明确，不套用观测能力“不得影响业务运行”的约束，也不因此改变业务规则或业务状态的权威归属。

### 正式实现与测试实现隔离

正式运行依赖链与装配不得直接或间接依赖、加载或启用测试代码资产，包括实验实现、夹具、原型测试运行器及其他测试运行器；约束覆盖正式入口和正式模块的引用、动态加载及配置装配。测试可以调用正式模块；用例身份不授予业务权限，不产生正式路由、数据库字段或运行开关。

按[工程资产边界](sdd-repository-governance.md#工程资产边界)归类的测试代码正式采用时，须迁入或提取到正式模块，移除模拟及实验装配，并补齐真实接口、权限与异常处理；必要测试和夹具保留在测试资产中。

## 专项约束

### 可观测性架构规范

业务负责业务执行及权威业务数据；观测负责日志、指标及链路的采集、关联、导出与分析。链路表达跨调用关联与先后，不充当业务状态或新的业务执行通道；日志记录事实，指标提供统计，三者通过项目契约关联。

业务与观测的依赖、故障及资源隔离遵循[观测基线 SDD-OBS-01](observability-baseline.md#职责与隔离sdd-obs-01)。该专项正文同时约束观测对业务的影响，以及业务使用观测数据、工具实现功能的反向依赖。

### 日志规范

日志事件、结构、字段、级别、关联、脱敏、采集、传输、缓冲、持久化、轮转、保留与失败处理统一遵循[日志专项要求](observability-baseline.md#日志实现规范)。SDD-OBS-02/03 的媒体边界、必要文字持久化及跨语言契约继续适用。项目将策略落实为可核对的契约与配置。

### 环境架构规范

开发、集成测试等环境可在同一份项目设计中分别表达，须明确各自拓扑、运行时、依赖服务、配置、网络、存储、数据及隔离边界。实际启动、连接与存储装配须符合所选环境的已确认设计。

环境切换须使用对应配置和数据边界；真实与模拟依赖、共享与独占资源及允许的网络访问应可辨识。环境差异及其对验证条件的影响须明确。规范不预选容器平台、部署拓扑、版本或服务端点。

### 脚手架规范

脚手架必须依据已确认架构生成工程骨架。模块化、包结构、公开接口与内部实现边界、依赖方向、构建单元及运行装配须与架构设计匹配，不得擅自增加模块、分层或依赖。

架构变更后检查并同步受影响的生成模板与生成结构，核对实际职责、接口、依赖和装配语义；目录名称一致不足以证明匹配。资产归属、落点及生成产物维护遵循仓库治理，不在脚手架规范另设分类。

### 测试工程与自动化规范

单元测试与集成测试是测试层次，回归是验证目的，可组合多个层次，不另建第三套独立框架。测试工程须按以下技术约束落实项目已确认的测试目标；测试范围决策、协作与验收结论仍归仓库治理。

| 技术对象 | 必须明确并落实的约束 |
|---|---|
| 测试边界与依赖 | 定义被测单元或组件、依赖替代边界、真实／模拟依赖的使用条件；集成与契约检查按声明的依赖条件执行交互 |
| 确定性与数据 | 控制影响结果的时间、随机性及外部状态；明确数据初始化、隔离与清理，执行失败后的清理结果可检查 |
| 结构与框架 | 用例、夹具、运行器按[工程资产分类](sdd-repository-governance.md#工程资产边界)组织；明确框架接入、配置和生命周期，复用已选框架能力 |
| 断言与验证依据 | 功能验证的断言对应需求或接口契约；探索验证对应已明确的假设、候选方案、比较目标及判断指标。检查可观察结果及适用的异常和边界，不能仅复述实现或以“未抛异常”代替目标判断 |
| 并行与恢复 | 明确共享资源、并行隔离、超时和重试条件；重试保留首次失败及各次结果，不以重试掩盖不确定性或重复副作用 |
| 执行与诊断 | 本地与 CI 使用一致的测试入口及配置约定，环境差异显式传入；运行器保留原始输出与诊断，关联场景／用例、算法或候选路径、运行版本、环境、结果及失败；正式报告归属见仓库治理 |

架构表达方法见[蓝图模板](../assets/blueprint_template.md#架构表达与判定)，变更分级及检查流程见[仓库治理](sdd-repository-governance.md#架构变更与遵循检查)。
