# 架构规范

本规范面向目标运行项目，按一级架构范式、二级规范指导组织。通用要求是明确边界、权威、契约及可验证的行为；具体职责归属、技术模式、运行策略、故障行为和隔离程度由目标项目确认，沿用适用的既有决定。规范指导不直接成为项目门禁，未确认的取舍列为待决，不预选分层、模块数量或部署方式。

| 一级：架构范式 | 二级：规范指导 |
|---|---|
| 职责与权威明确 | [模块边界与依赖](#模块边界与依赖)、[状态权威与持久化](#状态权威与持久化)、[业务与运行保障分工](#业务与运行保障分工) |
| 契约驱动协作 | [接口与交互语义](#接口与交互语义)、[观测数据与日志契约](#观测数据与日志契约) |
| 隔离与受控影响 | [观测影响与故障隔离](#观测影响与故障隔离)、[环境边界与运行装配](#环境边界与运行装配)、[测试隔离与可控验证](#测试隔离与可控验证) |

架构不变量贯穿适用规范，覆盖正常、失败、并发、取消和恢复路径，不另设独立类别。各项按对象和风险适用，不要求每项单独建立模块或文档。

## 职责与权威明确

<a id="系统与模块边界"></a>
<a id="工程骨架规范"></a>

### 模块边界与依赖

系统与模块须按已确认职责实现；公开接口、内部实现、允许及禁止的依赖方向、状态权威和运行边界应与设计一致。请求、决策、写入和副作用由对应职责承担，跨模块协作通过已确认接口进行，不以目录或包名相同代替职责与依赖语义一致。

工程目录、模块、package、构建单元及运行装配须落实这些约束。新增模块、分层或依赖须有已确认的架构依据。设计变更后同步受影响的工程结构；使用生成模板时同步模板并核对生成结果。手工与生成的工程结构均沿实际职责、接口、依赖和装配路径核对，资产归属遵循[工程资产边界](sdd-repository-governance.md#工程资产边界)。

<a id="单一事实来源ssot"></a>

### 状态权威与持久化

同一作用域内，同一事实有一个逻辑权威来源。明确谁负责写入和裁决分歧，以及副本、缓存、快照或派生数据的用途。复制、多节点写入或合并机制须明确一致性与冲突裁决规则，不将逻辑权威等同于单一物理数据库。沿实际读取、写入及恢复路径指出哪些入口可以决定该事实。

#### 业务实体持久化

对需要持久化的业务实体，明确权威存储、写入职责、写入完成判据、写入失败处理及恢复要求。普通观测副本不能未经设计确认成为状态权威；按用途被确认为权威业务记录的数据须遵循业务契约，不能仅凭日志或事件的形式判断归属。

<a id="业务与运维可靠性职责分离"></a>

### 业务与运行保障分工

项目明确业务规则、运行策略及技术执行机制的责任主体、作用域和协作接口。限流、背压、熔断、诊断、进程唤醒、保活、重启和恢复的模块归属、集中或分散实现方式由项目确认。区分策略制定者与机制执行者、技术恢复与业务补偿；多层保护或重复机制须说明目的、叠加效果和冲突处理，不统一归入运维，也不一概禁止业务模块实现。

按职责语义判断归属：套餐调用额度等业务配额属于业务规则，唤醒词识别等产品能力属于业务功能。运行控制须通过已确认的接口、权限与策略作用于运行过程，明确对业务状态、结果及副作用的影响，不能因流控、重启或重试而隐式取得业务裁决或重放权限。资产归属仍按[工程资产边界](sdd-repository-governance.md#工程资产边界)确定。

## 契约驱动协作

### 接口与交互语义

明确调用双方、输入输出、权限、状态及副作用归属，区分发送、接收、受理和完成，未知结果不能表达为成功。按适用性明确同步与异步、顺序、并行、竞争、身份与版本关联，以及取消、超时、迟到结果、重试、回滚和恢复语义。只表达实际保证的顺序与等待，重试和恢复不得超出契约扩大副作用。以实际接口和状态路径验证，不强制采用事件驱动或独立服务。

### 观测数据与日志契约

按数据用途明确事件、字段、关联、保存完成、禁存与保留要求，以及缺失和失败的表达。具体指导见[数据保存与日志契约](observability-baseline.md#数据保存与日志契约)和[采集、持久化与故障处理](observability-baseline.md#采集持久化与故障处理)。

## 隔离与受控影响

<a id="可观测性架构规范"></a>

### 观测影响与故障隔离

按用途确认观测对业务状态、决策、执行、资源及生命周期的允许影响，以及阻塞、故障传播和降级边界。同步或异步、隔离程度、开销预算、丢失容忍度及记录失败是否阻止业务由项目确认；具体指导见[可观测性架构规范](observability-baseline.md)。

<a id="环境架构规范"></a>

### 环境边界与运行装配

明确各环境拓扑、运行时、依赖服务、配置、网络、存储、数据及隔离边界。实际启动、连接与存储装配须符合所选环境的已确认设计。

环境切换须使用对应配置和数据边界；真实与模拟依赖、共享与独占资源及允许的网络访问应可辨识。明确环境差异对行为与验证条件的影响。具体共享策略和隔离程度由项目确认，不强制物理隔离，不预选容器平台、部署拓扑、版本或服务端点。

<a id="测试工程与自动化规范"></a>

### 测试隔离与可控验证

#### 正式实现与测试实现隔离

正式运行不得直接或间接依赖、加载或启用实验实现、夹具、原型测试运行器等测试代码资产。正式入口、模块依赖、动态加载或运行配置发生变更时，须沿实际运行路径检查正式依赖链及配置装配。

测试可以调用正式模块。用例身份不授予业务权限，不产生正式路由、数据库字段或运行开关。按[工程资产边界](sdd-repository-governance.md#工程资产边界)归类的测试代码正式采用时，须迁入或提取到正式模块，移除模拟及实验装配，并补齐真实接口、权限与异常处理。必要测试和夹具保留在测试资产中。

#### 测试设计与执行

单元测试与集成测试是测试层次，回归是验证目的，可组合多个层次，框架与运行入口按项目设计分工，避免无依据的职责重复。测试工程须按以下技术约束落实项目已确认的测试目标；测试范围决策、协作与验收结论仍归仓库治理。

| 技术对象 | 必须明确并落实的约束 |
|---|---|
| 测试边界与依赖 | 定义被测单元或组件、依赖替代边界、真实／模拟依赖的使用条件；集成与契约检查按声明的依赖条件执行交互 |
| 确定性与数据 | 控制影响结果的时间、随机性及外部状态；明确数据初始化、隔离与清理，执行失败后的清理结果可检查 |
| 结构与框架 | 用例、夹具、运行器按[工程资产分类](sdd-repository-governance.md#工程资产边界)组织；明确框架接入、配置和生命周期，复用已选框架能力 |
| 断言与验证依据 | 功能验证的断言对应需求或接口契约；探索验证对应已明确的假设、候选方案、比较目标及判断指标。检查可观察结果及适用的异常和边界，不能仅复述实现或以“未抛异常”代替目标判断 |
| 并行与恢复 | 明确共享资源、并行隔离、超时和重试条件；重试保留首次失败及各次结果，不以重试掩盖不确定性或重复副作用 |
| 执行与诊断 | 本地与 CI 使用一致的测试入口及配置约定，环境差异显式传入；运行器保留原始输出与诊断，关联场景／用例、算法或候选路径、运行版本、环境、结果及失败；正式报告归属见仓库治理 |

## 在目标仓库中落实

项目规则的生成与更新按[决策边界](sdd-repository-governance.md#目标仓库的-code-review-rules)执行。收到明确要求后，依据已确认的设计、契约及实际路径，将适用指导归并为项目 [Code Review Rules](../assets/code-review-rules_template.md)。沿用现有规则编号、代码、配置、测试和审查机制，不要求逐项新增模块或文档。安装、升级和写入 Blueprint 本身不触发规则维护。

每条项目规则须明确以下要素，执行证据归相应 Review 或测试报告：

| 要素 | 可执行要求 |
|---|---|
| 适用对象与条件 | 指定模块、接口、状态或运行路径及适用条件 |
| 已确认的决定 | 引用设计依据，明确允许、禁止和项目选定的策略；缺少依据或冲突的部分列为待决 |
| 检查方法 | 指定依赖扫描、语义审查、实际路径追踪、契约测试或故障实验等方法及取证入口 |
| 通过条件 | 给出可观察结果、适用预算或阈值及违规判据，不能以原则口号代替结果判断 |
| 检查时机 | 明确触发检查的直接变更或间接影响，以及适合的局部验证、CI 或专项审查时机 |

| 规范指导 | 落实对象与检查示例 |
|---|---|
| 模块边界与依赖 | 检查模块、接口、包依赖及构建入口，结合依赖扫描与语义审查识别越界调用 |
| 状态权威与持久化 | 追踪数据库、缓存和状态入口的读写；验证写入失败、重复写入及恢复后的状态 |
| 业务与运行保障分工 | 检查策略与执行入口；验证重试、重启和降级是否越权或产生重复副作用 |
| 接口与交互语义 | 对 API、消息、回调或状态机执行适用的契约及场景测试，覆盖并发、取消、超时及迟到结果 |
| 观测数据与日志契约 | 检查事件结构、采集接口和保存路径，验证字段、关联、敏感数据处理、完成及保留策略 |
| 观测影响与故障隔离 | 模拟导出失败、缓冲饱和或存储不可用，检查业务行为和资源开销是否符合项目策略 |
| 环境边界与运行装配 | 检查实际启动、连接、权限及数据落点，验证环境切换与依赖选择 |
| 测试隔离与可控验证 | 沿正式依赖链和配置检查测试替代行为，验证数据清理、并行隔离、失败保留及复跑条件 |

机械检查用于结构、依赖和证据辅助，不能替代职责语义、策略适用性或证据充分性的判断。Review 依据已确认项目规则检查；未确认的推荐策略不能作为违规判据，未执行或证据不足的检查不能报告通过。变更分级及检查流程见[仓库治理](sdd-repository-governance.md#架构变更与遵循检查)。
