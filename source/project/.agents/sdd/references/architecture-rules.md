# 架构规范

本规范面向目标运行项目，按一级架构范式、二级规范指导组织。通用要求是明确边界、权威、契约及可验证的行为；具体职责归属、技术模式、运行策略、故障行为和隔离程度由目标项目确认，沿用适用的既有决定。规范指导不直接成为项目门禁，未确认的取舍列为待决，不预选分层、模块数量或部署方式。

| 一级：架构范式 | 二级：规范指导 |
|---|---|
| 职责与权威明确 | [模块边界与依赖](#模块边界与依赖)、[状态权威与持久化](#状态权威与持久化)、[业务与运行保障分工](#业务与运行保障分工) |
| 契约驱动协作 | [接口与交互语义](#接口与交互语义)、[观测数据与日志契约](#观测数据与日志契约) |
| 隔离与受控影响 | [观测影响与故障隔离](#观测影响与故障隔离)、[环境边界与运行装配](#环境边界与运行装配)、[测试隔离与可控验证](#测试隔离与可控验证) |

架构不变量贯穿适用规范，覆盖正常、失败、并发、取消和恢复路径，不另设独立类别。各项按对象和风险适用，不要求每项单独建立模块或文档。

以下 AR 编号是技能预置 checklist 的稳定标识，条款所在段落保留适用边界与例外。勾选表示已经核对并记录结论，不表示实现通过。依据已确认项目决定将适用项映射到项目规则，再按子系统、模块、组件及协作边界建立独立 [Review Matrix](../assets/review-matrix_template.md)。项目判据、批次任务与证据不写回通用 checklist。

## 职责与权威明确

<a id="系统与模块边界"></a>
<a id="工程骨架规范"></a>

### 模块边界与依赖

- [ ] **AR-01.1**：沿实际接口和调用链核对系统与模块职责、允许及禁止的依赖、状态权威和运行边界是否落实已确认设计。请求、决策、写入和副作用由对应职责承担，跨模块协作通过已确认接口进行，不以目录或包名相同代替职责与依赖语义一致。越界承担职责或绕过已确认接口构成偏差。

- [ ] **AR-01.2**：核对工程目录、模块、package、构建单元、生成模板及运行装配是否落实这些约束。新增模块、分层或依赖须有已确认的架构依据。设计变更后同步受影响的工程结构；使用生成模板时同步模板并核对生成结果。手工与生成的工程结构均沿实际职责、接口、依赖和装配路径核对，结构与职责或装配不符构成偏差。资产归属遵循[工程资产边界](sdd-repository-governance.md#工程资产边界)。

<a id="单一事实来源ssot"></a>

### 状态权威与持久化

- [ ] **AR-02.1**：沿读取、写入及恢复路径核对同一作用域内同一事实的逻辑权威、写入职责及分歧裁决是否明确且落实。明确副本、缓存、快照或派生数据的用途。复制、多节点写入或合并机制须明确一致性与冲突裁决规则，不将逻辑权威等同于单一物理数据库。未授权入口决定该事实或副本越权裁决构成偏差。

#### 业务实体持久化

- [ ] **AR-02.2**：对需要持久化的业务实体，沿成功、写入失败及恢复路径核对权威存储、写入职责、完成判据及恢复要求。保存结果和失败表达须符合业务契约，未满足完成判据即返回成功构成偏差。普通观测副本不能未经设计确认成为状态权威；按用途被确认为权威业务记录的数据须遵循业务契约，不能仅凭日志或事件的形式判断归属。

<a id="业务与运维可靠性职责分离"></a>

### 业务与运行保障分工

- [ ] **AR-03.1**：沿策略与执行入口核对业务规则、运行策略及技术机制的责任主体、作用域和协作接口是否符合项目决定。限流、背压、熔断、诊断、进程唤醒、保活、重启和恢复的模块归属、集中或分散实现方式由项目确认。区分策略制定者与机制执行者、技术恢复与业务补偿；多层保护或重复机制须说明目的、叠加效果和冲突处理，不统一归入运维，也不一概禁止业务模块实现。

- [ ] **AR-03.2**：按职责语义判断归属：套餐调用额度等业务配额属于业务规则，唤醒词识别等产品能力属于业务功能。检查流控、重启、重试及恢复路径是否遵守已确认接口、权限、策略和副作用边界；隐式取得业务裁决、重放权限或产生契约外重复副作用构成偏差。资产归属仍按[工程资产边界](sdd-repository-governance.md#工程资产边界)确定。

## 契约驱动协作

### 接口与交互语义

- [ ] **AR-04.1**：沿接口和状态路径核对调用双方、输入输出、权限、状态及副作用归属，区分发送、接收、受理和完成；未知结果表达为成功构成偏差。
- [ ] **AR-04.2**：按适用性以契约或场景验证同步与异步、顺序、并行、竞争、身份与版本关联，以及取消、超时、迟到结果、重试、回滚和恢复语义。只表达实际保证的顺序与等待，重试和恢复不得超出契约扩大副作用。不强制采用事件驱动或独立服务。

### 观测数据与日志契约

- [ ] **AR-05.1**：按数据用途检查事件、字段、关联、保存完成、禁存与保留要求，以及缺失和失败的表达是否符合项目契约。沿采集与保存路径取证，缺少必需数据、保存完成错报或违反禁存／保留要求构成偏差。专项判据来源见[数据保存与日志契约](observability-baseline.md#数据保存与日志契约)和[采集、持久化与故障处理](observability-baseline.md#采集持久化与故障处理)。

## 隔离与受控影响

<a id="可观测性架构规范"></a>

### 观测影响与故障隔离

- [ ] **AR-06.1**：按用途核对观测对业务状态、决策、执行、资源及生命周期的影响是否符合项目决定。按风险模拟导出失败、缓冲饱和或存储不可用，检查阻塞、故障传播、降级及资源开销；超出已确认边界或预算构成偏差。同步或异步、隔离程度、开销预算、丢失容忍度及记录失败是否阻止业务由项目确认；具体指导见[可观测性架构规范](observability-baseline.md)。

<a id="环境架构规范"></a>

### 环境边界与运行装配

- [ ] **AR-07.1**：沿实际启动、连接与存储路径核对环境拓扑、运行时、依赖服务、配置、网络、存储、数据及隔离边界。实际装配须符合所选环境的已确认设计，错连依赖、权限或数据落点越界构成偏差。

- [ ] **AR-07.2**：检查环境切换是否使用对应配置和数据边界；真实与模拟依赖、共享与独占资源及允许的网络访问应可辨识。核对环境差异对行为与验证条件的影响，模拟结果不得作为未覆盖的真实依赖证据。具体共享策略和隔离程度由项目确认，不强制物理隔离，不预选容器平台、部署拓扑、版本或服务端点。

<a id="测试工程与自动化规范"></a>

### 测试隔离与可控验证

#### 正式实现与测试实现隔离

- [ ] **AR-08.1**：正式入口、模块依赖、动态加载或运行配置发生变更时，沿实际运行路径检查正式依赖链及配置装配。正式运行直接或间接依赖、加载或启用实验实现、夹具、原型测试运行器等测试代码资产构成偏差。

测试可以调用正式模块。用例身份不授予业务权限，不产生正式路由、数据库字段或运行开关。按[工程资产边界](sdd-repository-governance.md#工程资产边界)归类的测试代码正式采用时，须迁入或提取到正式模块，移除模拟及实验装配，并补齐真实接口、权限与异常处理。必要测试和夹具保留在测试资产中。

#### 测试设计与执行

- [ ] **AR-08.2**：对测试工程及其依赖、数据或执行配置变更，按下表逐项核对项目已确认的测试目标是否落实，并检查实际断言、失败记录与复跑条件。缺少目标对应的断言、隔离或诊断证据不得报告符合。单元测试与集成测试是测试层次，回归是验证目的，可组合多个层次，框架与运行入口按项目设计分工，避免无依据的职责重复；测试范围决策、协作与验收结论仍归仓库治理。

| 技术对象 | 必须明确并落实的约束 |
|---|---|
| 测试边界与依赖 | 定义被测单元或组件、依赖替代边界、真实／模拟依赖的使用条件；集成与契约检查按声明的依赖条件执行交互 |
| 确定性与数据 | 控制影响结果的时间、随机性及外部状态；明确数据初始化、隔离与清理，执行失败后的清理结果可检查 |
| 结构与框架 | 用例、夹具、运行器按[工程资产分类](sdd-repository-governance.md#工程资产边界)组织；明确框架接入、配置和生命周期，复用已选框架能力 |
| 断言与验证依据 | 功能验证的断言对应需求或接口契约；探索验证对应已明确的假设、候选方案、比较目标及判断指标。检查可观察结果及适用的异常和边界，不能仅复述实现或以“未抛异常”代替目标判断 |
| 并行与恢复 | 明确共享资源、并行隔离、超时和重试条件；重试保留首次失败及各次结果，不以重试掩盖不确定性或重复副作用 |
| 执行与诊断 | 本地与 CI 使用一致的测试入口及配置约定，环境差异显式传入；运行器保留原始输出与诊断，关联场景／用例、算法或候选路径、运行版本、环境、结果及失败；正式报告归属见仓库治理 |

## 在目标仓库中落实

项目规则与矩阵的生成和更新按[决策边界](sdd-repository-governance.md#目标仓库的-code-review-rules)执行。重构初始化或明确的规则维护任务中，依据已确认设计、契约及实际路径，将适用 checklist 映射为项目 [Code Review Rules](../assets/code-review-rules_template.md)，已有规范直接引用，缺项与变化提交确认。重构技能按项目对象建立独立 [Review Matrix](../assets/review-matrix_template.md)，确认后在蓝图中维护固定链接。沿用现有编号、代码、配置、测试和审查机制，不要求逐项新增模块。安装和升级只分发知识与模板；已有矩阵的蓝图结构变化按治理同步。

每条项目规则须明确以下要素，执行证据归相应 Review 或测试报告：

| 要素 | 可执行要求 |
|---|---|
| 适用对象与条件 | 指定模块、接口、状态或运行路径及适用条件 |
| 已确认的决定 | 引用设计依据，明确允许、禁止和项目选定的策略；缺少依据或冲突的部分列为待决 |
| 检查方法 | 指定依赖扫描、语义审查、实际路径追踪、契约测试或故障实验等方法及取证入口 |
| 通过条件 | 给出可观察结果、适用预算或阈值及违规判据，不能以原则口号代替结果判断 |
| 检查时机 | 明确触发检查的直接变更或间接影响，以及适合的局部验证、CI 或专项审查时机 |

| 规范指导 | 落实对象与检查示例 |
|---|---|
| 模块边界与依赖 | 检查模块、接口、包依赖及构建入口，结合依赖扫描与语义审查识别越界调用 |
| 状态权威与持久化 | 追踪数据库、缓存和状态入口的读写；验证写入失败、重复写入及恢复后的状态 |
| 业务与运行保障分工 | 检查策略与执行入口；验证重试、重启和降级是否越权或产生重复副作用 |
| 接口与交互语义 | 对 API、消息、回调或状态机执行适用的契约及场景测试，覆盖并发、取消、超时及迟到结果 |
| 观测数据与日志契约 | 检查事件结构、采集接口和保存路径，验证字段、关联、敏感数据处理、完成及保留策略 |
| 观测影响与故障隔离 | 模拟导出失败、缓冲饱和或存储不可用，检查业务行为和资源开销是否符合项目策略 |
| 环境边界与运行装配 | 检查实际启动、连接、权限及数据落点，验证环境切换与依赖选择 |
| 测试隔离与可控验证 | 沿正式依赖链和配置检查测试替代行为，验证数据清理、并行隔离、失败保留及复跑条件 |

机械检查用于结构、依赖和证据辅助，不能替代职责语义、策略适用性或证据充分性的判断。Review 依据已确认项目规则检查；未确认的推荐策略不能作为违规判据，未执行或证据不足的检查不能报告通过。变更分级及检查流程见[仓库治理](sdd-repository-governance.md#架构变更与遵循检查)。
