# 仓库治理规范

适用于规则生效后新增或修改的产物。开工时用一句话说明目标、产物归属和完成条件。已有项目先查 `docs/index.md` 的实际映射；目录在产生产物时创建，每项约定只有一个权威正文。

## 规范层级与职责

本文件是 SDD 仓库研发活动的上位规范，负责人与 Agent 协同、决策授权、工程资产与文档权威。下位资源不得扩大授权、改变决策归属或另立竞争正文；冲突回到相应权威来源处理。

| 下位资源 | 职责 |
|---|---|
| [架构规范](architecture-rules.md) | 系统与代码的通用及专项技术约束 |
| [角色执行与交接](delegation.md) | 角色、模型与交接 |
| [文档写入规则](document-writing.md)与模板 | 归并与写后核对；模板规定结构和填写约束 |

按任务读取适用资源，不加载全部流程。

## 工程资产边界

按系统用途分类，不按文件形式或技术模块名称分类；本节唯一维护分类与默认落点，项目实际路径沿用索引。

| 工程资产 | 默认目录及用途 | 边界 |
|---|---|---|
| 正式实现 | `src/`；业务代码、通用技术模块、契约实现、正式提示词及配套运行配置 | 依据已确认需求或工程目标；具体环境值由环境配置管理 |
| 测试 | `tests/`；按需使用 `prototypes/`、`experiments/`、`cases/`、`fixtures/`、`datasets/` | 包括可行性验证、Demo、同场景算法对比、候选技术路径探索与迭代代码，以及测试专用配置 |
| 运维 | `ops/`；部署、排障、备份与恢复操作工具，按需使用 `deploy/`、`diagnostics/`、`recovery/` | 通过授权接口操作；检查注明环境、版本、副作用范围，与产品验收分别取证 |

例如，连接池初始化、限流、重试、自动重连及 JDBC 运行配置归正式实现；隔离测试数据库的连接配置归测试；数据库部署、诊断、备份及管理员恢复脚本归运维。

正式与测试资产的依赖、装配及运行隔离遵循[架构规范](architecture-rules.md#正式实现与测试实现隔离)。测试资产按[测试工程规范](architecture-rules.md#测试工程与自动化规范)维护；报告按[测试范围约束](#测试范围约束)归并，保留场景、算法／路径、版本与结果关联。功能完整、接入真实服务、验证通过或方案选中均不自动改变归属；正式方案确定后的正常产品开发属于正式实现。复用选定测试代码时，在当前任务关联已确认目标，说明行为、契约、需剔除的实验装配及验收条件，再按[迁入、提取与运行隔离要求](architecture-rules.md#正式实现与测试实现隔离)实施验证。

文档见下节。工具按用途归类，通用研发工具沿用已有工具目录并登记索引。生成产物记录来源及重建入口，修改生成源，不手工维护第二份正文；输出沿用既有构建位置，缺少路径时随产物确定，不预建空目录。

## 文档与产物落点

根 AGENTS 只导航，`docs/index.md` 维护实际映射；已有权威正文沿用映射，新产物使用以下默认位置。

| 产物 | 默认落点 |
|---|---|
| 能力需求 Spec、运行与验收指南 | `specs/<能力>/spec.md`、相邻 `quickstart.md` |
| 产品原型及静态资源 | `tests/prototypes/<能力>/<用例>/index.html`，旁设 `assets/` |
| 测试报告 | `docs/test-reports/<主题>/<批次>.md`；简单任务可在当前任务记录同一份报告 |
| Issue | `docs/issues/<问题编号>.md`；沿用已有项目的唯一记录与索引，使用 [Issue 模板](../assets/issue_template.md) |
| 架构 Review 记录 | `docs/test-reports/<主题>/<批次>-review.md`；按 [Review 模板](../assets/review_template.md)维护检查与整改复核，已有记录沿用 |
| 架构边界与不变量 | `docs/blueprint.md` |
| 场景时序、接口契约 | `docs/sequences/<场景>.md`、`docs/contracts/<接口或协议>.md` |
| 运维手册、其他项目文档 | `docs/runbooks/`；其他文档在 `docs/` 按用途命名 |
| 项目研发规则 | `.agents/governance/`，如 coding.md、test-data.md、environment.md，按需建立 |
| 共享治理、模板、Skills | 本文件；`.agents/sdd/assets/`；`.agents/skills/` |

产品与技术验证 HTML 均归测试资产；产品原型用于确认用户操作与预期体验，适用范围、版本确认和复用见[原型规则](prototype.md)。

## 人与 Agent 协同及决策权限

产品决定用例、运行环境、非功能指标及集成后的可视化验收；架构决定系统设计、模块边界与不变量；测试决策负责范围与数据集。项目协作约定指定决策人。

Agent 在已确认边界内执行契约、实现、修复、测试、部署及排障，沿用任务已有授权；只有实质决策变化才重新对齐。讨论、文档完成、验收或流程接续均不自动扩大写入、实施、测试、外部操作及 Git 授权；纯讨论不落盘。已授权实施按 sdd-imp 生成 Plan 后直接执行，不设置计划审批阶段。

需要确认时按[可视化沟通规范](visual-confirmation.md)呈现对应 Preview／Review。

## 职责与交接

需求与架构讨论允许自由探索，不设固定流程、模板填报或架构符合性门禁。用户要求写入 Blueprint 时，sdd-doc 按已确认内容和模板整理，不新增设计或 Blueprint Skill。

Agent 按任务意图和 Task Contract 自主选择、接续下表 Skill，默认 Main 执行，无需用户输入指令名。Skill 表示职责，不绑定固定 Agent；模型、委派及交接按[执行约定](delegation.md)。

架构 Review 要求前置文档一致、依据明确，复用 sdd-doc 的写入检查。文档冲突交 sdd-doc，设计未决或契约缺口回讨论，实现偏差交 sdd-imp；各流程返回结论与证据，正式文档由 sdd-doc 归并。

## 权威实体

| 实体 | 权威内容（均由 sdd-doc 写入） |
|---|---|
| Blueprint | 高位全产品用例、终端、关键体验与验收维度；架构、概念所有权、边界及已确认 ARC |
| Spec | 具体需求的唯一正文：目标、详细行为、业务规则、条件、异常与可执行 AC；细化并追溯适用 Blueprint 条款，不重复同层级正文 |
| 测试报告 | 本批次目标、计划、环境、准备数据、执行覆盖、逐项结果、证据、问题引用及结论限制；保留批次事实 |
| Issue | 独立问题事实、稳定编号、承接者、处理状态及历次处理／复验引用；修复方案引用 imp Plan／Task |
| Status | 进度、报告引用、阻塞与恢复点 |

初始化不创建需求或状态正文。代码是实现事实；模板、候选规则库和历史讨论不是已批准契约。

## Skill 场景与对象分工

角色配置与最小交接内容见[执行协作](delegation.md)。

| Skill | 场景与职责 | 判断依据 / 作用对象 | 结果 |
|---|---|---|---|
| sdd-init | 安装、升级能力，补齐缺失骨架 | 仓库 Skill、工具、模板、治理入口及必要配置 | 可用安装及冲突说明 |
| sdd-doc | 对话结论整理、落盘及写入一致性检查 | 确认来源及现行权威 → 授权文档 | 准确实体内容、引用及集中问题声明 |
| sdd-imp | 上游任务交付、局部自验与修复 | 明确上游任务（需求、Bug、Review issue 等）→ 授权代码/测试及验证证据 | 本轮上游任务完成情况与局部自验证据 |
| sdd-review-loop | 架构落地一致性、架构规则执行检查及整改后复核 | 架构 Rule + Blueprint/ARC → 实现及跨模块架构关系 | Review Gate 与快照证据 |
| sdd-test-loop | 需求行为验收、Issue 交接及整改后复验关闭 | Spec/AC → 实际行为及测试 | Test Gate、Issue 结论、实际版本与证据 |
| sdd-deploy | 按请求准备环境、部署及启动／重启服务 | 目标环境、版本及既有实例 | 运行入口、就绪检查与环境处理结果 |
| sdd-commit | 代理 Git 与 GitHub／GitLab 协作，执行指定交付终点 | 授权范围、分支、Issue、PR／MR 及合并 | 对象链接与已核验的交付回执 |

imp 交付明确的上游任务，不主动读取 Blueprint，不承担 ARC 对齐、架构规则检查或自行扩展重构；共享资源中的架构条款不构成 imp 的间接前置条件。Review 专门负责架构落地判断、整改目标与复核，Test 检查需求行为，二者不相互替代；整改接续、修复边界及复核按 [sdd-review-loop](../../skills/sdd-review-loop/SKILL.md)，问题修复与复验按 [sdd-test-loop](../../skills/sdd-test-loop/SKILL.md)。执行 Loop 不等于已获得独立审查证据，独立性按实际执行者判断。

## 文档写入检查

文档写入交由 sdd-doc；执行写入时读取[文档写入规则](document-writing.md)。其他流程只提供确认结论和真实证据。

## 按任务意图定位正文

从 `docs/index.md` 定位权威章节；未有产物时链接适用模板并标明编写入口。设计依据与指定版本证据分开导航。

引用在使用处维护：需求关联适用原型；蓝图关联驱动决定的需求及必要时序；时序关联需求、蓝图条款与接口；契约关联所属模块或不变量；测试报告关联目标、依据与复现入口；Quickstart 关联 Spec 场景／AC、适用原型与契约；Status／Plan 沿用场景编号引用报告，不复制逐项结果。

正文原位更新；入口新增、移动或替代才更新索引及直接受影响引用，无需反向登记。

## 测试范围约束

范围与数据选择在讨论中确认。sdd-doc 按 [Quickstart 模板](../assets/quickstart_template.md)整理操作与预期，按[测试报告模板](../assets/test_report_template.md)归并执行者的批次证据；字段、完整性和批次保存要求由模板维护，模板不改变执行权限、范围或完成条件。问题生命周期按 [Issue 模板](../assets/issue_template.md)独立维护，报告只引用问题及本轮影响；架构一致性使用 Review 专用报告。已有记录沿用，简单任务不重复建文件。

变更后结合 Git 差异及相关需求、实现、接口、数据、环境判断复验影响。需用户决定时展示变化、受影响场景和建议；影响无法确定时交用户判断。授权已含修复、复验则直接执行。仅补验收事实或无关变化不触发复验；版本不同不自动使历史结果过期、重跑或重新登记。既有 AC、Status、Gate 保留事实与快照；旧 Spec/Status 治理命令已退役，项目工作通过现行 Skills 执行。

Agent 准备环境、证据与操作指引，用户查看、操作、判断或反馈，机器结果与人工确认分别记录。可视化验收在约定环境操作集成版本，对照适用原型与非功能指标，按确认范围检查结构、业务状态、交互、权限、错误路径及指标；不设纯样式或像素还原门禁，浏览器与截图仅是手段。

## 实施和独立审查

实施按 [sdd-imp](../../skills/sdd-imp/SKILL.md)先生成 Plan／Task 清单再执行，简单授权任务可由 Main 直接完成；Goal 仅在用户或更高优先级指令明确要求时创建。Main 按[执行协作](delegation.md)协调闭环、核对关键差异，出现缺口、矛盾、失败或相关变化才深入检查局部。

| 执行者 | 范围与边界 |
|---|---|
| coder | 编写修复实现、测试及自动化脚本；局部自验限于必要定向单测、构建和类型检查，注明覆盖及待验收范围 |
| validator | 集成环境、跨组件交互、UI 操作验证及复验（含浏览器、computer-use）；检查断言证明能力和覆盖缺口，不修改代码 |

自动化是手段，coder 可自动执行定向单测，断言对应上游目标、需求或接口契约。imp 不执行完整业务流程、整体效果验证或全量业务回归；跨 Spec 分析及专项门禁不扩大其范围，这些验证由授权的 Test Loop 或专项验收承担。

COMPLETED 表示本轮实现完成：上游任务目标实现覆盖、局部自验、对应版本证据齐备且无阻塞，已知失败已处理。Review/Test Gate 不作为默认前置，也不在实施后固定追加。

按任务目标、风险与授权选择 Loop；Review 按架构约束记录并核验跨模块关系，Test 对多 Spec 分别记录并核验相关跨能力行为。实现修复后返回对应流程复核，要求独立审查时由原独立审查者复核；Gate 判据分别见 [Review](../../skills/sdd-review-loop/SKILL.md) 与 [Test](../../skills/sdd-test-loop/SKILL.md)。

## 交付

环境部署与服务运行按 [sdd-deploy](../../skills/sdd-deploy/SKILL.md)执行，默认 Main 承担；代码修改完成不自动触发。环境准备与运行检查按该入口接续，业务验收仍由 Test Loop 承担。

Git 与 GitHub／GitLab 仓库协作按 [sdd-commit](../../skills/sdd-commit/SKILL.md)执行，默认 Main 承担。用户指定交付终点后，Agent 在已有授权内自主完成所需分支、提交、推送、Issue、PR／MR 或合并步骤，不要求用户逐项操作或确认；只做终点必需的动作，目标歧义或范围实质变化时聚焦缺口确认。平台操作不改变 Spec 与报告权威；未指定终点仍只完成本地提交，PR／MR 创建不隐含合并，保护规则及审批按目标仓库执行。

## 架构变更与遵循检查

遵循判定区分“架构语义 → 当前实现映射 → 所需证据”。目录、包名及类名用于定位，不能替代职责、状态所有权、权限和调用链检查；迁移更新映射，不隐式改变规则。跨模块请求、受理、执行、交付、应用及呈现分别取证，不相互代替。

Review 中的架构变更按语义影响分级，项目在其遵循规范维护适用判据：L0 为实现变化且外部契约与架构语义不变；L1 为已确认边界内的契约扩展，须同步生产者、消费者及异常语义；L2 为职责、状态权威、决策权限、信任边界、依赖方向或关键不变量的改变，须按项目门禁确认。提示词或目录改动同样按影响判断；纯正文迁移且语义不变不升级为架构决策。

Blueprint 表达已确认的项目设计；ADR（项目采用时）记录具体取舍。架构规范作为 Review 的输入，与已确认 Blueprint 一起用于检查实现；不作为需求／架构讨论、Blueprint 写入或 imp 实施的前置约束。

## 观测基线落实与审查

- Review 逐项检查[观测基线](observability-baseline.md) SDD-OBS-01/02/03 及日志实现要求；必查业务故障隔离、媒体各写入与重试入口拒收、合法音频资产归属与隔离，分别提供证据。
- 审查记录采用“基线 ID → 项目 ARC／条款 → 检查对象 → 证据／快照 → 结论”；基线 ID 不替代项目编号，映射不要求写入 Blueprint。
- 证据不足为 UNVERIFIED，契约冲突为 BLOCKED，证实违反为 FAIL；未整改或有检查缺口不得给 Review Gate PASS。偏差按[实施和独立审查](#实施和独立审查)闭环并更新同一最新快照。
- 升级保留现行正文，漏项与冲突记为审查差异；设计变化回讨论，获写入授权后由 sdd-doc 归并，不由初始化器或写入流程补定设计。
