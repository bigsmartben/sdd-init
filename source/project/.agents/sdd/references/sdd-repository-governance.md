# 仓库治理规范

这是跨任务契约的维护入口，统一规定决策与授权、阶段推进、委派、产物权威、证据和交付边界。各 Skill 维护自己的步骤、专项确认点和完成判据；角色定义维护专业职责，模板规定产物结构。执行者按任务读取适用条款，同一版本已读内容直接沿用。

## 人与 Agent 协同及决策权限

项目协作约定指定人的决策权限。业务需求、用例、产品运行条件、非功能指标及集成验收目标由产品决策人确定；系统设计、模块边界及不变量由架构决策人确定；验收范围和改变验收含义的数据选择由项目约定的测试决策人确定。Agent 可在已确认目标、项目约束和授权内决定常规实施、验证与取证细节。依据已确认行为可推导的异常、边界和验收覆盖由 Agent 补齐。新增或改变用户可观察的异常结果、业务状态、权限、数据结果或质量承诺时，由相应决策人确认；该边界同样适用于主流程保持的场景。

技能 Agent 按本阶段规则确定确认对象和时点，向 Main 提供待决内容、依据及影响。Main 面向用户按[意图对齐](visual-confirmation.md#意图对齐)呈现，保留确认并把结论交回原技能 Agent。仍适用的已有确认直接沿用。

### 需求与架构讨论

纯讨论可围绕待决问题自由展开，无需固定流程、填报正式模板或通过架构规范符合性检查。讨论交付候选结论、依据和待决事项，按需参考[场景提示](scenarios.md)。正式写入按[文档写入规则](document-writing.md)归并已确认内容，架构遵循检查由 Review 承接。

### 目标仓库的 Code Review Rules

项目规则依据已确认设计形成，供架构 Review 使用。重构初始化中，由 sdd-refactor 核对蓝图中的规范或引用，整理缺失、过时的规则及项目 Review 矩阵候选，向用户展示内容、差异和影响，确认后归并。单独生成或更新规则仍可由用户明确要求，获授权的执行者按[文档写入规则](document-writing.md#code-review-rules)维护并登记路径。

Review 矩阵是独立的长期项目资产，由 sdd-refactor 生成和更新，在蓝图架构章节保留固定链接。按子系统、模块、组件及协作边界映射适用规则与取证判据；具体结构见 [Review Matrix](../assets/review-matrix_template.md)。矩阵承载覆盖依据，批次 Review Task、执行者、结果与整改事实归 Architecture Review Record，实施方案和局部自验归 Plan／Task。

已初始化矩阵的项目中，子系统、模块、组件、职责、依赖、契约或适用规范变化时，写入者将变化和受影响矩阵范围交 Main，由 Main 按本维护约定组织 sdd-refactor 同步，并向用户展示、确认更新。技能之间不直接调用；同步任务止于已确认资产维护，不自动开始审查或代码整改。没有变化沿用确认。首次写入蓝图不强制初始化；安装与升级只分发知识和模板，不生成或覆盖项目规则与矩阵。

本轮 Review Task 从有效矩阵按目标及影响范围派生，执行初审前确认任务范围、版本、排除项与终点，已有明确确认直接引用。初审后需整改的原检查项形成重构工单，按授权实施和复核。sdd-refactor 没有蓝图时直接结束，该前置不扩展为独立开发工单的门禁。

## 职责与交接

主任务（Main）是面向用户的阶段调度与交付负责人。Main 明确本轮目标、终点和授权，选择并启动技能 Agent，接收阶段回执并核对整体交付，协调跨阶段接续、必要的用户决定及技能未覆盖事项。常规路径为主任务 → 技能 Agent → 专业角色。Goal 仅在用户或更高优先级指令明确要求时创建。

技能 Agent 是在独立执行上下文运行所选 Skill 的 Agent。它核对阶段输入的来源、版本、环境和权限，负责工作组织、专业角色调度、依赖管理、专项确认、失败修正与复验，向 Main 交付阶段结果。专业角色按工单完成本职工作，向任务调用者返回[任务回执](task-receipt.md)。Main 启动阶段前读取[技能 Agent 的启动与接续](delegation.md#技能-agent-的启动与接续)。

### 选择工作流

按授权终点选择入口。需要完整阶段交付时，使用对应 Skill，即使预计改动少或耗时短。多个入口可能适用时按交付结果区分，例如恢复已确认行为、保持行为的技术重构、全产品集成验收。只交付明确的局部操作或一份专业产物时，分别按下文判定。部分覆盖时明确边界，余下独立事项由 Main 处理。

项目资料、工单、版本和证据可来自任何合格来源，按实际内容、版本、环境和授权判断是否就绪。技能 Agent 独立完成本阶段，禁止调用其他 Skill、要求其他 Skill 先执行或自行跨阶段交接。属于其他阶段的事项随证据、影响、建议和接续条件交 Main。协调与输入传递按[技能 Agent 的启动与接续](delegation.md#技能-agent-的启动与接续)进行。

### 直接执行局部操作

仅当用户明确要求一项局部操作，操作对象和预期结果已确定，且完成该操作本身就是授权终点时，Main 可以直接执行并做相称检查。已进入阶段的局部操作由技能 Agent 在本阶段处理。

| 用户请求 | 执行入口 |
|---|---|
| 把这个配置项从 30 改成 60 | Main 修改并核对该配置项。 |
| 服务经常超时，调整配置解决 | 按诊断及恢复目标选用适用 Skill。 |
| 删除这个目录中七天前的日志 | Main 核对目录及时间条件后执行局部操作。 |
| 磁盘满了，清日志并恢复服务 | 使用 sdd-deliver 组织运行排障与恢复。 |
| 这个 Bug 很小，修一下 | 使用 sdd-bugfix。 |

直接执行中发现需要归因、方案取舍或扩大范围时，Main 按实际目标选择并启动适用的技能 Agent，交接已知事实及已执行操作。新范围按授权边界处理。

### 直接委派专业角色

授权终点是一项专业产物，且工单的目标、依据、范围、版本、授权与完成条件就绪时，Main 可直接委派合格角色，即使已有适用 Skill。Main 负责派单、接收回执、核对适用的确认与验证、记录仍待验的判据。角色在同样的专业边界内执行。需完整阶段交付时按[选择工作流](#选择工作流)安排；已授权的复验、独立验收或后续阶段仍按本轮约定接续。

### 阶段授权与推进

通常一个主任务交付一个技能阶段。集成测试与 Bugfix 往返、重构相关的多技能交付以及其他明确授权的组合由 Main 协调。开工前在当前工单集中核对目标、范围及排除项、适用约束、验收判据、授权终点和已知待决事项；已有明确依据可直接引用。授权内可通过技术调查与实验消除未知。执行中新事实触及已确认的用户结果、关键约束或授权时，回报证据及受影响的决定。

- **明确授权多个阶段时按指定顺序推进，未授权阶段必须由人显式发起。** 例如“先重构，再集成测试”已经授权两个阶段。Main 按序核对每个阶段的前置和完成条件，保留该阶段适用的确认节点；前置满足即可启动已授权的后续阶段，无须再请求阶段启动许可。
- 仅当前阶段完成、下一阶段就绪或发现跨阶段事项，不授予下一阶段权限。Main 返回可选目标及就绪条件，等待用户发起未授权阶段。“继续”按当前唯一明确的待办解释；多个可能阶段导致歧义时，先确认要推进的目标。
- 缺少必要输入、能力、证据或授权，或有待决事项时，只暂停受影响项及其依赖。记录具体缺口、影响、承接者和恢复条件，继续其他已授权且就绪的事项。补齐后从受影响处接续，复用仍适用的证据。

### 运行状态与接续

长程或需跨轮接续的任务沿用当前工单、Plan／Task 或 Status 中的既有进度载体。Main 在阶段开始、决定或版本实质变化、新增关键阻塞、暂停及交接时更新目标、有效决定与授权、实际版本、进展、证据引用、剩余项及恢复条件。技能 Agent 和角色通过原调用链提供影响状态的变化。接续先核对版本、决定及证据的适用性，继续原工单和仍可复用的证据。

常规进展留在该记录。Main 及时集中呈现需用户决定的事项，含影响、选项和接续条件，并告知关键阻塞、预期变化和最终结果。用户询问进度时据最近记录与仍在运行的状态说明已完成、当前工作、阻塞及下一步。

### 技能未覆盖的工作

没有适用 Skill 时，Main 可直接完成能够承接的事项，也可按[直接委派专业角色](#直接委派专业角色)交付合格工单。

| 场景 | Main 的处理 |
|---|---|
| 独立咨询、解释或只读调查 | 直接回答或按需要安排专业能力。 |
| 目标明确的单独文档维护 | 按[权威正文归属](#权威实体)安排写入，完成[写后检查](document-writing.md)。 |
| 有明确边界的技术实验 | 说明假设、比较目标、证据和结束条件，在授权内执行。 |
| 阶段执行中发现范围外事项 | 回报证据、影响和建议，待用户授权后处理。 |
| 跨领域且无成熟流程 | 提出最小可执行方案，明确产物、职责和人工决策点。 |
| 改变已确认需求或架构 | 回到对应的决策边界，由用户显式发起相关工作。 |

这些事项适用同样的授权、业务和架构决策、写入及验证约束。按工作本身的目标处理，阶段边界继续有效，无须为每个空白工作新增 Skill。

### 阶段回执

技能 Agent 按阶段终点核对覆盖、完成判据、实际版本、证据和交付物，向 Main 返回阶段回执。Main 核对整体目标并协调后续阶段。阶段回执回答四件事：

1. 本轮目标完成到哪里，包含失败、未完成或未适用的检查。
2. 实际产物、版本和证据入口。
3. 缺口、影响、恢复条件与需用户决定的事项。
4. 适用的下一阶段选项和就绪条件。

沿用当前任务或现有记录。后续阶段已授权时用该回执核对前置后按序推进，未授权时交付条件并等待用户发起。

## 验收计划与方案

单个需求、缺陷或 Review 检查项采用点对点验收。上游在派发实施工单前固化以下内容，在原工单记录或提供可访问引用。

- **验收计划**明确验哪些项、由谁执行、何时执行或满足什么条件后执行，覆盖本工单及直接受影响的行为。
- **验收方案**明确各项的前置条件、操作或检查步骤、观察点和通过判据。用户侧从实际操作或公开调用入口出发，Review 从开发者视角检查适用架构约束。

需求依据 Spec／AC 定义，缺陷归入原 Issue，整改归入原检查项。混合工单分别关联用户侧与架构判据、执行者及证据。直接复用已确认和可执行的内容，从已有依据推导常规步骤、数据与取证方式。根据已确认的主流程、主要体验及交付范围推导需求的具体通过判据。计划和方案应足以确定实施范围和局部自验，并能在条件具备后照方案取证。实际版本、运行入口和结果按取得的事实补记。缺项及涉及用户决定的变化按[实施交接](delegation.md#实施交接)处理。

点对点验收按工单范围取证，可按判据运行真实组件。集成测试从 Blueprint、Spec／AC 和适用契约推导全功能点覆盖清单，交付可复跑的用户验收文档。可复用工单中的操作或检查步骤。

需要用户实际操作或判断才能成立的判据，执行者在验收记录中列出判据、实际版本与入口、复现步骤、需反馈的观察和缺证影响，沿调用链交 Main。Main 获取反馈并交回原执行者，记录来源及适用版本。执行者按原判据归并实际反馈。必要反馈未到时保留关联项待验、恢复条件及受影响的验收结论，继续其他就绪项。

## 工程资产边界

按系统用途分类。项目已有落点从索引定位，新增资产采用以下默认目录。

| 资产 | 默认目录与范围 |
|---|---|
| 正式实现 | `src/`。业务代码、通用技术模块、契约实现、正式提示词及配套运行配置。具体环境值由环境配置管理。 |
| 测试 | `tests/`。包括可行性验证、Demo、算法对比、候选技术探索、产品原型及测试专用配置。按需使用 `prototypes/`、`experiments/`、`cases/`、`fixtures/`、`datasets/`。 |
| 运维 | `ops/`。部署、排障、备份、恢复工具，按需使用 `deploy/`、`diagnostics/`、`recovery/`。经授权接口操作，记录环境、版本及副作用范围，运行检查与业务验收分别取证。 |

功能完整、接入真实服务、验证通过或方案选中都不改变测试资产的归属。正式方案确定后的产品开发归正式实现。采用测试代码时，任务注明目标行为、契约、需移除的实验装配和验收条件，按[运行隔离与迁入要求](architecture-rules.md#正式实现与测试实现隔离)实施。设计或调整测试工程时读[测试工程规范](architecture-rules.md#测试工程与自动化规范)。探索报告关联场景、算法或路径、版本与结果。

生成物记录来源和重建入口，变更落在生成源。通用研发工具沿用项目目录并登记索引，目录随产物建立。

## 权威实体

| 实体 | 权威内容 |
|---|---|
| Blueprint | 高位产品用例、终端、关键体验及验收维度，已确认架构职责、边界、不变量和 ARC。采用 ADR 的项目用其记录具体取舍。 |
| Code Review Rules | 从已确认设计形成的项目可检查规则及 checklist 映射；沿用蓝图内已有规范或项目既有正文。 |
| Review Matrix | 子系统、模块、组件及协作边界与适用项目规则的长期映射、检查方法及判据，由 sdd-refactor 维护。批次证据与进度不在此维护。 |
| Technical Research and Selection Report | 调研问题、候选方案比较、证据引用、选型建议和确认记录。已确认的架构决定归 Blueprint 或项目已有 ADR，实际验证结果归对应 Test Report。 |
| Spec | 具体需求、业务规则、条件、异常和 AC。引用适用 Blueprint 条款与原型。 |
| Scenario Sequence / Interface Contract | 设计中的协作顺序、接口语义与异常约定。运行事实归对应 Test Report。 |
| Quickstart | 集成回归用户验收文档，组织覆盖、准备条件、操作与预期。批次实际结果归 Test Report。 |
| Test Report / Architecture Review Record | 分别维护实际验证的批次事实和架构检查项的历次证据。 |
| Delivery Record | 实际交付与运维操作、目标状态、运行检查、故障影响及恢复结果。适用的 Review 和集成证据引用原记录。 |
| Issue | 独立问题事实、Bug 工单及处理状态。修复方案引用 Plan／Task。 |
| Plan／Task、Status | 分别维护实施方案与任务、进度与恢复点。验证结果引用对应报告和版本。 |

代码记录实现事实。模板规定产物结构，确认后的决定归并到对应实体。引用在使用处维护，区分设计依据与指定版本的执行证据。

## 证据与复用

保留原始证据入口、实际版本、环境、覆盖范围和所证明的判据，可使用任何来源的合格证据。版本、环境、判据或关联实现变更时先判断影响，仅复用仍能证明当前对象和范围的部分，其余按本轮权限补验或记录缺口。原型模拟、局部自验、正式集成测试、架构复核和运行检查各自证明实际覆盖范围。沿用原记录，以引用关联事实、进度与决定。

## 流程场景与对象分工

Main 从项目导航定位流程入口。下表按输入与产物导航，各入口维护具体做法和确认点。具体落点见[工程资产边界](#工程资产边界)与[文档与产物落点](#文档与产物落点)。

| 输入与回执入口 | 产物载体 |
|---|---|
| 已安装的 `sdd-init` Skill | 共享资源版本、项目链接及托管引用、安装或恢复回执 |
| [文档交接](delegation.md#文档交接) | 项目权威正文和写后诊断 |
| [需求→实现](../../skills/sdd-develop/SKILL.md)，输入用户目标、约束和已有交付依据 | Spec／AC、原工单的验收计划与方案、Plan／Task、实际版本、点对点验收证据及集成准备条件 |
| [架构蓝图的设计与演化](../../skills/sdd-architecture/SKILL.md)，输入已确认产品依据、现有设计和可核验事实 | 经确认的 Blueprint，按需关联 ADR、契约、时序、可行性证据及待决项 |
| [实施交接](delegation.md#实施交接) | Plan／Task、实际改动、版本及代码单测等局部证据，关联上游工单及待验判据 |
| [缺陷修复](../../skills/sdd-bugfix/SKILL.md)，输入异常报告或原 Issue 及已确认行为依据 | 原 Issue、归因及历次复验证据、Plan／Task、修复版本、关闭依据或恢复条件 |
| [集成测试](../../skills/sdd-test-loop/SKILL.md)，输入用户明确请求、已确认范围及目标版本和环境 | 可复跑的用户验收文档、含 Test Gate 的 Test Report、关联 Issue 及恢复条件 |
| [架构对齐与重构](../../skills/sdd-refactor/SKILL.md)，以已有蓝图为前提，初始化／更新规范与矩阵，再确认本轮审查范围 | 长期矩阵由蓝图固定链接；Architecture Review Record 记录矩阵快照、Review Task、初审、重构工单、两类复核及 Review Gate，Plan／Task 记录实施和局部自验。按授权终点交付资产、审查、工单或整改结果及集成准备条件 |
| [交付与运行](../../skills/sdd-deliver/SKILL.md)，输入授权终点、目标版本、环境及适用依据 | 平台或运行回执，按需归并 Delivery Record，记录实际终点、版本、证据与恢复条件 |

## 测试范围约束

以任务给定的覆盖范围、适用判据、确认状态和完成条件为准。从 Spec／AC、指南和任务约定推导常规数据、边界取值及顺序，记录依据与覆盖。用户可感知的质量指标沿用已确认的测量条件、统计口径和阈值。范围或标准不明、数据涉及新业务含义、需新增外部授权或有不可逆影响时，只暂停受影响项及其依赖，在回执中说明缺项、影响和接续条件。

## 实施和独立审查

[实施与局部自验](implementation.md)按明确工单开展。验证和审查的执行者按本职判据取证，核对断言、覆盖并回报缺口。取证与判定不包含修改被测实现。有独立性要求时，记录适用依据与实际执行者。

### Issue 关单

产品缺陷按原 Issue 的判据关单。证据须证明原场景或有依据的等价场景在实际修复版本上恢复、必要回归通过、本次修复引入的问题已解决，并包含判据所需的人工反馈。证据齐备即按本轮状态写入授权关闭原 Issue，引用对应批次。Bugfix 和集成复验适用同一判据。集成测试可提供关单证据，获本轮状态写入授权时可更新原 Issue，整轮 Test Gate 独立判定。

证据缺失时保留待复验或阻塞，写明受影响判据及恢复条件。需要用户实际操作或判断的结果，按[验收计划与方案](#验收计划与方案)取证。待确认状态用于需用户决定的事项。

## 交付

交付工单明确目标仓库、环境、版本、操作范围、恢复授权及终点。执行者按[交付与运行规则](delivery.md)完成独立或已授权的组合操作，核对实际状态。运行健康和约定冒烟按交付目标取证。回执列明涉及产品代码修复、全产品集成测试、业务需求或整体架构演化的发现与接续条件。

## 架构变更与遵循检查

按语义影响判定，项目在遵循规范维护具体判据。先判断 L2，再判断 L1 或 L0。

| 级别 | 条件与动作 |
|---|---|
| L2 | 改变职责、状态权威、决策权限、信任边界、依赖方向或关键不变量，按项目门禁确认。 |
| L1 | 已确认边界内的契约扩展，同步生产者、消费者及异常语义。 |
| L0 | 外部契约与架构语义均未改变的调整。 |

提示词、目录及正文迁移按同一语义影响判断。架构设计任务交付已确认的设计与决策证据，实现遵循由架构审查执行者取证。设计归并影响已初始化矩阵时，按[矩阵维护契约](#目标仓库的-code-review-rules)同步；其余规则可能过时的情况提示用户决定维护时机。判据无法覆盖时，回执列明缺项及影响。
