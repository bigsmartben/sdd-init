# 缺陷修复与定向复验

Main 在用户明确要求处理指定缺陷时进入，包括直接报告、集成测试发现、架构重构或发布后的行为回归，以及接续未完成的原 Issue。可用任何合格来源的需求、契约、历史行为、工单、代码、版本、日志及验证证据；接续时从实际就绪步骤继续。其他阶段发现问题或登记 Issue 本身不启动 Bugfix。只诊断或准备工单时，交付取证结论或就绪工单，不安排修复。只复验从实际修复版本取证并按授权记录，即使失败也不实施修复。

恢复目标、范围和授权明确时，直接推进本轮工作。先查证项目依据，仅在可观察的预期仍有实质歧义，或需要改变恢复目标、扩大授权范围、改变已确认架构约束时，把已知待决项和影响合并交 Main，请用户决定。等待时继续其他已授权且不受影响的工作。进入其他阶段由 Main 按[阶段授权与推进](../../sdd/references/sdd-repository-governance.md#阶段授权与推进)处理。

## 从复现到关闭

1. **明确目标。** 核对原 [Issue](../../sdd/assets/issue_template.md)、关联 Plan／Task、已确认预期、版本、环境和既有证据。说明要恢复的行为、缺陷范围和本轮终点，沿用用户请求与原 Issue 中已明确的内容。相关缺陷可合批，每项保留自己的编号、判据和关闭依据。
2. **复现评估。** 对照适用需求、契约与有效历史行为，核对实际版本、环境、数据、触发条件、观察结果和影响。区分已证实缺陷、待取证、预期行为及环境故障。确认是预期行为或环境故障时，把分类证据和处理建议交回 Main，按阶段授权处理后续；未授权阶段由用户显式发起。
3. **验证归因。** 给出候选原因、能区分原因的观测预测和排除条件；运行定向检查或核对可直接证明因果的路径，记录实际观测、版本及适用条件。出现反证时沿原编号修订归因。缺证继续取证；客观阻塞时记缺项、影响及恢复条件，其他可执行缺陷继续。
4. **准备修复与复验。** 验证归因后，获授权准备工单时沿用原 Issue；需要交付工单或修复且无原 Issue 时，先在授权内登记。记录恢复目标、已验证原因与证据、直接影响、边界和须保持行为，按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)固化或引用可执行的计划与方案，覆盖原场景与必要定向回归。用户可感知的缺陷从原操作或公开调用入口取证，采用等价场景须说明等价依据；质量指标沿用已确认的测量条件、统计口径和阈值。实施执行者按[实施与局部自验](../../sdd/references/implementation.md)在同一 Plan／Task 自主确定技术方案、改动和局部检查，关联原 Issue 和归因证据。异常边界覆盖和测试方法由 Agent 决定。
5. **实施并局部自验。** 工单就绪且修复获授权时修正根因，按影响修改相关模块的产品代码、测试和配套配置，运行相称的局部检查并修正失败。记录实际修复版本（含相关未提交改动或制品标识）、改动、局部证据和仍待验证的判据。
6. **在修复版本复验。** 核对实际运行版本、环境和数据，验证原故障或可证明等价的场景、必要定向回归及副作用。依据判据选用单测、局部检查或真实组件实测，复用匹配版本、环境、覆盖及判据的有效证据。故障仍在或本次修复引入回归时，保留本批事实，按证据回到归因或实施并继续复验，受本轮授权终点约束。
7. **更新原 Issue 并交付。** 原故障恢复、必要回归通过且本次修复引入的问题已解决时，证据齐备即按授权关闭原 Issue。判据所需的证据只能从用户环境或实际操作取得时，请用户提供具体观察结果，并说明取证步骤和受影响的判据。证据未齐时保留待复验或阻塞及恢复条件，待确认用于需要用户决定的事项。交付实际版本、改动、关闭依据或缺口，以及后续集成所需入口和准备条件。

各执行者按[文档写入规则](../../sdd/references/document-writing.md)维护原 Issue、Plan／Task 及适用的 [Test Report](../../sdd/assets/test_report_template.md)。分批保留归因、局部自验和历次复验的版本、结果及证据。Issue 记录状态和处理历史，Plan 引用实际证据。

## 阶段内执行安排

本 Skill 按[最小交接](../../sdd/references/delegation.md#最小交接)显式选用具备能力的执行者，给出目标、授权、写入边界、必要输入和完成条件，核对回执后在本阶段接续。

| 时点与所需能力 | 给定依据 | 回收结果 |
| --- | --- | --- |
| 核对预期行为，通常由 `sdd-product-manager` 承接 | 原场景、已确认需求和契约、适用历史行为 | 权威依据、恢复目标、场景判据和歧义。角色回执交本 Skill；本 Skill 将需用户决定的行为交 Main |
| 复现、归因及获授权的实施，通常由 `sdd-coder` 承接 | 原 Issue、版本和入口、适用代码范围、证据与判据 | 复现与归因证据；同一 Plan／Task、改动、版本、局部结果和待验项 |
| 运行取证或准备复现环境，通常由 `sdd-devops` 承接 | 目标环境、版本、日志和配置入口、授权操作 | 实际版本、配置和依赖事实、运行证据、复现条件及阻塞 |
| 文档依据冲突时，按需选 `sdd-doc-consistency` | 具体疑点、权威依据和指定只读范围 | 差异位置、权威依据、影响及待核实项 |
| 修复版本就绪后复验，由本 Skill 执行或选择合格执行者 | 原 Issue 判据、修复版本、环境、已有证据 | 原场景结果、回归覆盖、实际版本、关闭依据或缺口 |

角色名仅作能力映射。简单工作或无可用角色时，技能执行者按同一契约承接。归因、修复及复验可复用执行者，有独立验证要求时按要求安排。角色直接使用项目资料、共享规则和模板，禁止加载工作流 Skill 或互相委派；跨职责事项先返回本 Skill，阶段内由本 Skill 调度，跨阶段再交 Main。

## 交付边界

修复可跨模块，范围限于指定的行为恢复。可准备已授权的复现环境。本 Skill 将独立缺陷随证据回报 Main，是否另行处理按实际授权。新增行为、需求变更、整体架构演化、发布、线上恢复和全产品集成回归由 Main 按[阶段授权与推进](../../sdd/references/sdd-repository-governance.md#阶段授权与推进)协调。
