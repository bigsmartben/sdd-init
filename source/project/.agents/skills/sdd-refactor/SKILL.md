# 架构对齐与技术重构

## 启动与边界

Main 在用户要求发布前架构对齐、落实已确认蓝图、处理指定技术债、接续整改、仅审查架构或维护项目 Review 矩阵时选择本入口。已初始化矩阵的蓝图结构变更按[矩阵维护契约](../../sdd/references/sdd-repository-governance.md#目标仓库的-code-review-rules)由 Main 组织同步。可使用任意合格来源的项目资料与证据。接续沿用原检查项、同一 Plan／Task 和适用证据。

启动或接续先从项目索引定位已有 Blueprint。缺失时仅说明缺项并结束，不写项目资产或派单。代码事实不能替代蓝图依据；独立开发工单按自身判据执行。

有蓝图时简述目标、范围、版本、已确认架构依据与授权终点，区分仅维护资产、仅审查、准备重构工单和包含实施。用户指令或已有确认已明确的内容直接沿用；新增或变化的实质决定按[意图对齐](../../sdd/references/visual-confirmation.md#意图对齐)经 Main 确认。仅审查允许维护经确认的规范、矩阵及蓝图链接，并写入审查记录，产品代码保持只读。

依据已确认架构调整内部结构、职责实现、重复代码、接口适配与测试。重构不得改变已确认的业务需求，须保持业务规则、操作结果、业务状态流转、公开契约、数据语义、异常结果及已确认质量指标。发现原有业务缺陷、依据不足或冲突、需要扩大范围、改变架构决定或无法保持业务行为时，附证据、影响和恢复条件交回 Main。只暂停受影响项及依赖，继续其余已授权且就绪的事项。用户同意讨论变化时，Main 负责协调决策及另行授权的阶段。

## 初始化与矩阵维护

1. **核对项目规范。** 沿蓝图正文及引用定位已确认的 ARC、契约、项目 Code Review Rules 和原验收证据。按[架构规范](../../sdd/references/architecture-rules.md)的三类范式、八项指导及 checklist 编号核对项目映射。已有合格规则原位复用；缺失或过时时，依据已确认设计与实际路径整理候选。项目已有规范可直接引用，缺少独立正文时使用 [Code Review Rules](../../sdd/assets/code-review-rules_template.md)及治理默认落点。未确认的架构取舍保留待决，不将现有实现或通用推荐视为项目决定。
2. **生成或核对长期矩阵。** 从蓝图枚举实际子系统、模块、组件及其协作边界，按 [Review Matrix](../../sdd/assets/review-matrix_template.md)维护独立资产。将对象与适用项目规则关联，记录设计与 checklist 来源、适用条件、检查方法及通过／违规判据；说明不适用和待决范围。矩阵不机械展开全部组合，不承载批次结果。已要求但未实现的对象也纳入适用性判断。
3. **确认并归并资产。** 首次生成或对象、职责、依赖、契约、规则变化时，向 Main 提交规范与矩阵的候选、增删改差异和影响，取得用户确认后保存，并在蓝图架构章节维护固定链接、同步项目索引。保留既有规则与矩阵编号，有效内容原位归并；撤销项的旧版本仍由历史审查快照追溯。未确认候选不替换当前有效资产。没有变化直接复用，不重复确认。仅维护资产的任务在此交付。

每次审查或接续核对蓝图、规则及矩阵版本是否匹配。变化只使受影响项及其依赖待更新，其余已授权且就绪项可继续；不得用旧矩阵对已变化范围判定通过。矩阵维护、用户确认和本轮任务选择各自的正文归属见[文档写入规则](../../sdd/references/document-writing.md)。

## 审查、整改与复核

1. **生成并确认本次 Review Task。** 根据本次目标、变更及跨模块影响，从有效矩阵按需选取检查项，使用 [Architecture Review Record](../../sdd/assets/review_template.md)生成稳定 `CHK`。记录矩阵与规则快照、矩阵项、对象、判据、检查步骤、执行者及排除项。一个任务可覆盖强关联规则，一条规则可对应多个对象任务。通过 Main 与用户确认本次任务范围、版本及仅审查／准备工单／包含整改的终点；已有明确确认直接引用，新增或变化范围重新确认。确认前只进行定位、资产核对和任务准备，不执行初审。
2. **逐项取证与初判。** 按确认任务先检查语义、源码、调用链、配置和实际装配，证据不足时在授权内补充定向运行。按适用范围核对职责、依赖、状态权威、接口、数据与异常恢复路径；涉及工程骨架时沿实际目录、模块、package、模板与生成结果取证。符合项直接 PASS，不适用说明原因；缺证记 UNVERIFIED、依据冲突记 BLOCKED，保留未执行项。指定技术债即便没有违规，也按获授权的技术目标取证并记录可检验判据。技能归并同一事实，横向核对跨模块覆盖。仅审查在此交付发现、证据和建议。
3. **建立整改前行为基线。** 对需整改的检查项，从 Spec／AC、契约和有效证据提取须保持的行为及通过判据，记录改前版本、环境、数据、公开入口及实际结果，覆盖相关状态、异常、恢复和适用质量指标。沿用已确认的测量条件、口径及阈值，缺证时在授权内补查。已确认预期与现有运行事实分别记录；原有业务缺陷交 Main，不当作须保持的预期。缺证项先补查，不凭疑点派发推测性修改。
4. **形成并派发重构工单。** 将有整改依据的原 `CHK` 作为工单引用，写明矩阵项、适用规则、受审版本、初审证据、整改目标、范围与位置、预期技术结果及须保持的业务行为。按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)分别给出架构复核与行为保持验收的判据、步骤及执行安排。Coder 的 `prepare` 模式只完成工单与 Plan 准备；包含实施时，将已就绪且获授权的工单按[实施交接](../../sdd/references/delegation.md#实施交接)以 `refactor` 模式交给 sdd-coder 或合格实施执行者，不另建重复工单台账。
5. **由实施执行者完成重构和局部自验。** 实施执行者按[实施与局部自验](../../sdd/references/implementation.md)选取最小 Plan 分档，完成工单约定的结构检查及局部行为保持测试。检查项与 Task 可多对多关联，回执保留原 CHK、实际改动、版本与工作树指纹、检查结果和后续复核入口。Coder 不判定 Review Gate。
6. **组织架构复核和业务行为保持验收。** 技能在实际整改版本按原工单组织验收。架构复核优先复用原审查者，检查原偏差、受影响规则、依赖、装配和跨模块关系。行为保持验收从原用户入口或公开调用按已确认判据核对业务结果、契约和适用质量指标，复用符合目标版本、环境及判据的证据并补验缺口。要求独立时安排独立执行者。行为保持判据需要用户操作或判断时，按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)通过 Main 取得反馈。验证代码由实施执行者补齐。逐项记录结果并保留初审和历次事实，通过后关闭，失败带原编号和新增证据返回对应 Task。
7. **交付重构结果及待集成条件。** 汇总改动、版本、检查项、Review Gate、业务行为保持验收证据、影响、待集成入口及准备条件。适用架构检查项在交付版本全部通过才报告 Review Gate PASS，仍有 FAIL 时继续授权内整改。重构完成还须技术整改完成、行为保持验收通过、本轮问题解决且证据可追溯。按[文档写入规则](../../sdd/references/document-writing.md)归并本轮证据。Status／Plan 引用同一专用审查记录。交 Main 的回执和审查记录按同一条件描述集成准备：候选版本、运行入口、环境和真实开测前置，列出受阻场景及恢复条件。Review Gate、行为保持结果及历史偏差分别说明，只有影响候选可用性、具体场景或项目已确认的开测条件时才阻塞对应集成。候选就绪且获授权时，Main 可接续可测范围。集成 Test Gate 由 test-loop 判定，正式发布另按[正式发布依据](../../sdd/references/release-evidence.md)核验。

## 执行协作

本 Skill 按[委派与独立性](../../sdd/references/delegation.md#委派与独立性)安排以下工作，核对回执并组织阶段内接续。

技能 Agent 负责矩阵覆盖、本轮任务拆分、证据适用性、发现归并和跨模块横向核对。按模块或共用路径派发可独立交付的专业工单，每单由同一负责人完成取证与初判。工单包含调用者与回执接收方、对象与版本、矩阵项和规则、必要依据、方法判据、写入边界及终点。专业执行者向调用者回报，由技能 Agent 分发新输入；不让同层执行者相互调度。复核优先沿用原审查者，独立性按项目要求核验。

| 执行时机和职责 | 可选角色 | 交接重点 |
| --- | --- | --- |
| 项目规范与矩阵的专业整理、初审、整改后复核 | sdd-architect | 输入蓝图、适用 checklist、矩阵项和实现版本。返回候选映射或原检查项、依据、实际路径、偏差、目标与复核结论；资产确认与归并由技能组织 |
| 按授权以 `prepare` 准备或以 `refactor` 实施与局部自验 | sdd-coder | 输入原检查项、整改边界、须保持行为、写入边界及验收计划与方案。返回对应模式产物、代码和测试改动、版本与工作树指纹、证据与待复核项 |
| 整改版本就绪后执行行为保持验收 | 技能 Agent 或合格验收执行者 | 输入原检查项、行为判据、公开入口、目标版本和可复用证据。返回逐项验收结果、实际版本与环境、证据及缺口 |
| 需核验配置、依赖、环境或运行装配时取证 | sdd-devops | 输入目标版本、运行环境和准备授权。返回实际装配、运行入口、证据及阻塞 |
| 行为基线需专业梳理时提取业务判据 | sdd-product-manager | 输入已有 Spec、契约及证据。返回须保持的行为、出处及歧义或缺口 |
| 发现正文或引用冲突时按需只读核对 | sdd-doc-consistency | 输入指定文档范围和疑点。返回差异、权威依据及影响，阶段内受影响项由本 Skill 接续 |

架构判断与复核由审查执行者负责，实施方案由开发执行者负责。架构 Review Gate 与全产品集成 Test Gate 分别取证。
