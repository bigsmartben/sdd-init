# 架构对齐与技术重构

## 启动与边界

Main 在用户明确要求多需求集成后的发布前架构对齐、落实已确认蓝图、处理指定技术债或结构问题、接续整改、仅审查架构时选择本入口。蓝图更新、集成通过或其他阶段的发现只提供依据。可使用任意合格来源的项目文档、代码、工单、版本及证据。接续时沿用原检查项、同一 Plan／Task 和适用证据，从实际就绪处继续。

开工时简述目标、范围、版本、已确认架构依据与授权终点。用户启动指令或已有确认已明确这些内容时，直接进入本轮工作；仅对未明确或已变化的实质决定按[意图对齐](../../sdd/references/visual-confirmation.md#意图对齐)请求确认。仅审查时，交付偏差、证据和建议，写入限于获授权的审查记录。

依据已确认架构调整内部结构、职责实现、重复代码、接口适配与测试。重构不得改变已确认的业务需求，须保持业务规则、操作结果、业务状态流转、公开契约、数据语义、异常结果及已确认质量指标。发现原有业务缺陷、依据不足或冲突、需要扩大范围、改变架构决定或无法保持业务行为时，附证据、影响和恢复条件交回 Main。只暂停受影响项及依赖，继续其余已授权且就绪的事项。用户同意讨论变化时，Main 负责协调决策及另行授权的阶段。

## 审查、整改与复核

1. **确定审查范围与规则。** 从项目索引定位已确认的 Blueprint／ARC、契约、项目 Code Review Rules 和原验收证据。核对实现快照及受影响的调用方，按本轮改动和跨模块影响从[共享架构规范](../../sdd/references/architecture-rules.md)筛选适用的通用和专项条款。结合已确认的设计与实际路径，核对各条款在项目 Code Review Rules 中的映射及其适用条件。映射缺失或过时时，在审查记录中将受影响项标为待查，列明条款、受影响路径及恢复条件，并提醒用户决定是否及何时生成或更新项目规则。其余有效规则继续审查。已要求但未实现的能力在范围内按实际缺口取证。
2. **建立行为基线。** 在整改前从 Spec／AC、契约和有效测试证据提取直接受影响的行为及通过判据。记录修改前版本、环境、数据、用户入口或公开调用、预期和可观察结果，覆盖相关状态、异常、恢复及适用质量指标，沿用已确认的测量条件、统计口径和阈值。缺少证据时在授权内补充定向检查。分别记录已确认判据与现有运行事实，保留差异并将原有业务缺陷交 Main，避免将缺陷作为须保持的预期。仅审查时按审查判据和授权取证。
3. **逐项审查。** 使用 [Architecture Review Record](../../sdd/assets/review_template.md)，以稳定检查项跟踪初审、整改及复核，关联适用的项目规则编号和设计依据。沿每条规则的取证路径核对源码、调用链、配置和实际装配，按违规判据逐项判定。按适用范围检查模块职责、依赖方向、状态所有权、接口边界、数据流、异常与恢复路径。全蓝图审查或影响工程骨架及其设计约束时，按[工程骨架规范](../../sdd/references/architecture-rules.md#工程骨架规范)核对实际目录、模块、package、生成模板与装配，并说明适用性。记录依据、对象、覆盖、快照、偏差与影响。符合项直接 PASS，不适用项说明理由，未检查项保留待查。证据不足记 UNVERIFIED，依据冲突记 BLOCKED。指定技术债即便未违反架构规则，也以获授权的技术目标建立检查项，记录结构问题和可检验的通过判据。仅审查的请求在本步汇总并交付。
4. **按原检查项派发重构工单。** 在原检查项写明适用规则、初审证据、整改目标、范围与位置、预期技术结果及须保持的业务行为。按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)分别给出架构复核与行为保持验收的判据和取证步骤。技能将已就绪且获授权的原检查项作为工单，按[实施交接](../../sdd/references/delegation.md#实施交接)交给 sdd-coder 或具备相应能力的实施执行者。就绪项可先行。
5. **由实施执行者完成重构和局部自验。** 实施执行者接单后按[实施与局部自验](../../sdd/references/implementation.md)制定并维护同一份 Plan／Task，完成工单约定的结构检查及局部行为保持测试。检查项与 Task 可多对多关联，回执保留原检查项和适用证据的引用。
6. **组织架构复核和业务行为保持验收。** 技能在实际整改版本按原工单组织验收。架构复核优先复用原审查者，检查原偏差、受影响规则、依赖、装配和跨模块关系。行为保持验收从原用户入口或公开调用按已确认判据核对业务结果、契约和适用质量指标，复用符合目标版本、环境及判据的证据并补验缺口。要求独立时安排独立执行者。行为保持判据需要用户操作或判断时，按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)通过 Main 取得反馈。验证代码由实施执行者补齐。逐项记录结果并保留初审和历次事实，通过后关闭，失败带原编号和新增证据返回对应 Task。
7. **交付重构结果及待集成条件。** 汇总改动、版本、检查项、Review Gate、业务行为保持验收证据、影响、待集成入口及准备条件。适用架构检查项在交付版本全部通过才报告 Review Gate PASS，仍有 FAIL 时继续授权内整改。重构完成还须技术整改完成、行为保持验收通过、本轮问题解决且证据可追溯。按[文档写入规则](../../sdd/references/document-writing.md)归并本轮证据。Status／Plan 引用同一专用审查记录。交 Main 的回执和审查记录按同一条件描述集成准备：候选版本、运行入口、环境和真实开测前置，列出受阻场景及恢复条件。Review Gate、行为保持结果及历史偏差分别说明，只有影响候选可用性、具体场景或项目已确认的开测条件时才阻塞对应集成。候选就绪且获授权时，Main 可接续可测范围。集成 Test Gate 由 test-loop 判定，正式发布另按[正式发布依据](../../sdd/references/release-evidence.md)核验。

## 执行协作

本 Skill 按[委派与独立性](../../sdd/references/delegation.md#委派与独立性)安排以下工作，核对回执并组织阶段内接续。

| 执行时机和职责 | 可选角色 | 交接重点 |
| --- | --- | --- |
| 初审、界定整改目标、整改后复核 | sdd-architect | 输入已确认约束和实现版本。返回原检查项、依据、实际路径、偏差、目标与复核结论 |
| 接单后制定 Plan／Task、实施与局部自验 | sdd-coder | 输入原检查项、整改边界、须保持行为及验收计划与方案。返回 Plan／Task、代码和测试改动、版本、证据与待验项 |
| 整改版本就绪后执行行为保持验收 | 技能 Agent 或合格验收执行者 | 输入原检查项、行为判据、公开入口、目标版本和可复用证据。返回逐项验收结果、实际版本与环境、证据及缺口 |
| 需核验配置、依赖、环境或运行装配时取证 | sdd-devops | 输入目标版本、运行环境和准备授权。返回实际装配、运行入口、证据及阻塞 |
| 行为基线需专业梳理时提取业务判据 | sdd-product-manager | 输入已有 Spec、契约及证据。返回须保持的行为、出处及歧义或缺口 |
| 发现正文或引用冲突时按需只读核对 | sdd-doc-consistency | 输入指定文档范围和疑点。返回差异、权威依据及影响，阶段内受影响项由本 Skill 接续 |

架构判断与复核由审查执行者负责，实施方案由开发执行者负责。架构 Review Gate 与全产品集成 Test Gate 分别取证。
