# 架构落地一致性 Review

审查目标是架构落地，包括适用 Code Review Rules 的执行；不审阅 Spec 内容，不检查业务需求覆盖或进行业务行为验收。业务模块仍按职责、状态所有权、依赖和接口等架构约束检查。

前置：复用 sdd-doc 对本轮蓝图和关联文档已有且仍有效的一致性检查。缺少一致性依据或发现冲突时，交 sdd-doc 按[文档写入规则](../../sdd/references/document-writing.md#按对象读取与语义核对)核对受影响的正文，受影响结论保持待查。需要用户确认新设计决定时，按[意图对齐](../../sdd/references/visual-confirmation.md#意图对齐)交回讨论。

1. 确定模块、快照与跨模块影响范围，从项目索引定位 Code Review Rules，按规则适用条件确定本轮检查项，覆盖受影响的调用方、依赖、读写和恢复路径。核对受影响的 Blueprint／ARC、契约、运行配置及实际路径，发现规则缺失或过时时，说明依据与影响，提醒用户决定生成或更新时机，将受影响范围记为 UNVERIFIED／待查并注明恢复条件，其余有效规则继续检查。已要求但尚未实现的能力仍纳入范围。按需查阅[架构规范](../../sdd/references/architecture-rules.md)的对应章节，记录不适用依据，未检查项保留待检查。证据不足记 UNVERIFIED 并补查，契约冲突记 BLOCKED。

   全蓝图 Review，以及变更影响工程骨架或其对应设计约束的 Review，均须按[工程骨架规范](../../sdd/references/architecture-rules.md#工程骨架规范)记录适用性和依据。对照已确认的 Blueprint 核对实际工程目录、模块和 package 的职责、接口、依赖及装配路径，覆盖手工搭建和工具生成的结构。存在受影响的生成模板时一并检查。本轮范围未涉及相关结构及其对应设计约束时，记录不适用及依据。

2. **逐项检查并接续**：对全部适用 Code Review Rules 建立检查项，关联规则稳定标识及设计依据。对当前检查项，对照源码、调用链、配置和运行装配检查职责、状态所有权、依赖、接口、数据流及异常时序，记录依据、位置、覆盖、快照及初审事实。符合直接 PASS；不适用说明理由，不计通过。按架构语义、实际实现路径和证据记录映射。迁移时更新实现映射，沿用原规则。跨模块关系按相关阶段分别取证，包括请求、受理、执行、交付、应用与呈现。可执行约束运行相应检查，目录和名称用于定位。
3. 当前项有可修复的实现偏差时，无需等待全范围初审或总 Gate：本流程判断是否需要重构、对齐哪些 ARC，明确检查项编号、偏差、整改目标、实现位置、预期结果和业务行为保持边界，默认自动接续 sdd-imp；用户明确只审不修时遵守。缺失验证代码也交 imp，修复方案由 imp 在其 Plan 中维护，架构依据与映射留在 Review，不要求 imp 读取 Code Review Rules、自行读取 Blueprint 或判定架构。复杂整改可拆多个 Task；存在依赖或共享修复时可合批，一个 Task 可关联多个检查项，但各项分别复核。逻辑逐项闭环不要求每项新建 Agent 或重复加载，批次与原执行者复用按[执行协作](../../sdd/references/delegation.md)。
4. imp 完成后由原审查者复核原偏差、修复波及的 Code Review Rules 及受影响跨模块关系，并核对业务逻辑保持的验证证据；需要集成验证时按本次整改范围执行，不扩展为业务需求验收。复核通过才关闭该项并继续其他检查项；失败则带检查项及增量证据返回对应 Task，继续整改和复核。证据缺口由审查执行者补查；文档冲突交 sdd-doc，设计待决交回讨论。修复保持业务逻辑和已确认架构不变；涉及外部契约或架构语义变化时，读取[架构变更与遵循检查](../../sdd/references/sdd-repository-governance.md#架构变更与遵循检查)判定影响。涉及业务规则、可观察业务行为、外部契约或架构决定变化，或无法确定影响时，仅暂停受影响项及其依赖项，其余可执行项继续，记录具体阻塞及恢复条件；不放宽 Code Review Rule 或修改蓝图迁就实现。外部操作仍沿用实际授权。
5. 调用 sdd-doc 按 [Review 模板](../../sdd/assets/review_template.md)维护同一记录：在每个检查项下保留初审、Task 引用、处理与复核证据及当前状态，不另建独立差异清单或问题生命周期；修复结果只引用 Plan／Task，不复制方案。随批次记录，不将全部初审落盘作为启动已授权修复的前提。未受影响证据经影响分析后复用，Gate 汇总全部适用检查项及规则缺失／过时导致的待查范围，全部在所声明同一快照通过才可报告 PASS；FAIL 是结果，不停止授权内修复。

审查执行者不修改代码、设计或正式文档；Main 按上述步骤接续 sdd-doc 与 sdd-imp，不要求固定角色轮转。架构 Review 记录作为专用报告，Status／Plan 引用该记录及实际 Gate，不重复归并另一份测试报告。需求行为验收由 sdd-test-loop 承担。向用户展示架构审查证据时，将证据对应到审查对象。独立审查按[执行协作](../../sdd/references/delegation.md)安排，自查不得称为独立审查。

例：项目 Code Review Rule 引用蓝图规定只有服务层写订单状态，发现界面层直接写库。引用规则标识、蓝图条款和实际调用链报告偏差，交给 sdd-imp。若项目尚无规则，先提醒用户生成并将受影响范围保留待查。
