# 架构落地一致性 Review

审查目标是架构落地，包括适用架构规则的执行；不审阅 Spec 内容，不检查业务需求覆盖或进行业务行为验收。业务模块仍按职责、状态所有权、依赖和接口等架构约束检查。

前置：sdd-doc 已保证本轮蓝图及关联文档一致，审查依据明确。发现文档冲突时暂停受影响结论，交回 sdd-doc；需要新设计取舍时交回讨论。

1. 确定目标模块、实现快照及相关跨模块关系。从[架构规范](../../sdd/references/architecture-rules.md)、Blueprint、适用 ARC 和[观测基线](../../sdd/references/observability-baseline.md)确定检查范围。
2. 对照源码、调用链、配置和运行装配检查职责、状态所有权、依赖、接口、数据流及异常时序，核对适用的通用与专项架构规则是否落实。可执行约束使用相应检查，语义判断提供具体实现证据；不能只检查目录或已列出的 ARC 而遗漏适用约束。
3. 输出逐项符合、偏差或未验证结论，注明依据、位置、覆盖范围和快照。范围内的跨模块架构关系须实际检查。
4. 调用 sdd-doc 按 [Review 模板](../../sdd/assets/review_template.md)将范围、检查项、初审结果、gap 与当前状态落盘，保留检查编号和实现快照。修复方案由 sdd-imp 自行推理并在其 Plan 中维护，Review 记录只关联 Task。
5. 默认自动接续 sdd-imp 修复范围内的实现偏差及缺失验证代码，再返回本流程复核；用户明确只审不修时遵守。交接 gap、架构依据、实现位置和修复边界，不代替 imp 制定方案。修复必须保持业务逻辑和已确认架构不变；涉及业务规则、可观察业务行为、外部契约或架构决定变化，或无法确定影响时，暂停该项并交回讨论，不放宽 Rule 或修改蓝图迁就实现。外部操作仍沿用实际授权。
6. 证据缺口由审查执行者补查；文档冲突交 sdd-doc，设计待决交回讨论。imp 完成后复核受影响架构项及跨模块关系，并核对其业务逻辑保持的验证证据；需要集成验证时按本次整改范围执行，不扩展为业务需求验收。复核失败则带增量证据返回 imp；无法继续时记录阻塞和恢复条件。要求独立审查时回原独立审查者。
7. 调用 sdd-doc 更新同一记录的修复结果、状态、复核证据及 Gate，保留初审与历史批次。已修改待复核不等于关闭；复核通过才关闭对应 gap。未受影响证据经影响分析后复用，全部适用项在所声明同一快照通过才可报告 Review Gate PASS。

审查执行者不修改代码、设计或正式文档；Main 按上述步骤接续 sdd-doc 与 sdd-imp，不要求固定角色轮转。架构 Review 记录作为专用报告，Status／Plan 引用该记录及实际 Gate，不重复归并另一份测试报告。需求行为验收由 sdd-test-loop 承担。需要用户判断时按[项目职责](../../sdd/references/sdd-repository-governance.md)沿场景时序展示证据。独立审查按[执行协作](../../sdd/references/delegation.md)安排，自查不得称为独立审查。

例：蓝图规定只有服务层写订单状态，发现界面层直接写库。引用蓝图条款和实际调用链报告偏差，交给 sdd-imp；不修改蓝图使实现合规。
