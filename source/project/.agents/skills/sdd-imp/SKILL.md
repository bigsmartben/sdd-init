# 实施与局部自验

HTML 原型属于测试代码，制作或复用原型时读取[原型规则](../../sdd/references/prototype.md)。coder 负责代码，交互与业务状态验证交给 validator；引用、确认记录与测试报告交给 sdd-doc。

1. 从已确认需求、缺陷复现步骤或已授权的探索验证目标确定本次实施目标，定位相关代码、测试以及直接约束本改动的接口和架构条款。沿用现有决定；需要改变职责、状态所有权或外部契约时，说明冲突并交回设计判断。
2. 读取 [Plan 模板](../../sdd/assets/plan_template.md)，先输出本轮 Plan，已授权实施直接按依赖执行，不设置计划审批阶段。按可判断完成的目标拆分 Task，结合实际代码定位改动范围、关联需求与约束，明确依赖、完成条件及相称的局部自验；检查任务共同覆盖本轮范围。输出结构和唯一载体按模板维护；简单修复可只有一个 Task，不机械套用固定阶段。
3. 按 Task 依赖在授权范围内实现或修复，开始时更新状态。仅在前置条件满足、改动与共享状态不会冲突时并行；不同文件本身不足以证明可并行。编写或修复必要的测试代码和自动化脚本；按[断言与验证依据](../../sdd/references/architecture-rules.md#测试工程与自动化规范)设置功能断言或探索比较指标，以相称的定向单元测试检查结果，按受影响范围补充构建或类型检查。开发局部自验限于上述检查；需要集成环境、跨组件交互或 UI 操作证明的行为，交给 sdd-validator 执行并返回证据，按任务范围协调后续验证，不纳入 coder 自验。失败则修复并复验，已有证据仍有效时直接复用。
4. 实施中发现遗漏、依赖或方案变化，先更新同一份 Plan 的受影响任务再继续，保留已有任务编号与有效证据；实质范围或设计变化交回讨论。任务实现及对应局部自验完成后标记完成并记录证据。
5. 核对 Task 对本轮目标的覆盖、完成情况与证据，交付关键改动、验证结果、未覆盖范围和阻塞。需要正式记录时，将当前快照与验证证据交给 sdd-doc 归并测试报告，Plan／Status 引用报告并维护进度。实现与局部验证完成即可结束本轮实施。

来自 sdd-test-loop 的修复，以独立 Issue 记录入口、发现报告、Issue 编号、场景依据、复现证据及修复边界为输入，在已有授权内执行。自行推理修复方案并维护在 Plan，关联原 Issue；完成后返回 Issue／Task、实际改动、修复版本、局部自验证据、待复验范围及阻塞，交 sdd-doc 在独立 Issue 中记录已修改待复验，由 test 复验关闭，不能凭局部自验关闭 Issue。需求或设计缺口交回讨论。

来自 sdd-review-loop 的整改，以 Review 记录中的 gap、架构依据及边界为输入，自行推理修复方案并维护在本流程 Plan，关联 gap 编号。保持业务逻辑与已确认架构不变，使用相称的定向测试、构建或类型检查验证改动及行为保持；不能确定影响或需要改变业务逻辑、外部契约、架构决定时暂停该项并返回讨论。完成后返回实际改动、版本及局部自验证据，由 Review 复核，不能自行关闭 gap。


需要写入文档时，由 `sdd-doc` 一并完成内容与格式一致性检查。架构符合性审查归 `sdd-review-loop`，完整需求行为验收归 `sdd-test-loop`；按各自任务范围执行。

实施按改动对象读取[架构通用与专项约束](../../sdd/references/architecture-rules.md)的适用条款，覆盖环境、脚手架和测试工程等直接约束；观测专项要求由其中的基线链接定位。确定验证范围时读取[共享规则](../../sdd/references/sdd-repository-governance.md#实施和独立审查)，需要角色及证据交接时读取[执行协作](../../sdd/references/delegation.md)。

例：修复空输入处理，补充并运行空输入的定向测试；报告局部覆盖，不自动启动完整业务验收或架构 Review。
