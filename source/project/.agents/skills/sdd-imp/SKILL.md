# SDD 实施

“按这个方案开始实现”“修复这个问题”等明确自然语言要求即可进入，无需重复输入 Skill 名。读取[协作约定](../../sdd/references/governance.md)，定位关联 Issue、适用 Blueprint、Draft PR 中的 Plan 和当前实现。沿用已有清楚结论与授权，不强求每项工作补齐全部实体或重新走完整链路。

变更前简短对齐目标、输入输出、范围和完成依据；信息充分时一句话即可。普通文档、工具维护按实际对象取证，不虚构产品页面或架构。沿用用户的模型与推理强度，[协作说明](../../sdd/references/delegation.md)不要求额外委派。

- 核对工作区、分支和他人改动，在授权范围实现、修复或重构，保留无关工作。
- 对照需求与适用架构实现，遇到需要改变需求、职责、接口或架构决定的冲突，暂停受影响部分回到讨论，继续其他已明确工作，不以实现现状反写需求。
- 按变化做必要局部自验：相关测试、构建、类型检查或接口检查按实际风险选择；失败在实施范围内修复并复验。有效检查通过且无新疑点后不重复扩大测试。
- 必要时在现有 PR 或任务记录说明进度、版本、证据和剩余项，不运行旧 Spec/Status 状态工具作为开工或完成门禁，不新增状态系统、独立 plan.md 或重复需求正文。
- 实施完成不自动进入部署验收或 Git 交付；明确要求的后续工作按其范围执行，不要求用户重复口令。

报告改动、实际验证命令及结果、未覆盖范围和待决事项。局部自验不代表用户人工验收，未完成或失败如实保留。用户要求验收时由 sdd-accept 准备指定版本与环境；反馈和重构要求开启下一轮讨论。
