# 上游任务交付与局部自验

目标是交付上游明确交给本流程的任务，包括需求、Bug、Review 检查项及已授权探索任务。仅依据明确任务和必要代码上下文实施；不主动读取 Blueprint，不承担 ARC 对齐、Code Review Rules 检查或自行扩展架构重构。架构落地的判断、整改目标与复核归 sdd-review-loop。

HTML 原型属于测试代码，制作或复用原型时读取[原型规则](../../sdd/references/prototype.md)。coder 负责代码，交互与业务状态验证交给 validator；引用、确认记录与测试报告交给 sdd-doc。

1. 从明确的上游输入确定交付目标、范围与完成条件，定位相关代码、测试和必要接口上下文。制定验证范围时读取[实施和独立审查](../../sdd/references/sdd-repository-governance.md#实施和独立审查)。新增资产或改变用途时查[工程资产边界](../../sdd/references/sdd-repository-governance.md#工程资产边界)。输入不足时向上游补齐缺项；不自行补定目标或扩展任务。
2. 读取 [Plan 模板](../../sdd/assets/plan_template.md)，根据已确认的目标和预期结果输出本轮 Plan，按依赖直接执行。按可判断完成的目标拆分 Task，结合实际代码定位改动范围、关联上游任务与完成条件，明确依赖、完成条件及相称的局部自验；检查任务共同覆盖本轮范围。输出结构和唯一载体按模板维护；简单修复可只有一个 Task，不机械套用固定阶段。
3. 按 Task 依赖在授权范围内实现或修复，开始时更新状态。修复故障时，先依据证据分析原因，再通过验证确认因果关系，最后针对原因修复并复验；不能仅凭现象消失或成功率提高认定根因已解决。仅在前置条件满足、改动与共享状态不会冲突时并行；不同文件本身不足以证明可并行。编写或修复必要的测试代码和自动化脚本；按上游目标、需求或接口契约设置断言；探索任务按明确假设、比较目标和指标验证，以相称的定向单元测试检查结果，按受影响范围补充构建或类型检查。按共享分工将所需的集成、跨组件或 UI 验证交给 sdd-validator。失败则修复并复验，已有证据仍有效时直接复用。
4. 实施中发现遗漏、依赖或方案变化，依据已确认的目标和预期结果自主调整方案及改动位置，更新同一份 Plan 中的受影响任务并继续，保留已有任务编号与有效证据。要解决的问题或预期结果发生变化时，交回 Main 与用户对齐后再更新对应任务。目标实现覆盖、局部自验完成、对应版本证据齐备、已知失败已处理且无阻塞时，标记 COMPLETED。
5. 核对 Task 对本轮目标的覆盖、完成情况与证据，交付关键改动、验证结果、未覆盖范围和阻塞。需要正式记录时，将当前快照与验证证据交给 sdd-doc 归并测试报告，Plan／Status 引用报告并维护进度。实现与局部验证完成即可结束本轮实施；整个任务是否完成由 Main 核对其余已授权目标和完成条件。

来自 sdd-test-loop 的修复，以独立 Issue 记录入口、发现报告、Issue 编号、场景依据、复现证据及修复边界为输入，在已有授权内执行。自行推理修复方案并维护在 Plan，关联原 Issue；完成后返回 Issue／Task、实际改动、修复版本、局部自验证据、待复验范围及阻塞，交 sdd-doc 在独立 Issue 中记录已修改待复验，由 test 复验关闭，不能凭局部自验关闭 Issue。需求或设计缺口交回讨论。

来自 sdd-review-loop 的整改须明确检查项编号、整改目标、实现位置、预期结果及业务行为保持边界。Task 关联原检查项；目标或行为影响不清、需超出交接范围时，暂停该项并返回 Review。完成后返回实际改动、版本及局部自验证据，由 Review 复核关闭。


需要写入文档时，由 `sdd-doc` 一并完成内容与格式一致性检查。架构符合性审查归 `sdd-review-loop`，完整需求行为验收归 `sdd-test-loop`；按各自任务范围执行。

需要委派或交接时读取[执行协作](../../sdd/references/delegation.md)。

例：修复空输入处理，补充并运行空输入的定向测试；报告局部覆盖，不自动启动完整业务验收或架构 Review。
