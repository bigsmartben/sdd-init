# 需求→实现

Main 根据用户明确发起的本轮目标选择本入口。从项目索引定位能力 Spec／AC、适用契约、确认记录、原型、工单、Plan 和已有证据。接续已有规格或实现时从实际就绪步骤继续。只讨论按[需求与架构讨论](../../sdd/references/sdd-repository-governance.md#需求与架构讨论)交付候选结论和待决项。只写规格时在规格归并和核对后结束。暂缓实施时按用户限定的终点交付，记录接续条件。

## 从需求到验收

本阶段固定两个[人工确认](../../sdd/references/visual-confirmation.md#意图对齐)节点。技能 Agent 将交付范围、主流程和主要体验交 Main 呈现给用户，按反馈续做并记录确认来源及适用范围。已有有效确认直接沿用。按[决策权限](../../sdd/references/sdd-repository-governance.md#人与-agent-协同及决策权限)推导常规异常、边界和验收覆盖；需要新增或改变用户可观察的业务结果时，将差异、影响及选项交 Main 按相应节点确认。技术方案、接口实现、代码结构及 Task 拆分由实施执行者在已确认边界内决定。

1. **形成需求候选。** 明确用户目标、本轮范围、主流程、主要体验、须保持的行为与可观察结果。按需调研，涉及需要实际操作的体验时按[原型规则](../../sdd/references/prototype.md)制作并验证中保真 HTML。基于已确认依据推导可确定的异常流程、边界输入、失败反馈和恢复行为，待决变化保持候选。
2. **A 需求落盘前确认。** 新需求和需求变更均在正式写入前确认主流程、主要体验、交付范围及本轮新增或变化的可观察业务结果。随后按[文档写入规则](../../sdd/references/document-writing.md)和 [Spec](../../sdd/assets/spec_template.md)原位归并，保留稳定编号和适用的固定版本原型引用。已有条款足够时直接引用。尚未确认的内容保持候选。
3. **固化验收并准备实施。** B 确认前，本 Skill 在原需求工单或当前任务记录中固化或引用适用的 Spec／AC、[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)、须保持的行为、适用契约及直接适用的已确认约束。按[实施交接](../../sdd/references/delegation.md#实施交接)，可在已有授权内安排 `sdd-coder` 调查代码或准备 Plan。B 前的准备限于获授权的调查、文档及隔离验证。
4. **B 交付实施前确认。** 以用户能理解的方式说明交付目标、范围、主流程、主要体验和就绪状态，取得本轮交付实施的明确确认。已有的交付实施确认覆盖本轮时直接沿用。必要外部授权交 Main 处理。
5. **派发工单并接收实施回执。** B 确认覆盖本轮、工单就绪且实施已获授权后，本 Skill 按[实施交接](../../sdd/references/delegation.md#实施交接)将原工单交给 `sdd-coder` 或具备同等能力的实施执行者。实施执行者按[实施与局部自验](../../sdd/references/implementation.md)制定或接续维护同一份 Plan／Task，推进就绪 Task，完成已授权的产品代码、测试及必要配置改动并局部自验。回执引用原工单及 Plan／Task，向本 Skill 回传实际改动、版本、局部证据和待验项。
6. **逐 AC 验收并核对交付。** 本 Skill 收到实施回执后，按原工单组织点对点验收。从用户操作或公开调用入口，按方案验证本轮各 AC 和直接受影响的行为。判据需要时运行真实组件。复用适用于本轮版本、环境、范围及判据的局部证据，补验缺项。记录逐项实际结果、版本和证据，明确实测入口、实际环境及组件。原型模拟和正式实现各自取证。需要用户操作或判断的 AC 按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)通过 Main 取得反馈。可按[测试记录](../../sdd/assets/test_report_template.md)归并到现有载体。本轮实现导致验收失败时，附证据退回原 Task，由实施执行者修正，本 Skill 组织复验。依据实测判定结果。核对已确认需求归并、约定实现、实际改动、验收结果及必要回归，交付版本、证据、集成入口和准备条件。待确认、缺证或失败的事项与其依赖保留实际状态和恢复条件，其他已就绪且获授权的工作继续。

## 执行安排

本 Skill 按[委派与独立性](../../sdd/references/delegation.md#委派与独立性)安排以下工作，核对回执后在本阶段接续。

| 时点与所需能力 | 给定依据 | 回收结果 |
| --- | --- | --- |
| 澄清、规格化、原型与验收规格，通常由 `sdd-product-manager` 承接 | 用户目标、确认范围、项目现状及适用 Spec／契约 | 候选需求、AC、原型和确认状态，随后交付确认后的规格、验收计划及可执行方案 |
| B 前按授权调查代码或准备 Plan，B 后按就绪工单实施与局部自验，通常由 `sdd-coder` 承接 | 原需求工单、适用 Spec／AC、验收计划与方案、须保持的行为、代码范围及直接适用的已确认约束 | 准备时返回调查证据或 Plan，实施后返回同一份 Plan／Task、实际改动、版本、局部证据与待验项 |
| 局部验收所需的环境准备或排障，通常由 `sdd-devops` 承接 | 环境、候选版本、运行入口、就绪判据及授权操作 | 环境、实际运行版本、入口、就绪状态与故障证据 |
| 跨文档疑点或需要独立一致性核对时，按需选 `sdd-doc-consistency` | 指定疑点、权威依据、只读范围 | 冲突或引用问题的证据、影响及建议 |
| 收到实施回执后的逐 AC 验收，由本 Skill 执行或安排具备能力的执行者 | 原工单的 AC 和验收方案、实施回执、版本、环境和可复用证据 | 逐 AC 实测结果、证据、版本及缺口 |

按[文档交接](../../sdd/references/delegation.md#文档交接)安排文档核对。架构符合性及整改复核由架构 Review 承接。

## 交付边界

工单缺项按[实施交接](../../sdd/references/delegation.md#实施交接)补齐。在已确认约束内，为交付目标必需的局部结构调整可归本轮工单。历史独立缺陷、范围外改进、需决策的架构冲突或外部授权缺口，随证据、影响和恢复条件交 Main。若当前需求的一部分确实依赖独立重构，记录具体依赖、影响、已检查的替代路径及取舍。Main 向用户呈现可行选择，包括另行授权前置重构、改用已确认约束内的可行路径或延后关联交付。决定前只暂停依赖项及其后续，其他已授权且就绪的工作继续。点对点验收以本需求及直接受影响行为为范围。全产品集成回归、独立 Bugfix、架构 Review 与技术重构及发布由 Main 按[阶段授权与推进](../../sdd/references/sdd-repository-governance.md#阶段授权与推进)处理。
