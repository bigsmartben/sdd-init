# 需求→实现

Main 根据用户明确发起的本轮目标选择本入口。从项目索引定位能力 Spec／AC、适用契约、确认记录、原型、工单、Plan 和已有证据。接受任何合格来源，接续已有规格或实现时从实际就绪步骤继续。只讨论时返回候选结论和待决项。只写规格时在规格归并和核对后结束。暂缓实施时按用户限定的终点交付，记录接续条件。

## 从需求到验收

本阶段固定两个[人工确认](../../sdd/references/visual-confirmation.md#意图对齐)节点。技能 Agent 将交付范围、主流程和主要体验交 Main 呈现给用户，按反馈续做并记录确认来源及适用范围。已有有效确认直接沿用。主流程、主要体验或交付范围变化时，以用户能观察的行为与结果在相应节点重新对齐。异常流程、边缘场景、验收覆盖与方法、技术方案、接口实现、代码结构及 Task 拆分由 Agent 决定。

1. **形成需求候选。** 明确用户目标、本轮范围、主流程、主要体验、须保持的行为与可观察结果。按需调研，涉及需要实际操作的体验时按[原型规则](../../sdd/references/prototype.md)制作并验证中保真 HTML。基于目标、项目约定和已有行为推导异常流程、边界输入、失败反馈和恢复行为。
2. **A 需求落盘前确认。** 新需求和需求变更均在正式写入前确认主流程、主要体验及交付范围。随后按[文档写入规则](../../sdd/references/document-writing.md)和 [Spec](../../sdd/assets/spec_template.md)原位归并，保留稳定编号和适用的固定版本原型引用。已有条款足够时直接引用。尚未确认的内容保持候选。
3. **固化验收并准备实施。** 按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)，沿用原需求工单或当前任务记录，固化或引用适用的 Spec／AC、验收项、执行者和触发条件。验收方案从用户操作或公开调用入口写明前置条件、步骤、观察点、通过判据及须保持的行为。用户可感知指标沿用已确认的测量条件、统计口径和阈值。本 Skill 识别适用的已确认架构约束，给工单附直接适用的条款。实施执行者调查代码，按[实施与局部自验](../../sdd/references/implementation.md)在同一 Plan 维护方案、Task、直接依赖、待查前提及局部验证入口，查证后再依赖。B 前的准备按授权限于调查、文档及隔离验证。
4. **B 交付实施前确认。** 进入交付实施前，说明用户能理解的交付目标、范围、主流程、主要体验和就绪状态。取得进入实施的明确确认后，开始已授权的产品代码、测试和配置改动。已有的交付实施确认覆盖本轮时直接沿用。技术方案和实施细节由 Agent 自主管理。必要外部授权交 Main 处理。
5. **实施并局部自验。** 按同一 Plan 推进就绪 Task，编写产品代码、测试及必要配套配置，记录实际版本、改动、局部证据及待验项。核对受影响的行为；本轮实现造成的失败进入同一 Plan 修正并定向复验。
6. **逐 AC 验收并核对交付。** 从用户操作或公开调用入口，按方案验证本轮各 AC 和直接受影响的行为。判据需要时运行真实组件。复用覆盖当前版本、环境、范围及判据的证据，补齐缺项。记录逐项实际结果、版本和证据，明确实测入口、实际环境及组件。原型模拟和正式实现各自取证。可按[测试记录](../../sdd/assets/test_report_template.md)归并到现有载体。本轮实现导致验收失败时回到实施修正并复验。依据实测判定结果。核对已确认需求归并、约定实现、实际改动、局部验收及必要回归，交付版本、证据、集成入口和准备条件。待确认、缺证或失败的事项与其依赖保留实际状态和恢复条件，其他已就绪且获授权的工作继续。

## 执行安排

本 Skill 在各时点按专业能力显式安排执行者。参考[执行协作](../../sdd/references/delegation.md#委派与独立性)的当前角色映射，按[最小交接](../../sdd/references/delegation.md#最小交接)提供目标、授权、读写边界、必要来源与完成条件，核对回执后在本阶段接续。

| 时点与所需能力 | 给定依据 | 回收结果 |
| --- | --- | --- |
| 澄清、规格化、原型与验收规格，通常由 `sdd-product-manager` 承接 | 用户目标、确认范围、项目现状及适用 Spec／契约 | 候选需求、AC、原型和确认状态，随后交付确认后的规格、验收计划及可执行方案 |
| 调查代码和拟定 Plan，以及 B 后的实施与局部自验，通常由 `sdd-coder` 承接 | 原工单、判据、验收计划与方案、代码范围及直接适用条款 | 调查证据或 Plan／Task、实际改动、版本、局部证据与待验项 |
| 局部验收所需的环境准备或排障，通常由 `sdd-devops` 承接 | 环境、候选版本、运行入口、就绪判据及授权操作 | 环境、实际运行版本、入口、就绪状态与故障证据 |
| 跨文档疑点或需要独立一致性核对时，按需选 `sdd-doc-consistency` | 指定疑点、权威依据、只读范围 | 冲突或引用问题的证据、影响及建议 |
| 需求验收，由本 Skill 执行或安排具备能力的执行者 | 本轮 AC、原工单方案、版本、环境和可复用证据 | 逐 AC 实测结果、证据、版本及缺口 |

角色名用于查找可用能力。简单工作或无可用角色时，技能执行者按同一契约承接。本 Skill 按[文档交接](../../sdd/references/delegation.md#文档交接)落实只读核对要求，验收按项目要求保持执行独立性。角色直接使用项目资料、共享规则和模板，禁止加载工作流 Skill 或互相委派。实施执行者读取 Blueprint／ARC 时限于工单直接引用且适用的条款。架构符合性及整改复核归架构 Review。

## 交付边界

将历史独立缺陷、范围外改进、架构冲突或缺项、跨阶段事项及必要外部授权交回 Main，附证据、影响、缺项和恢复条件。点对点验收以本需求及直接受影响行为为范围。各阶段独立受理，禁止调用其他 Skill、把其执行当作前置条件或自动推进。完整交付以本轮约定和实测证据为准；全产品集成回归、独立 Bugfix、发布前架构 Review 和技术重构及发布由 Main 按[阶段授权与推进](../../sdd/references/sdd-repository-governance.md#阶段授权与推进)处理。
