# 需求验收

1. 从项目索引定位 Spec、AC、适用的已确认原型和该能力实际 Quickstart（索引缺失时查[仓库治理](../../sdd/references/sdd-repository-governance.md#文档与产物落点)定位），核对验收环境、实际运行时的 Git commit 及必要的未提交修改说明、数据和判断点。开始验收前读取[测试范围约束](../../sdd/references/sdd-repository-governance.md#测试范围约束)。实际指南缺失或不可执行时，将依据和准备内容交 sdd-doc 整理，新增或修改测试代码交 sdd-imp。使用可执行指南进行验收。
2. 运行能证明目标行为的测试，核对前提、触发及可观察结果。重试、恢复等多步骤行为须实际执行并核对关键过程及结果。多个 Spec 同时验收时分别记录结果，并检查相关组合行为、异常恢复和跨模块交互。
3. 沿用指南的场景 / AC 编号和判断点，输出通过、失败、未测或阻塞及预期差异、证据、环境、数据和实际版本。向 sdd-doc 交接[测试报告模板](../../sdd/assets/test_report_template.md)所需的安排与执行证据，问题发现事实按[Issue 模板](../../sdd/assets/issue_template.md)交接；跨场景、跨批次复用同一问题及编号，无问题不建 Issue，未测或阻塞不自动判为缺陷。Agent 提供证据与操作指引供用户查看、操作、判断或反馈。
4. 按 Issue 交接独立问题记录入口、发现报告、编号、场景／AC 与已有依据、复现步骤、预期实际差异、影响、版本证据及修复边界。实现缺陷及缺失测试交 [sdd-imp](../sdd-imp/SKILL.md)，按其修复交接要求接续。证据缺口由验收执行者补查，需求缺口或变更交回讨论，文档矛盾交 sdd-doc。修复、复验沿用实际授权；无法继续时记录承接者、阻塞及恢复条件，不因登记 Issue 自动开始修复。
5. 有改动时结合 Git 差异核对需求、实现、接口、数据和环境对复验范围的影响。影响无法确定时交回判断，事实补录、无关变更或版本差异本身不触发复验，旧批次及 Gate 保留原快照。授权涵盖修复和复验时，Main 自动接续 imp，并由原验收者接收改动、修复版本、局部自验证据及待复验范围，复验受影响场景和相关组合行为；角色复用及例外按[执行协作](../../sdd/references/delegation.md)。修复完成仅记已修改待复验，本流程复验通过才关闭对应缺陷；失败继续沿用原编号；非代码问题依据处理结果核验闭环。将处理与复验事实交 sdd-doc 更新同一 Issue，按报告模板保留新旧批次并关联原用例，Status／Plan 引用相应记录。
6. 报告 Test Gate 时说明验证版本、范围及未验证项；全部目标 AC 和相关组合行为在所声明版本均有通过证据才可报告 PASS。不同版本的证据分别注明归属；不可执行或证据不足的目标项记为阻塞或未验证。所需人工确认与机器结果分别记录，待反馈的保持待确认。

本流程负责验收与复验，不修改实现、测试代码、需求或正式文档。验收证据和人工确认由 sdd-doc 归并测试报告，Status／Plan 引用报告，不回填指南；架构一致性由 sdd-review-code 检查。需要声明独立性时按[执行协作](../../sdd/references/delegation.md)判断。

例：AC 要求取消后不再提交订单，实际取消后仍发出请求。报告 B1 记录操作、实际请求及失败证据，关联独立 ISS-001；授权修复后交 imp 并关联其 Task。修复返回后 Issue 标待复验，实际重走取消场景通过后记录报告 B2，由 doc 据此更新 ISS-001 为已复验关闭，B1 的失败保持原状。
