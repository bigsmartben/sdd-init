# 面向用户功能的集成测试

按用户明确发起的集成测试验证验收产品范围内全部适用功能点。多个需求已集成时检查功能完整性、跨模块协同及相互影响；缺陷修复后兼顾原故障、必要回归与整轮覆盖；架构重构后验证须保持的业务行为及适用的发布前集成要求；接续批次时核对实际版本、环境与已有证据。需求、修复或重构完成本身不触发测试。单工单点对点验收沿用原工单[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)。

从项目索引、既有规格、工单或其他可核对来源定位已确认的产品用例、Spec／AC、适用契约和原型、目标版本、运行指南及已有证据。

## 人工确认与待验

- **首次实测前是唯一的常规确认点。** 集中核对验收产品范围、目标版本、测试环境和主要用户路径。沿用启动指令及已有确认中明确的内容，只把未明确的部分集中交 Main 按[意图对齐](../../sdd/references/visual-confirmation.md#意图对齐)确认。四项均明确时，完成常规准备即可实测。
- **执行中只对齐受影响事项。** 验收范围变化、拟改测其他版本或环境、业务判据需补齐、调整或消除冲突，或需要补充操作授权时，将具体影响交 Main 对齐。暂停受影响项及其依赖，继续其他已授权且就绪的场景。判据明确而实测不符时，按原判据记录失败和证据。
- **按需获取人工验收反馈。** 准备复跑指南时标出需要用户实际操作或判断的场景，按[验收计划与方案](../../sdd/references/sdd-repository-governance.md#验收计划与方案)通过 Main 获取反馈。在 Test Report 中单列人工待验、实际反馈及其对 Test Gate 的影响。

## 本轮闭环

1. **确定测试对象。** 核对验收产品范围、目标版本、测试环境、主要用户路径、已确认判据、本轮目标及前次批次，明确批次边界。
2. **建立覆盖。** 将范围内全部适用功能点映射到稳定场景／AC 和已确认判据，按用户目标补齐正常、异常、边界、组合、恢复和跨模块协同场景。复用适用指南和工单方案。常规测试数据、异常与边界覆盖、执行顺序和取证方法由执行者按[测试范围约束](../../sdd/references/sdd-repository-governance.md#测试范围约束)推导。
3. **准备指南与环境。** 用 [Quickstart](../../sdd/assets/quickstart_template.md) 给出可复跑的版本、环境、真实入口、前置数据、操作步骤、关键观察点、通过判据及必要复位。只在本轮已授权环境内准备数据、依赖、入口与测试工具，核实实际运行的版本（含相关未提交改动或制品标识）、组件及就绪状态。无法证明实际版本或真实装配时，标出受影响项及恢复条件。
4. **执行与逐项留证。** 核对[实测前确认](#人工确认与待验)已覆盖本轮验收边界。从用户操作或公开调用入口检查真实组件协同及可观察业务结果。内部调用和数据可辅助取证；纯内部职责、依赖及 Code Review Rules 的遵循交 Main，单独的架构偏差不充当本轮业务判据。适用质量指标沿用已确认的测量条件、统计口径与阈值，记录实测值。UI 按项目已确认的中保真范围核对信息架构、结构布局、操作路径、交互反馈与业务状态，排除纯视觉样式和像素比对；原型或模拟结果只证明其实际覆盖。沿场景／AC 记录版本、环境、实际结果、证据及通过、失败、未测或阻塞。
5. **处理取证问题。** 在授权内修正本轮测试脚本、测试数据或环境准备问题，必要时安排测试代码补充，沿用已确认断言并重跑受影响场景；测试侧问题已有 Issue 时按授权记录核验结果。判据与实现冲突时保留预期与实际差异，交 Main。实现缺陷沿用原 [Issue](../../sdd/assets/issue_template.md) 或按授权登记，保留原编号、复现条件、预期、实际、影响、版本和证据，交 Main 按阶段授权处理。未测或阻塞写明原因、影响和恢复条件。
6. **核对版本、覆盖和复验。** 对照覆盖清单与实际报告补验遗漏。版本或环境变化时，按[证据与复用](../../sdd/references/sdd-repository-governance.md#证据与复用)分析实现、接口、数据、装配和测试方法的影响，在目标版本补验其余场景。纳入已就绪的修复版本时，为原 Issue 取证并保留历次结果。按[Issue 关单](../../sdd/references/sdd-repository-governance.md#issue-关单)更新获授权的状态，其余情况将证据交 Main。状态记录本身不启动缺陷处理。
7. **交付与判定。** 交付可复跑的指南或可访问链接、[Test Report](../../sdd/assets/test_report_template.md)、缺陷及恢复条件。获授权时按[文档写入规则](../../sdd/references/document-writing.md)归并，Status／Plan 引用报告。本 Skill 按证据直接判定 Test Gate。指定版本和环境下，范围内全部适用功能点及本轮判据均满足，且必要证据和必需的人工验收反馈齐备时，才可判为 PASS。完整记录的失败或阻塞也可结束本轮测试执行，保留未通过原因和恢复条件。存在可执行的场景时继续取证，直至得到完整覆盖状态。

## 阶段内执行安排

本 Skill 按[委派与独立性](../../sdd/references/delegation.md#委派与独立性)安排以下工作，核对回执并汇总 Gate。仅当本轮要求独立验收而无法满足时，记录受影响场景及恢复条件；其余按能力选择执行者。

| 何时需要／专业工作 | 当前角色与必要输入 | 回收结果 |
| --- | --- | --- |
| 复杂需求需推导覆盖与验收步骤 | 通常由 `sdd-product-manager`；给定已确认范围、场景、判据及适用契约，可推导用例但不改变业务 | 功能点与场景／AC 映射、用户验收文档、依据缺口 |
| 缺少或需修正测试代码、工具与诊断装配 | 通常由 `sdd-coder`；给定场景、确认判据、工具现状和测试资产写入边界 | 改动、可跑入口、局部自验证据、适用范围和未验项 |
| 需准备或排查测试环境 | 通常由 `sdd-devops`；给定目标环境、候选版本、入口、授权操作与就绪条件 | 环境、实际版本、入口、服务状态及故障证据 |
| 规格或证据引用疑似冲突 | 按需由 `sdd-doc-consistency`；给定疑点、权威来源及指定只读范围 | 证据位置、权威依据、影响和待核实项 |
| 执行测试或核对结果 | 技能执行者直接执行或选合格执行者；给定用户入口、批次、覆盖、确认判据及可复用证据 | 逐场景结果、版本、证据及覆盖缺口 |

产品代码修复、业务需求变更、架构决定与重构、架构 Review 和发布由 Main 按[阶段授权与推进](../../sdd/references/sdd-repository-governance.md#阶段授权与推进)协调。修复版本返回本批次时，按[技能 Agent 的启动与接续](../../sdd/references/delegation.md#技能-agent-的启动与接续)恢复测试。
