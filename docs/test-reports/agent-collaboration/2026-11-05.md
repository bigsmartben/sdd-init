# 测试报告：专职 Agent 协作机制

## 1. 测试目标与依据

- 报告批次、验证类型、执行者与时间：2026-11-05；规则协作行为及分发集成验证；Main 协调，sdd-coder 实施与局部自验，sdd-validator 初验及复验。
- 测试对象与目标：本轮 imp、test、review 的专职角色交接、自动接续和分发安装保护。
- 依据：[Spec FR-011／AC-011](../../../specs/platform-independent-sdd/spec.md)、[本轮 Plan](../../plans/agent-collaboration.md)及用户确认范围。

## 2. 测试范围与计划

- 范围：本仓库候选规则、隔离 direct 行为评测、blind 行为评测、分发与安装保护；外部服务及真实项目升级不在本轮范围。
- 测试安排：按 Plan T004—T006；direct 使用种入缺陷的隔离订单夹具，blind 的执行者不预先获知预期角色路线。
- 完成标准：对应 Spec 与 Plan 中角色调用、修复复验、规则覆盖、证据及授权边界；未完成事项不判通过。

## 3. 测试环境

- 被测版本：`b46594a1a17704039197d0d1af8b44cbf19ad6fd` 加本轮未提交修改；direct 初审规则和代码哈希见[初审快照](evidence/initial/sha256.json)，规则修复后的载荷哈希见[字节核对](evidence/distribution/byte-check.json)。
- 环境与入口：本机 Windows；隔离订单夹具使用 Python 3.14.6 和 SQLite 3.50.4，见[运行事实](evidence/initial/runtime.log)；构建及安装检查使用隔离目录。
- 真实与模拟边界：订单缺陷为评测有意种入，SQLite 为本地实际文件；未访问真实外部服务。blind 的任务只给候选项目入口和中性目标，未告知预期角色路线；实际角色事件见[blind Main](evidence/trace/blind_main.json)、[validator](evidence/trace/blind_main-validator.json)与[coder](evidence/trace/blind_main-coder.json)。
- 轨迹范围：`evidence/trace/` 中 Main、validator、coder 及边界角色轨迹是 app 已导出 JSON 的逐字节副本，保留原始事件标识、角色线程 ID、调用与命令；导出排除 reasoning、`includeOutputs=false` 且文本有截断，不是完整会话，命令输出另见评测证据。[rollout 调用参数提取](evidence/trace/rollout-agent-call-parameters.json)保留可读的角色类型、call ID、fork 参数、原行号及 SHA-256；来源为本会话三个 rollout 的 134 条相关调用／返回、11 次 spawn。原 message 在 rollout 中为密文，提取文件只保留其哈希，不是解密内容；发起 Main 的[中性任务转录](evidence/trace/neutral-dispatch-transcription.json)由其根据实际派发记录，不能单独当作独立解密证据，须结合 call ID、`fork_turns` 和夹具任务交叉核对。原始密文提取留在 `.build/agent-collaboration/trace-20261105/rollout-agent-calls.json`，其 SHA-256 记录在参数提取中。候选规则由评测执行者读取；这些事实不能证明平台重载新 TOML 或实际模型遥测。
- Review 收敛的[增量角色事件](evidence/review-items/r2/trace/blind_main.json)及对应 [coder](evidence/review-items/r2/trace/blind_main-coder.json)、[validator](evidence/review-items/r2/trace/blind_main-validator.json)记录仅含筛去旧事件 ID 后的新轮次，沿用上述 app 导出的截断和不含输出限制；角色 ID 可与前一阶段轨迹交叉核对。

- 仓库及安装检查：初次仓库测试 50 项通过，见[原始输出](evidence/distribution/unittest.log)；构建后安装回归 25 项通过，见[原始输出](evidence/distribution/test_govern.log)。新构建的 67／67 项项目载荷及 46／46 项共享投影字节匹配，见[核对结果](evidence/distribution/byte-check.json)。初次测试在规则 GAP-001 修复前执行，修复后对受影响分发源做字节核对及规则复核，不将初次结果标为新快照的重跑结果。

## 8. 测试结论与限制

- 总体结论：原 validator 对 direct、1 个 blind 和 3 个边界场景的通用协作机制阶段，以及 Review 检查项收敛的已声明增量机制场景分别给出 PASS；结论不扩展到全部 38 个静态案例，也不代替隔离夹具自身的 Test／Review Gate。
- 遗留风险与未验证项：direct AC-3 的夹具入口明确不联网且恒为 BLOCKED。本轮禁止配置或访问外部；后续需明确授权的服务端点、调用权限，并在授权范围内选用或提供可执行真实外部核验入口及其契约、配置，不能仅修改 `runtime.json` 恢复。
- 人工确认：订单夹具不要求人工视觉确认；用户已确认实施范围和后续 Review 收敛方向。
- Gate：本仓库通用协作机制阶段 Test Gate、Review 检查项收敛增量机制验收及本轮源规则 Review 在各自已声明范围内为 PASS；direct 隔离订单夹具 Test Gate 为 BLOCKED；blind 的 Test／Review Gate 均为 BLOCKED，Review 原因包括 GAP-002：夹具无正式观测系统与 SDD-OBS-02/03 强制条款的适用性及必要文字事实范围待决，须由项目决策人确认适用性与范围，若适用再确定授权及可执行契约。只审边界的 Review Gate 因 GAP-R1 为 FAIL，CHK-006／008 的 GAP-R2 为 BLOCKED，恢复须确认合规方案、归并一致契约并在授权内实施复核。r2 隔离夹具的 Review Gate 为 BLOCKED：CHK-006 须有权人员提供已授权端点、权限、网络与外部验证授权；CHK-007 依赖该项及明确的外部装配核验入口；CHK-008 须确认观测基线适用性与事实范围，适用时明确契约及授权。各 Gate 分别报告，不把本地修复通过写成全部 AC 或架构规则通过。
