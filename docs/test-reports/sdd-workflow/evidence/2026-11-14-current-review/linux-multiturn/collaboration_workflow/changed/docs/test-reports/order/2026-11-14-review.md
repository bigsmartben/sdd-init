### CHK-001：状态写入职责及工程边界

- 依据与对象：CR-001、ARC-1；`ui.mark_paid → order_service.set_status → UPDATE/commit`，并核对 `src` 全部 SQL。`storage.connect` 仅连接/建表，`order_service` 承担订单写入。
- 初审事实：**FAIL**。`ui.py` 的 `mark_paid` 直接 `connection.execute(UPDATE...)` 及 `connection.commit()`，绕过服务写入口。`order_service.py` 的 create/set_status 自行 commit，storage 没有订单实体状态 UPDATE。实际目录与职责总体一致，局部 UI 写权限越界。
- 整改目标与交接：交 Main 判断是否纳入本地缺陷修复；目标为恢复已确认的 UI→服务调用，保留公开签名和现存订单 paid 持久化结果，不额外发起重构。
- 验收计划：修复快照就绪后由本审查者沿同一原项复核实际源码、AST/import、SQL/commit 全部落点；通过条件是 UI 不含状态 SQL/commit，仅调用服务写入入口，storage 仍仅连接/建表。行为保持从 `ui.mark_paid` 公开入口调用，第二连接及重开后 paid；不存在订单遵守 ValueError，数据库故障上抛，不转成功。完整行为复验由 Main 协调测试阶段并引用实际快照证据。
- 初始行为证据：独立临时 SQLite 文件创建/提交订单 A，再 `ui.mark_paid`，第二连接读为 paid；只读连接调用 UI 写入抛 `sqlite3.OperationalError: attempt to write a readonly database`。这些结果不消除职责违规。
- 初审时实施工单：待 Main 交接；本审查未改代码。初审状态：未修复，FAIL。
- 实际交接：Main 将恢复服务边界纳入 [BUG-002](../../issues/BUG-002.md) 与[修复计划 T001](../../../specs/order/plan.md#t001-恢复两个原-issue-的已确认行为)，作为缺失订单异常修复的同一路径，不另启技术重构。

### CHK-002：持久化完成及数据库异常

- 依据与对象：CR-002、ARC-2、订单契约；create/cancel/submit/set_status/mark_paid 写入及 commit 路径、文件数据库回读。
- 初审事实：**PASS（架构范围）**。所有实际写入后执行 commit，无吞异常或将数据库失败转换成功的处理；submit 的 true 位于写入与 commit 之后。独立实验创建 A→submit，返回 true；关闭后重开读取 submitted；UI paid 经第二连接读取 paid。以 `sqlite3.connect(file_uri + '?mode=ro', uri=True)` 真实只读连接执行服务 set_status 和 UI mark_paid，均上抛 OperationalError，未返回成功。
- 已知差异：submit 无取消状态保护，是 AC-2 业务缺陷。该检查的 PASS 仅说明持久化/错误传播符合 CR-002，不表达取消后提交符合契约。
- 复核计划：如写入/判断改动，复核实际 commit 与异常链，沿公开接口定向回读；允许引用同快照集成报告中重开及异常证据。通过条件为成功必须完成数据库 commit，数据库异常上抛，失败不能表达成功。行为基线见第 1 节。
- 整改交接：本项无独立架构整改。初审状态：符合，PASS。
