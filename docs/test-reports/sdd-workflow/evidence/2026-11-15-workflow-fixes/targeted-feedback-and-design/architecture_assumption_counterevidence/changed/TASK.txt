观察点、判据及实际结果：
- E1_current_rows：通过真实 src 服务创建两库，路径 A 为 pending→submitted→paid，B 为 pending→paid，各次操作 commit；关闭所有写连接，再以新连接 SELECT。若现有记录足以恢复历史，应能区分两条路径。实际均为 [('O','paid')]，same_logical_export=true，假设被推翻。这里比较的是可查询逻辑记录；未声称数据库文件字节完全相同，也未对残页/WAL 作取证。
- E2_trace：注册一个连接的 SQL trace，执行 submitted 后 rollback；另一连接通过真实服务提交 paid；关闭并重开。trace 有 submitted UPDATE 和 ROLLBACK，却没有另一连接的 paid；持久状态 paid。因此连接回调不是跨连接、跨生命周期的已提交历史存储，不能直接充当历史。
- E3_service_history：隔离候选使用 orders + history(seq, order_id, old_status, new_status)，状态写与追加历史置于同一 with connection 事务中。一次事务内 submitted→paid 都保存，重开后 history 的 new_status 为 pending/submitted/paid，seq 为 1/2/3。主动失败后的 cancelled 不留存；注入历史写失败后状态写也回滚，仍为 paid。另一连接直接 SQL 改为 cancelled 后 history 不变，证实此候选需保证所有写路径统一经过入口。不是现有 src 的功能，也未接入现有服务。
- E4_trigger_history：隔离候选在数据库建持久 AFTER INSERT / AFTER UPDATE OF status 触发器，后者只记录值实际不同的更新。关闭创建触发器的连接，另一连接同一事务执行 submitted→paid→paid，之后尝试 cancelled 并 rollback；再重开，history 仍为 pending/submitted/paid，顺序 seq=1/2/3；跨连接写入有记录，同事务中间状态保留，同值写与回滚剔除。这里明确区分“写 SQL 的顺序”与“事务提交后对外可见”；同事务中间状态在提交前不可对外观察，提交后可从历史恢复。

证据驱动的候选比较（均未获设计确认）：
1. 现有 orders 直接导出：改动最少，但只能返回末态；E1 反证其满足目标的前提，不进入满足逐次历史的推荐集合。
2. 周期轮询/连接 trace/普通 SQL 日志：轮询不能保证捕获两次读取之间或同一事务内的中间状态；trace 的跨连接与回滚问题由 E2 证实。若额外建设完整持久提交捕获和顺序协议，则已成为新的记录系统，不能当成“直接读现有历史”。未做日志系统或轮询性能实验。
3. 服务显式追加历史表：orders 保持当前状态权威，history 承载已记录变化；order_service 负责状态与历史的单事务写入，storage 负责 schema/迁移，调用方使用独立读取接口按 seq 排序。最贴近 ARC-1 的职责，易携带业务原因/操作者等上下文；每次变化多一次 INSERT 和存储增长。E3 验证基本原子性及回滚，同时证明旁路 SQL 漏记。实施需调整现有函数内部 commit 边界、覆盖创建和所有状态写路径；任一历史写失败必须向上传播并回滚状态，不返回成功。此方案条件：能约束所有业务写入口；并非已确认选型。
4. SQLite 持久触发器追加历史表：业务状态权威仍为 orders，业务入口仍归 order_service；数据库承担历史捕获不变量，需确认扩展 storage 的 schema/迁移职责及修改契约。E4 验证跨连接、同事务多次变化与回滚隔离；每次变化增加触发器 INSERT。适合要求连接无关或需要覆盖 SQL 旁路的情况；业务上下文传递较复杂，迁移/停用触发器/直接改 history 的权限与运维需要约束。只建永久触发器，不能用连接专属 TEMP 触发器代替。若历史表/触发器写失败应阻止本次状态写成功；该故障路径未在 E4 单独注入，不把 E3 的结果冒充触发器故障测试。
5. 追加事件作为状态权威、从事件重建当前状态：可为新写入保留序列及回放基础，但改变状态权威、查询和一致性责任，重构及迁移成本更高；本地尚未实验。没有额外业务需要时，不优先于同库历史表。文件 SQLite 仍可承载，不需要新增技术栈。

顺序、读取及恢复的候选约束：
- 用明确的单调序号作为 ORDER BY 键，不能依赖未排序 SELECT 或时间戳打平后的自然顺序。实验 seq 为数据库内 INTEGER PRIMARY KEY AUTOINCREMENT；只保证本数据库保留记录的排序，不能解释为无缺口计数、墙钟时间、跨数据库全局顺序或跨备份恢复后的永久唯一事件身份。
- 已提交历史包含成功事务内每次实际变化，回滚不留记录；同值 UPDATE 是否算一次历史、创建 pending 是否算初始事件，实验采用“不算同值更新、算创建”，仍是候选口径待用户决定。
- 新接口候选为按 order_id + seq 读取/导出；变更与历史写原子提交后才报告成功，异常沿现有契约向上传播。未来如增加增量游标，需确认全局/每订单顺序及分页快照一致性；本轮未设计外部 API。
- 候选引入只能自启用后开始可靠记录；旧数据只能标记为基线快照，不能伪造已丢失路径。迁移需在受控写窗口内建表/建触发器或统一切换服务写入口，避免基线与首个事件之间出现空档。回退若停用捕获将产生缺口，须先决定可接受程度并保留已有历史。
- 同库快照备份/恢复需让 orders 与 history 一致；历史增长、保留策略和索引按查询量决定。未测大量数据、竞争写锁、硬断电、损坏恢复、迁移中断、备份回退或生产性能，不从本实验推导这些保证。
- WAL/残页不等于受支持、完整且长期保留的业务历史；本轮未实验其取证能力，也不声称任何方法均无法恢复旧片段。结论仅为现有可查询逻辑记录无法保证恢复每次变化。

交 Main 的待决项及接续条件：
