# BUG-001 — 取消订单被再次提交覆盖

## 事实与归因

- 类型：已证实的实现缺陷；影响 [订单需求](../../specs/order/spec.md) AC-2 和 [订单契约](../contracts/order.md) 的 cancelled 不写入、返回 false 判据。
- 本轮授权：Main 已转交用户确认，仅当前隔离项目、本地 Python 和临时文件 SQLite；修复取消后提交缺陷并更新本地记录。保持既有接口、AC-1、mark_paid 的 paid 结果；不操作 Git、外部平台或部署，不整改其他架构偏差。
- 首次取证：2026-11-14 UTC，`/root/bugfix/coder`；Python 3.12.3、SQLite 3.45.1，实际基线及依赖哈希见 [环境证据](../test-reports/order-cancel/baseline-environment.json)。
- 公开入口：`create_order` → `cancel_order` → `submit_order`。`python -B checks/acceptance.py --scenario AC-2` 返回 true，关闭并重开文件数据库后为 submitted；预期 false 和 cancelled。见 [复现输出](../test-reports/order-cancel/baseline-ac2.json)。影响为订单取消状态丢失。
- 已验证原因：submit_order 读取状态后无条件 set_status(submitted)，未判断 cancelled。[SQL 轨迹](../test-reports/order-cancel/baseline-causal-trace.json) 证明提交前 cancelled，提交执行 UPDATE submitted 与 COMMIT，重开后 submitted，排除取消未持久化假设。既有 2 项单测通过但缺少取消路径，见 [基线单测](../test-reports/order-cancel/baseline-tests.json)。

## 修复工单与验收计划

恢复目标为取消后提交返回 false 且不写入，文件中保持 cancelled。实施者维护 [同一 Plan](../plans/order-cancel-fix.md)，只定向修改 order_service 与必要测试；ui 的既有直接 SQL 不在本单整改。其他非 pending、非 cancelled 的提交语义不新增决定，保持当前路径。

局部自验由 coder 在候选就绪后执行；独立定向复验由 `/root/bugfix` 对同一源哈希执行。使用实际服务公开接口和真实临时文件 SQLite，不用内存数据库或模拟成功替代原场景。判据如下。

| 判据 | 前置、操作与观察 | 通过条件 |
| --- | --- | --- |
| 取消后提交 | 新建 pending，取消，提交；采集该提交 SQL；关闭并重开数据库 | 返回 false；该提交无写入；重开为 cancelled |
| 正常提交保持 | 新建 pending，提交；关闭并重开 | 返回 true；重开为 submitted |
| paid 保持 | 新建现存订单，调用 ui.mark_paid；重新连接读取 | paid 已持久化 |
| 异常保持 | 不存在订单提交；真实 SQLite 提交失败 | 分别抛出 ValueError、原数据库异常，不返回成功 |

AC-3 需要外部端点与权限，既不是本缺陷关单判据，也不能用本地结果替代。无视觉或人工判断判据。若独立复验失败，沿本编号回到归因或实施。
