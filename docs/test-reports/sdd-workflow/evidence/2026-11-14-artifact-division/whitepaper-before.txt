# sdd-workflow 白皮书

## 设计目标

支持用户确定关键结果，由 Agent 在授权范围内持续完成工程交付，并提供可追溯的验证证据。

| 目标 | 要求 |
|---|---|
| 关键决策集中 | 人类决定业务主流程、核心体验、交付范围及关键取舍；Agent 自主处理授权内的设计与执行细节。 |
| 交付目标独立 | 需求交付与架构重构分别定义范围、完成标准和验证依据，避免相互扩大任务。 |
| 长程自主执行 | 前置必要确认，持续实施、验证、修正与接续；正常执行减少无决策价值的打扰。 |
| 项目知识有效 | 当前依据唯一、准确、可定位；及时清理失效、重复及无用内容，历史资料与当前依据分离。 |
| 交付可信可续 | 结论对应实际版本和覆盖证据；中断或交接后可恢复，已确认决定与有效证据可复用。 |

适用范围包括需求、架构、开发、验证、交付和运行维护，支持讨论、规格、评估、诊断等独立终点。工程质量覆盖架构一致性、探索结果追溯、正式与测试隔离、业务与运行职责及持久化可靠性。目标项目自行确定业务需求与具体架构。

本文不覆盖初始化、安装、升级与分发机制。具体行为承诺及验收条件归 [Spec](../specs/platform-independent-sdd/spec.md)；具体版本的审查发现、证据与整改状态归审查记录，本文引用其事实维护[当前版本综合结论](#当前版本综合结论)。设计要求不代表实现已通过审查。

## 问题清单

以下为工作流需要解决的问题，不作为现有实现的缺陷结论。

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 推断替代意图确认，关键决定与技术细节混杂 | 交付偏离预期，用户承担过量决策。 |
| P2 | 确认零散、重复，已知缺口未前置 | 长程执行频繁中断。 |
| P3 | 需求交付与架构重构范围交叉扩张 | 阶段相互阻塞，完成标准失焦。 |
| P4 | 已授权工作不接续，局部阻塞扩大 | 执行停滞，修正与复验无法闭环。 |
| P5 | 规则、文档和代码过时、冲突或重复 | Agent 读取负担增加，推理依据失真。 |
| P6 | 局部通过替代整体验收，修复或重构遗漏原判据 | 完成声明缺乏充分证据。 |
| P7 | 决定、版本、进展和证据无法可靠交接 | 中断后重复执行或要求用户重述。 |
| P8 | 固定流程、冗余材料及无效进度通知 | 协作成本超过实际价值。 |
| P9 | 设计约束、授权和实际执行脱节 | 架构难以核验，交付与运行操作越界。 |

## 实现策略

### 工作流策略

| 编号 | 策略 | 约束 |
|---|---|---|
| S1 | 按影响确认 | 需求与方案分别确认，沿用有效确认；关键变化重新对齐。技术事项仅在实质影响用户结果时提交决策，并说明影响与选项。 |
| S2 | 前置执行约定 | 集中明确目标、范围、排除项、约束、验收、授权终点及已知待决事项。技术未知可在授权内探索，无须预先穷尽；触及关键约束时重新确认。 |
| S3 | 分别闭环 | 需求交付可包含必要局部结构调整；重构保持已确认业务需求与行为。跨类别发现不自动扩围；独立重构成为必要前提时，提交依赖、影响与选择供用户决定。按目的和影响区分任务。 |
| S4 | 持续推进 | 自主实施、调整、验证、修正及接续已授权阶段。关键预期变化、授权不足或无法自主解决的阻塞触发决策；仅暂停关联事项及其依赖。 |
| S5 | 原位维护知识 | 已确认结论归并至唯一正文，同步直接受影响的内容与引用。清理失效、重复和无用内容，保留有效条件、例外与追溯关系，保护范围外资产；局部维护不自动扩为全仓整改。 |
| S6 | 按证据完成 | 结论绑定判据、版本、环境和覆盖范围；失败按原判据修正复验。各类验证分别证明其覆盖，原型与正式运行分别取证；未执行或缺少必要人工反馈的事项保持待验。 |
| S7 | 保持可恢复状态 | 保存有效决定、版本、进展、证据、剩余项、阻塞及恢复条件；接续时核对适用性，避免重复确认、重复执行或复用失效证据。 |
| S8 | 按需组织、静默执行 | 流程、材料和检查与交付目标相称。纯讨论无需正式模板及架构门禁；明确工单可按自身判据执行，不以完整 Blueprint 为前提。减少无决策价值的通知，支持状态查询，及时呈现关键阻塞、预期变化和最终结果。 |

### 三层架构

采用**主任务 → 技能 → 角色**的职责组织关系，承接 S3、S4、S8。

| 编号 | 约束 | 职责与边界 |
|---|---|---|
| I1 | 职责单一 | 主任务面向用户、组织交付、协调阶段；技能负责单一交付目标的阶段闭环；角色负责专业执行与产物。主任务不重复技能流程，技能不重复角色执行规则，角色不组织跨阶段工作。 |
| I2 | 同层禁止依赖 | 技能之间、角色之间均不直接调用、调度或交接，由共同上层组织协作。允许复用上层提供的合格产物和证据；不得要求同层单元先运行，或依赖其内部流程。 |
| I3 | 上下位禁止倒置 | 上层确定目标、范围与完成要求；下层执行并回报结果、缺口和建议，不得重定义目标、扩大授权或指挥上层。阻塞回报不构成倒置。 |

三层架构不要求严格逐层调用。主任务可直接执行对象和结果明确、操作本身即授权终点的局部操作，也可直接委派角色；两类路径均须保留适用的阶段闭环。具体 Skill 清单、角色数量、调度实现及模板形式按上述约束审查。

## 审查清单（Review Checklist）

### 审查规则

以各技能与角色能否按职责完成任务交付为首要判据。先用[Review 矩阵](#review-矩阵)逐个核对技能和角色的交付闭环，再逐项覆盖 RW-01～RW-12。给定合格输入和明确授权，技能组织阶段内执行、适用的验收与复验，按授权终点向主任务交付结果与证据。角色独立完成本职工单，向实际调用方交付可核验的专业产物和证据。未完成事项在回执中说明缺口、影响和接续条件。

审查对象为本仓源码及其实际生效入口、共享规则、技能、角色、模板与直接引用。记录受审范围、排除项、版本及未提交改动快照；不加载或修改用户级已安装工作流。实现与目标冲突时按目标识别偏差，保留仍适用的能力要求与例外。

本仓全面评审与回归由用户显式启动 [sdd-workflow-review](../.agents/skills/sdd-workflow-review/SKILL.md)。通用角色 [review-prompt](../source/initializer/assets/user-agents/review-prompt.toml) 可承接提示词专项取证，技能汇总跨对象覆盖和整版结论。

先审语义与引用，再按需核验行为。行为结论须有适用的执行记录，新增验证在授权的隔离环境中进行。机械检查仅覆盖结构、编号、编码与引用，不替代语义或证据判断；不按关键词、材料数量、步骤数量或固定询问次数判定质量。

清单勾选表示已检查并记录结论。实际结果写入对应版本的审查记录，包含检查项、对象与版本、依据位置、事实证据、结论、影响、建议及未验范围。结论分为**符合、存在偏差、证据不足、不适用**，不适用须说明原因；静态符合不得替代行为验证。

### RW-01 决策负担

依据：S1；Spec FR-025。证据：确认规则、用户决定、询问与变更记录。

- [ ] 01.1 人工决策限于关键结果；技术事项提供可判断的影响与选项。
- [ ] 01.2 有效确认得到复用，需求与方案确认未扩为逐层细节审批。
- [ ] 01.3 关键预期变化重新确认，无擅自变更路径。

### RW-02 执行准备

依据：S2；Spec FR-029。证据：执行约定、缺项记录、探索与决策记录。

- [ ] 02.1 目标、范围、排除项、约束、验收、终点及已知待决事项在执行前明确。
- [ ] 02.2 授权内技术探索不以人工审批为前提。
- [ ] 02.3 区分可预见缺项与执行中新事实；探索结果触及关键约束时重新确认。

### RW-03 交付目标独立性

依据：S3；Spec FR-020、FR-029。证据：任务范围、改动、业务与架构判据、依赖决定。

- [ ] 03.1 需求交付不被无关架构治理阻塞或扩围。
- [ ] 03.2 重构不夹带业务变更，架构改善与行为保持分别验证。
- [ ] 03.3 区分必要局部调整、范围外发现与独立重构依赖；必要依赖经用户决定，不按代码类型归类。

### RW-04 持续推进与授权

依据：S4；Spec FR-005、FR-031。证据：授权、依赖、阶段回执与修正复验记录。

- [ ] 04.1 已授权且就绪的工作自主接续，无重复启动确认。
- [ ] 04.2 失败修正与复验闭环；局部阻塞不暂停无关就绪事项。
- [ ] 04.3 执行止于授权终点；阻塞注明影响及恢复条件。

### RW-05 知识有效性

依据：S5；Spec FR-001、FR-006。证据：当前决定、读取入口、引用链、内容用途与变更差异。

- [ ] 05.1 当前依据唯一有效，失效、重复、不匹配内容及废弃代码不再误导执行。
- [ ] 05.2 语义变更同步直接引用，替代关系清晰，历史退出当前依据。
- [ ] 05.3 清理有依据，保留有效例外与追溯关系，保护范围外资产。链接存在不代表语义有效，缺少近期引用不足以判定可删除。

### RW-06 完成可信度

依据：S6；Spec FR-008、FR-009、FR-010、FR-026。证据：判据、版本、环境、报告、人工反馈及复验历史。

- [ ] 06.1 完成声明对应实际覆盖；局部自验、需求验收、集成验证、架构复核及运行检查不越界互替。
- [ ] 06.2 失败、未执行及人工待验显式保留，按原判据复验，历史失败可追溯。
- [ ] 06.3 复用证据仍适用，原型模拟与正式运行分别取证。

### RW-07 恢复与交接

依据：S7；Spec FR-005、FR-009、FR-031。证据：接续时可见资料、实际版本及接续执行记录。

- [ ] 07.1 决定、版本、进展、证据、剩余项与恢复条件可定位。
- [ ] 07.2 中断或交接后可继续，无须用户重述或重复已验证工作。
- [ ] 07.3 陈旧状态和失效证据得到识别，必要补验范围明确。记录齐全不等于已证明可恢复。

### RW-08 流程成本与静默执行

依据：S8；Spec FR-012、FR-025、FR-031。证据：流程规定、产物用途与沟通记录。

- [ ] 08.1 讨论、局部操作及完整交付采用相称流程；材料与检查用途明确。
- [ ] 08.2 正常长程执行减少无决策价值的通知，必要决策集中呈现。
- [ ] 08.3 状态查询、关键阻塞、预期变化及最终结果可见，静默不损害可恢复性。

### RW-09 三层组织与直接调用

依据：三层架构。证据：入口条件、职责规则、任务约定与调用记录。

- [ ] 09.1 三层职责清楚，无强制逐层调用门禁。
- [ ] 09.2 主任务可直接执行合格局部操作、直接委派角色。
- [ ] 09.3 直接路径保留适用阶段闭环，不以跨层调用本身判定违规。

### RW-10 职责单一

依据：I1。证据：规则归属、输入输出、流程引用与实际动作。

- [ ] 10.1 用户交互与阶段协调、阶段闭环、专业执行分别归属相应层次。
- [ ] 10.2 无跨层重复维护的流程或执行规则；必要引用不判为重复。
- [ ] 10.3 角色专注专业任务与产物，不承担跨阶段组织。

### RW-11 同层执行独立

依据：I2。证据：前置条件、输入来源、调用与交接记录。

- [ ] 11.1 同层协作由共同上层组织，无直接调用、调度或交接。
- [ ] 11.2 本职执行不要求指定同层先运行，不依赖其内部流程。
- [ ] 11.3 可复用上层提供的合格产物与证据；输入缺失回报上层。信息复用不判为执行依赖。

### RW-12 上下位关系

依据：I3。证据：任务约定、执行动作、回执及后续决定。

- [ ] 12.1 下层遵守上层目标、范围和完成要求，无重定义或扩权。
- [ ] 12.2 回报结果、缺口及建议，不指挥上层或代其决策。
- [ ] 12.3 目标与授权变化来源可追溯；正常阻塞回报不判为倒置。

### Review 矩阵

按受审对象选择下表的场景和证据，使用 RW 子项记录结论。表内编号对应上方清单，列出各对象优先核对的子项。其他子项按本轮场景判断适用性。RW-09～RW-12 按实际入口、调度关系和回执跨行核对。

五个项目角色按 [Spec AC-011](../specs/platform-independent-sdd/spec.md#验收条件)进行独立执行检查。在隔离项目中逐个只注册受验角色，提供合格工单、适用项目资料及共享资源，令工作流 Skill 不可用。核对实际调用、专业产物，并确认结果、证据、缺口和建议交回实际调用者。通用提示词审查的独立性按 AC-028 验证，工单与项目依据齐备即可。

### 结果归并

审查记录逐个列明技能和角色的交付结论，并记录 RW-01～RW-12 的实际覆盖、未查项与证据缺口，结论限于受审范围。同一事实可关联多个检查项，避免重复建问题。整改优先级按问题对实际交付的影响排序，并说明受影响的交付结果。新取舍须确认，范围外事项不自动整改。

界面审查覆盖信息架构、结构布局、交互与业务状态，不含纯视觉样式及像素还原。行为验证、原型模拟、局部自验和正式系统验收分别记录覆盖范围。

## 质量与执行成本评估

本节承接 [Spec FR-033／AC-033](../specs/platform-independent-sdd/spec.md#验收条件)。每次评估绑定源码快照、依据版本、日期及证据入口。白皮书维护当前摘要，逐项发现、原始测量与历次记录保留在对应报告中。更新源码后先核对证据适用性，再更新结论。

### 评估维度与口径

| 维度 | 记录内容 | 判断依据 |
|---|---|---|
| Review 矩阵 | 各受审对象及 RW 子项的结论、未查项、问题编号与证据 | 采用符合、存在偏差、证据不足、不适用四类结论；发现清单不能代替完整矩阵覆盖。 |
| 提示词 token 量 | 源码总量及入口、技能、角色、共享规则等分项；按任务记录实际加载量 | 固定文件清单、快照、tokenizer 名称及版本，源码按文件去重；实际加载按轨迹统计，重复加载另列。不把全部引用文件视为必然加载，不以字符数替代 token。 |
| 提示词质量 | 清晰性、职责与优先级、完整性、重复与冲突、可执行性、交接与完成判据 | 每项对应具体条款或行为证据，说明影响及整改建议。静态语义结论与行为验证分开；不以篇幅短、关键词齐全或无报错判为优质。 |
| 任务 token 消耗 | review 与 testcase 执行分开记录输入、缓存输入、输出、可取得的推理 token 及总量 | 使用运行时 usage，注明平台字段含义；缓存输入、推理 token 若已包含在输入或输出中，不重复相加。覆盖 Main 及子 Agent，按请求去重，注明重试、整改、复验是否包含。 |
| 任务执行时长 | 两类任务各自的开始、结束、总历时、人工等待及可分离的执行历时 | 同一批次记录时区和时间戳。总历时按墙钟计算；并行 Agent 时长不相加冒充用户等待时长。执行历时扣除可确认的人工等待，仍包含工具及调度等待；无法拆分时标明未测。 |
| 质量与成本综合判断 | 已证明的能力、主要偏差、成本证据缺口、优化优先级 | 在相同任务范围、用例、模型配置、环境和完成标准下比较，记录样本数及失败批次。没有可比基线不宣称节省比例，不以降低 token 为由省略必要验证。 |

提示词源码体积、单次任务实际加载量和运行时累计 token 消耗分别计量。任务记录注明任务类型、批次／用例 ID、源码快照、模型与推理配置、环境、结果、统计范围和证据。review 内若执行 testcase，按实际可分离的阶段分别登记并关联同一批次；共享开销只归属一次，无法拆分时注明，不填入两个独立总量。

缺少实测数据统一填“未测”并说明原因；部分覆盖注明已测范围和缺失部分，不把部分值作为完整总量。未测不等于零，也不等于任务未执行。估算须单独标识方法，不能替代实测。多个批次先保留逐次数据，再给样本数和范围；质量缺口与成本缺口分别判断。
