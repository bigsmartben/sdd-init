# sdd-workflow 白皮书

本文按[白皮书结构模板](../.agents/skills/sdd-workflow-review/assets/whitepaper-template.md)组织已确认设计。S1～S8、I1～I3 是可独立引用的设计条款；修改这些决定须有相应确认。

## 设计目标

支持用户确定关键结果，由 Agent 在授权范围内持续完成工程交付，并提供可追溯的验证证据。

| 目标 | 要求 |
|---|---|
| 关键决策集中 | 人类决定业务主流程、核心体验、交付范围及关键取舍；Agent 自主处理授权内的设计与执行细节。 |
| 交付目标独立 | 需求交付与架构重构分别定义范围、完成标准和验证依据，避免相互扩大任务。 |
| 长程自主执行 | 前置必要确认，持续实施、验证、修正与接续；正常执行减少无决策价值的打扰。 |
| 项目知识有效 | 当前依据唯一、准确、可定位；及时清理失效、重复及无用内容，历史资料与当前依据分离。 |
| 交付可信可续 | 结论对应实际版本和覆盖证据；中断或交接后可恢复，已确认决定与有效证据可复用。 |

## 适用范围与边界

适用范围包括需求、架构、开发、验证、交付和运行维护，支持讨论、规格、评估、诊断等独立终点。工程质量覆盖架构一致性、探索结果追溯、正式与测试隔离、业务与运行职责及持久化可靠性。目标项目自行确定业务需求与具体架构。

本文不覆盖初始化、安装、升级与分发机制。具体行为承诺及验收条件归 [Spec](../specs/platform-independent-sdd/spec.md)；具体版本的审查结论、发现、证据、整改状态与实测成本归对应批次的 Review 报告。设计要求不代表实现已通过审查。

## 问题清单

以下为工作流需要解决的问题，不作为现有实现的缺陷结论。

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 推断替代意图确认，关键决定与技术细节混杂 | 交付偏离预期，用户承担过量决策。 |
| P2 | 确认零散、重复，已知缺口未前置 | 长程执行频繁中断。 |
| P3 | 需求交付与架构重构范围交叉扩张 | 阶段相互阻塞，完成标准失焦。 |
| P4 | 已授权工作不接续，局部阻塞扩大 | 执行停滞，修正与复验无法闭环。 |
| P5 | 规则、文档和代码过时、冲突或重复 | Agent 读取负担增加，推理依据失真。 |
| P6 | 局部通过替代整体验收，修复或重构遗漏原判据 | 完成声明缺乏充分证据。 |
| P7 | 决定、版本、进展和证据无法可靠交接 | 中断后重复执行或要求用户重述。 |
| P8 | 固定流程、冗余材料及无效进度通知 | 协作成本超过实际价值。 |
| P9 | 设计约束、授权和实际执行脱节 | 架构难以核验，交付与运行操作越界。 |

## 实现策略

### 工作流策略

| 编号 | 策略 | 约束 |
|---|---|---|
| S1 | 按影响确认 | 需求与方案分别确认，沿用有效确认；关键变化重新对齐。技术事项仅在实质影响用户结果时提交决策，并说明影响与选项。 |
| S2 | 前置执行约定 | 集中明确目标、范围、排除项、约束、验收、授权终点及已知待决事项。技术未知可在授权内探索，无须预先穷尽；触及关键约束时重新确认。 |
| S3 | 分别闭环 | 需求交付可包含必要局部结构调整；重构保持已确认业务需求与行为。跨类别发现不自动扩围；独立重构成为必要前提时，提交依赖、影响与选择供用户决定。按目的和影响区分任务。 |
| S4 | 持续推进 | 自主实施、调整、验证、修正及接续已授权阶段。关键预期变化、授权不足或无法自主解决的阻塞触发决策；仅暂停关联事项及其依赖。 |
| S5 | 原位维护知识 | 已确认结论归并至唯一正文，同步直接受影响的内容与引用。清理失效、重复和无用内容，保留有效条件、例外与追溯关系，保护范围外资产；局部维护不自动扩为全仓整改。 |
| S6 | 按证据完成 | 结论绑定判据、版本、环境和覆盖范围；失败按原判据修正复验。各类验证分别证明其覆盖，原型与正式运行分别取证；未执行或缺少必要人工反馈的事项保持待验。 |
| S7 | 保持可恢复状态 | 保存有效决定、版本、进展、证据、剩余项、阻塞及恢复条件；接续时核对适用性，避免重复确认、重复执行或复用失效证据。 |
| S8 | 按需组织、静默执行 | 流程、材料和检查与交付目标相称。纯讨论无需正式模板及架构门禁；独立实施工单可按自身判据执行，不以完整 Blueprint 为前提。重构阶段以已有蓝图为前提，复用项目长期 Review 矩阵，按确认范围派生本轮审查任务。减少无决策价值的通知，支持状态查询，及时呈现关键阻塞、预期变化和最终结果。 |

### 三层架构

采用**主任务 → 技能 → 角色**的职责组织关系，承接 S3、S4、S8。

| 编号 | 约束 | 职责与边界 |
|---|---|---|
| I1 | 职责单一 | 主任务面向用户、组织交付、协调阶段；技能负责单一交付目标的阶段闭环；角色负责专业执行与产物。主任务不重复技能流程，技能不重复角色执行规则，角色不组织跨阶段工作。 |
| I2 | 同层禁止依赖 | 技能之间、角色之间均不直接调用、调度或交接，由共同上层组织协作。允许复用上层提供的合格产物和证据；不得要求同层单元先运行，或依赖其内部流程。 |
| I3 | 上下位禁止倒置 | 上层确定目标、范围与完成要求；下层执行并回报结果、缺口和建议，不得重定义目标、扩大授权或指挥上层。阻塞回报不构成倒置。 |

三层架构不要求严格逐层调用。主任务可直接执行对象和结果明确、操作本身即授权终点的局部操作，也可直接委派角色；两类路径均须保留适用的阶段闭环。具体 Skill 清单、角色数量、调度实现及模板形式遵循上述约束。

## 关键取舍

- S1、S2、S4：前置关键决定，授权内细节由 Agent 持续完成；关键结果变化才重新对齐。
- S3：需求交付与架构重构分别闭环，必要局部调整不自动扩大目标；独立重构依赖交用户决定。
- 重构知识按范式与通用 checklist 预置，项目规范及按子系统／模块／组件组织的 Review 矩阵在运行时形成。矩阵由重构技能维护，蓝图保留固定链接，初始内容和结构变化同步更新须展示确认。本轮范围确认后取证，初审结果形成重构工单，实施和两类复核沿原检查项闭环；矩阵的长期约束与批次事实分别维护。
- S5、S7：当前知识唯一且可恢复，保留历史证据的版本语境，不把历史结论当作当前依据。
- S6、S8：证据与流程应匹配交付目标；减少无效材料和通知不降低完成标准。
- I1～I3：分层明确职责而不强制逐层调用；共同上层组织同层协作，直接路径保留适用闭环。
