# 架构落地一致性 Review

审查目标是架构落地，包括适用架构规则的执行；不审阅 Spec 内容，不检查业务需求覆盖或进行业务行为验收。业务模块仍按职责、状态所有权、依赖和接口等架构约束检查。

前置：sdd-doc 已保证本轮蓝图及关联文档一致，审查依据明确。发现文档冲突时暂停受影响结论，交回 sdd-doc；需要新设计取舍时交回讨论。

1. 确定目标模块、实现快照及相关跨模块关系。从[架构规范](../../sdd/references/architecture-rules.md)、Blueprint、适用 ARC 和[观测基线](../../sdd/references/observability-baseline.md)识别检查范围与适用项；未检查项保留待检查状态。
2. **逐项检查并接续**：对当前检查项，对照源码、调用链、配置和运行装配检查职责、状态所有权、依赖、接口、数据流及异常时序，记录依据、位置、覆盖、快照及初审事实。符合直接 PASS；不适用说明理由，不计通过。范围内的跨模块架构关系须实际检查，可执行约束使用相应检查，语义判断提供实现证据，不能只检查目录或已列 ARC 而遗漏适用约束。
3. 当前项有可修复的实现偏差时，无需等待全范围初审或总 Gate：本流程判断是否需要重构、对齐哪些 ARC，明确检查项编号、偏差、整改目标、实现位置、预期结果和业务行为保持边界，默认自动接续 sdd-imp；用户明确只审不修时遵守。缺失验证代码也交 imp，修复方案由 imp 在其 Plan 中维护，架构依据与映射留在 Review，不要求 imp 自行读取 Blueprint 或判定架构。复杂整改可拆多个 Task；存在依赖或共享修复时可合批，一个 Task 可关联多个检查项，但各项分别复核。逻辑逐项闭环不要求每项新建 Agent 或重复加载，批次与原执行者复用按[执行协作](../../sdd/references/delegation.md)。
4. imp 完成后由原审查者复核当前项及受影响跨模块关系，并核对业务逻辑保持的验证证据；需要集成验证时按本次整改范围执行，不扩展为业务需求验收。复核通过才关闭该项并继续其他检查项；失败则带检查项及增量证据返回对应 Task，继续整改和复核。证据缺口由审查执行者补查；文档冲突交 sdd-doc，设计待决交回讨论。修复保持业务逻辑和已确认架构不变；涉及业务规则、可观察业务行为、外部契约或架构决定变化，或无法确定影响时，仅暂停受影响项及其依赖项，其余可执行项继续，记录具体阻塞及恢复条件；不放宽 Rule 或修改蓝图迁就实现。外部操作仍沿用实际授权。
5. 调用 sdd-doc 按 [Review 模板](../../sdd/assets/review_template.md)维护同一记录：在每个检查项下保留初审、Task 引用、处理与复核证据及当前状态，不另建独立差异清单或问题生命周期；修复结果只引用 Plan／Task，不复制方案。随批次记录，不将全部初审落盘作为启动已授权修复的前提。未受影响证据经影响分析后复用，Gate 仅汇总全部适用检查项，全部在所声明同一快照通过才可报告 PASS；FAIL 是结果，不停止授权内修复。

审查执行者不修改代码、设计或正式文档；Main 按上述步骤接续 sdd-doc 与 sdd-imp，不要求固定角色轮转。架构 Review 记录作为专用报告，Status／Plan 引用该记录及实际 Gate，不重复归并另一份测试报告。需求行为验收由 sdd-test-loop 承担。需要用户判断时按[项目职责](../../sdd/references/sdd-repository-governance.md)沿场景时序展示证据。独立审查按[执行协作](../../sdd/references/delegation.md)安排，自查不得称为独立审查。

例：蓝图规定只有服务层写订单状态，发现界面层直接写库。引用蓝图条款和实际调用链报告偏差，交给 sdd-imp；不修改蓝图使实现合规。
