# 对齐意图与沟通规范

意图对齐按[呈现与确认](#呈现与确认)进行。人工审阅和验收按[证据与状态](#证据与状态)呈现结果、提供证据并记录用户判断。决策与授权边界见[仓库治理](sdd-repository-governance.md#人与-agent-协同及决策权限)。

## 沟通语言

从用户视角说明目标、操作和可见结果。需求讨论优先使用产品术语，方案讨论优先使用架构术语表达职责、边界、协作及取舍。沿用项目已有概念，未定义或有歧义时先澄清含义。

技术方案默认表达至蓝图与时序层级，用户明确要求时按问题范围展开实现细节。影响决策的实现问题转化为行为变化、边界、取舍和可观察后果，重要风险、代价及未验证项随结论说明。正式工程文档的内容仍按相应规范和模板维护。

## 呈现与确认

变更前必须与用户对齐意图，禁止跳过。先判断已有确认是否覆盖当前要解决的问题和预期结果。已覆盖的部分直接沿用。只针对待确认的事项，按[沟通语言](#沟通语言)和[内容视图选择](#内容视图选择)，在同一次回复中说明问题和预期结果，呈现足以判断的视图，明确请用户判断什么，并请用户确认。图表以渲染后的视图呈现，原型可直接操作，随确认请求展示或提供可访问入口，并复用已有有效视图。需求与方案都待定时，先对齐需求，再讨论方案。用户确认即完成对齐，由对应 Skill 接续。

回复前由 Agent 核对术语、意图与细节层级，以及重要影响是否完整，发现偏差先改写。语义判断由 Agent 完成。

## 内容视图选择

按当前需要核对的问题区分需求与方案，选用下表对应视图。图中只展开本轮涉及的对象和变化。

| 场景 | 核对内容 | 专业视图与必要内容 |
|---|---|---|
| 需求 | 谁使用系统、要完成什么、能力范围是什么 | **UML 用例图**，标明参与者、用例和系统边界 |
| 需求 | 用户如何操作、看到什么、异常如何处理 | 按[原型适用范围](prototype.md#适用范围)提供**可操作 HTML 原型**，走通相关关键操作和异常路径。CLI、库及维护任务用**场景对照表**展示输入或操作、预期结果和判断点 |
| 需求 | 业务流程如何分支或汇合 | **活动图**，标明条件分支、并行步骤及汇合条件 |
| 需求 | 业务对象允许哪些状态变化 | **状态机图**，标明状态、触发事件和转换条件 |
| 方案 | 组件负责什么、谁拥有状态、如何依赖 | **组件图＋职责表**，标明职责、状态归属、边界及依赖变化 |
| 方案 | 参与方如何协作、失败后怎样处理 | **时序图**，展示关键消息、先后关系、超时、迟到结果及恢复处理 |
| 方案 | 服务运行在哪里、跨越哪些网络和信任边界 | **部署图**，展示运行位置、连接及边界 |
| 方案 | 数据如何组织 | **ER 图**，展示实体、关系及约束 |
| 方案 | 规则或文档怎样调整 | **条款前后对照表**，对应原条款、拟定条款、适用范围和执行行为变化 |

方案视图标出推荐方案及其取舍，已有设计的调整展示前后差异。组件图表达逻辑职责，部署图表达运行位置。正式架构文档的表达要求见[蓝图模板](../assets/blueprint_template.md#架构表达与判定)。

## 证据与状态

审阅和验收沿用已确认的需求场景或方案视图，对照预期与实际结果，标明差异、证据及未验证项。产品验收在约定环境操作实际集成版本，对照适用原型与已确认指标，按范围核对结构、业务状态、交互、权限及错误路径。展示操作结果和后续动作能否继续，样式与像素还原排除在符合性门禁之外。原型审阅注明模拟范围和实际验证程度，版本与访问要求遵循[原型规则](prototype.md)。

测试使用**覆盖矩阵**，沿用 Quickstart 场景和 AC 编号，关联适用数据、判断点、通过／失败／未测／阻塞及证据。架构审阅将符合、偏差和未验证标到相关视图元素。规则、文档及工具维护对照实际差异和检查结果。详细事实按仓库治理归入各自权威记录。

任务交付先报告完成结果、关键差异、验证结论和未完成项，附详细记录入口。影响判断的重要风险、代价和未验证项在摘要中说明，完整清单和报告在需要判断或用户要求时展开。

视图入口对应本次内容和版本，访问未核验或证据缺失时注明缺口及其影响，相关内容保留待确认状态。原型、模拟数据与模拟结果明确标识。用户明确确认后记录已确认范围，并关联对应视图及版本。
