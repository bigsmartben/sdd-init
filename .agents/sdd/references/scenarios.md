# 六类场景提示

需求和架构讨论保持宽松，不要求按固定流程或架构规范检查候选方案。以下提示用于普通 Chat 按需参考和 sdd-doc 固化时定位内容。只选影响当前结论的问题；不是必填问卷或审批门禁。场景提示分析问题，最终按内容层级及权威归属确定落点，同一任务可涉及多个实体。讨论结果进入对应实体，不保存另一份需求或 Plan。

| 场景 | 参考输入与关键问题 | 固化去向 |
| --- | --- | --- |
| 新需求／产品定义 | 谁在何种场景遇到什么问题？现状与期望、目标、规则、范围、异常、适用原型及可验证结果是什么？ | 高位用例、体验与验收维度归 Blueprint；具体行为及 AC 归 Spec |
| 验收反馈／缺陷 | 哪个版本、环境与操作？预期和实际如何不同，怎样复现、影响谁、有什么证据、怎样验证修复？区分实现违反已有要求与确认改变要求，事实与猜测分开。 | 独立 Issue 记录维护问题事实、承接者、状态及复验关闭，测试报告记录批次执行事实，Status／Plan 引用报告与 Issue；只有确认需求变化才更新 Spec；修复方案归 imp 的 Plan（Task 清单），Issue 只引用 Task |
| 需求变更 | 当前需求及变更原因是什么？改什么、保留什么，影响哪些行为、原型与验收项？ | 按变更层级更新 Blueprint 或 Spec，必要时更新原型引用 |
| 架构设计／变更 | 需求、现有架构和实现事实是什么？职责、接口、状态归属、依赖、约束及取舍如何确定？ | 职责、边界与不变量归 Blueprint；接口语义归契约，交互顺序及异常分支归时序 |
| 重构要求 | 实现与架构有什么差异，为什么重构？目标、范围、保持的行为、影响和验证方式是什么？ | 按内容层级归 Spec／Blueprint／契约／时序，验证结果归测试报告，实施 Plan（Task 清单）归当前任务或已有计划载体 |
| 实施 Plan | 已确认需求、适用架构与当前实现是什么？改哪里、分哪些步骤、有什么依赖、如何验证、有哪些实际风险？ | 当前任务或已有计划载体中的 Plan（Task 清单） |
