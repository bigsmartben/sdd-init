# SDD 工程协作职责

## 范围与需求

适用于本仓库维护的 SDD 指令、共享规则、模板与安装载荷。

- FR-001：具体需求以对应 Spec 文件为唯一正文，维护详细行为、业务规则、适用条件、异常及可执行 AC。Blueprint 定义高位抽象层级的全产品用例、关键体验、验收维度及架构职责与边界，不涉及具体需求细节；Spec 细化并追溯适用的 Blueprint 用例与验收维度，同一层级条款不重复维护。Plan 与 Task 合并为同一份可执行清单，按依赖推进并记录完成证据。
- FR-002：分发资源服务于需求整理、架构表达、实施、局部自验、需求验收和 Git 交付；初始化与安装校验按这些职责维护资源清单。
- FR-003：sdd-commit 负责本地 Git 及 GitHub／GitLab 仓库协作，覆盖分支准备、提交、推送、远端 Issue 创建与更新、PR／MR 创建与更新、检查跟进及合并；支持平台托管与企业／自托管实例，按实际 remote、仓库元数据及已有认证选择连接工具、CLI 或 API。用户指定交付终点后，Agent 自主完成该终点必需且属于授权范围的步骤，不要求用户手动操作仓库或逐步授权；已有授权沿用，仅目标歧义、范围实质变化、认证或权限缺口等必要情况交用户处理。未指定终点仍只完成本地提交，实施或文档写入不自动触发远端操作，创建 PR／MR 不隐含合并。远端 Issue 只承载协作摘要及 Spec／报告／独立 Issue 引用，不替代需求、验证或问题处理记录正文，也不因提交代码自动新增。操作前查重并复用本任务已有对象；保护无关工作区与暂存差异，合并遵循最新提交、适用检查、审批及分支保护。超时或结果不明先查询实际状态再决定重试；返回对象链接、提交与分支及实际交付状态，区分已推送、已创建、等待检查／审批、排队／自动合并与已合并。
  分支与推送前须检查远端同步：新建用于远端交付的分支前及每次 push 前，fetch 实际源仓库和目标仓库所需引用，分别比较本地任务分支与远端同名分支、最新目标分支（如 main／develop）。新分支无 upstream 或同名远端分支仍须检查目标基线；除已确认固定基线外，落后或分叉先按项目策略安全整合、完成受影响检查再推送。普通交付授权包含必要 fetch、快进及不改写历史的同步 merge；保护无关未提交和预暂存内容，不以自动 stash、reset、强推或无参数 pull 代替判断。获取失败、历史不足、冲突未解或状态不明时不继续 push；操作前后远端再变化时重新比较并处理，持续变化返回具体阻塞。同步记录本地、远端任务及目标 SHA，push 成功不代表已基于最新主线。

- FR-004：历史证据、来源链接及第三方依赖地址保留原义与版本归属。

- FR-005：实施指令与输出模板分离：sdd-imp 负责依据实际需求和代码拆分、排序、执行及调整任务，plan_template.md 固定 Plan 的输出结构。Plan 以 Task 清单承载实施内容，包含目标与依据、改动范围、依赖、完成条件、状态、实际证据及交付核对；在当前任务或已有计划载体中维护同一份正文。简单任务允许一项，不强制固定阶段。已授权实施仅保留生成 Plan 后直接执行的路径，不设置计划审批阶段；实质范围或设计变化仍交回相应决策。

- FR-006：sdd-doc 负责确认来源取证、对象路由、原位归并、关联影响分析及写后语义核对；模板负责输出结构、字段含义和填写约束，不授予设计、执行或验收权限。按变更对象和语义影响读取适用上游，不以章节结构是否变化决定是否核对。覆盖需求、蓝图、契约、时序、原型、测试报告、独立 Issue、Plan、指南及执行事实；缺陷事实与需求变更分别归位。正式时序只维护设计，Review 沿用步骤引用测试报告中的证据。

- FR-007：文档输出模板统一使用 `*_template.md` 命名，实际项目产物沿用自身名称；规则目录、说明和安装片段不冒充输出模板。正式时序只保留 `sequence_template.md`，不分发重复导航模板。验证记录统一为报告，通常使用 test_report_template.md，架构 Review 使用 review_template.md 专用结构，由 sdd-doc 根据真实执行证据维护；Issue 使用 issue_template.md 独立维护问题生命周期；不授予测试执行权限，实际验证结果归报告，Status／Plan 引用报告并记录进度。

- FR-008：coder 负责实现、测试及自动化脚本的编写修复，并通过必要的定向单元测试、构建和类型检查完成开发局部自验。validator 负责集成验证、自动化验证（包括 UI 自动化、浏览器操作和 computer-use）、架构 Review 及整改后的复验，检查断言对目标行为的证明能力并报告覆盖缺口；不修改实现或测试代码。自动化是验证手段，不排除 coder 执行定向单测。需要集成环境、跨组件交互或 UI 操作证明的行为交给 validator；Main 按任务范围协调与汇总。

- FR-009：测试报告记录一次测试活动，适用于方案可行性、开发局部自验、集成验证、业务需求验收及复验，注明实际类型；架构一致性使用 Review 专用报告。报告必备内容为测试目标与依据、范围与计划、环境、准备与数据、执行与覆盖汇总、测试明细、关联问题与影响、测试结论与限制。章节不得静默省略，不适用说明原因，缺失注明缺口及影响；计划与标准取自已确认安排，不能补造。范围内未执行项保留并标未测或阻塞；统计与明细一致，用例通过率不替代需求覆盖，结论须有证据支持。报告只引用 Issue 与本轮影响；复验作为新批次保留，不把历史失败改为通过。Quickstart 维护操作与预期，Status／Plan 引用报告。场景按内容层级分流，不按任务名称固定落点；原型引用与确认记录由 documenter 维护，原型代码归属按 FR-010 执行；通用时序不预设业务专属概念。

- FR-010：HTML 原型用于需要界面操作的交互与体验确认；后端、库、CLI 或维护任务按实际接口、行为或变更内容确认，无此需要时不要求制作 HTML 或填写原型章节。HTML 原型统一归测试代码资产，由 coder 编写修复，validator 验证交互与业务状态，documenter 记录入口、版本、需求关联、确认及实际验证结果。原型以后续直接复用为目标，沿用项目实际架构；实现对应需求时将选定代码迁入或提取到正式模块，移除模拟装配并补齐真实接口、权限与异常处理。正式运行依赖链与装配不得直接或间接启用原型测试运行器，必要测试与夹具保留在测试资产中。

- FR-011：Main 与角色交接采用最小充分上下文：目标与完成条件、授权和归属边界、必要来源引用，按职责补充输入；角色返回结论、增量差异、可复查证据与未完成项。续派只传变化，复用有效证据，不复制完整上下文、日志或报告，不强制角色轮转或新增交接文档；压缩不得丢失关键约束、失败、版本与覆盖范围。

- FR-013：提供随项目分发的只读文档校验 CLI，由 sdd-doc 在写后对明确选定的文件或目录执行。机械检查覆盖 UTF-8、代码围栏、标题层级提示、表格列数、受支持的编号声明重复、本地链接及 Markdown 锚点；输出文件、行号、规则码、级别和问题，支持文本／JSON 及稳定退出码。CLI 不访问网络、不修改文档，不推定语义一致或验收通过；未支持的语法和未检查范围明确说明，语义判断仍由 Agent 完成。

- FR-012：仓库治理统一承载 SDD、repository、governance 所指的研发治理，作为上位规范负责人与 Agent 协同、决策与授权、流程接续、工程资产及文档权威、完成与交付规则，正文为 sdd-repository-governance.md。下位架构规范 architecture-rules.md 定义可落实到系统与代码并可审查的架构原则、范式和约束；开发者与验证者的协作归治理，正式实现与测试实现的依赖、装配和运行隔离归架构。需求和架构讨论保持宽松，不设固定流程、模板填报或架构规范符合性门禁。用户明确要求写入 Blueprint 时，sdd-doc 按已确认内容及模板整理并检查内容一致性，不依赖架构规范或观测基线、不自动补齐规范映射。架构规范作为 Review 的输入，与已确认 Blueprint 一起检查实现；Review 聚焦架构落地一致性及架构规则执行，不审阅 Spec 内容，不检查业务需求覆盖或进行业务行为验收。业务模块仍属于架构检查对象，按职责、状态所有权、依赖和接口等架构约束判定；映射与遵循证据归审查记录。Blueprint 表达项目设计，ADR 记录具体取舍，Review 检查遵循；不新增设计或 Blueprint Skill；表达方法和工作流程不充当架构规范本体。通用架构原则限于已确认条款，不额外引入 SOLID 等原则。

- FR-014：架构规范按“通用约束＋专项约束”组织：通用约束覆盖模块职责、接口、依赖方向、状态权威、运行边界、业务／基础设施分工及正式／测试隔离；专项约束覆盖可观测性、日志、环境、脚手架、测试工程与自动化五项。通用约束是架构规范内部章节，不另立系统架构规范；目标项目的实际模块、协作与部署由 Blueprint 表达。业务禁止依赖日志、指标等观测数据及观测工具实现需求功能，业务状态、流程和计费由业务接口与权威数据承载。观测不得拥有或修改权威业务状态，可记录业务接口提供的状态事实或快照供观测与评测读取，仍遵守日志保存边界。日志规范覆盖事件至持久化、轮转、保留及失败处理，项目日志契约明确必记事件清单、触发条件及必需字段；环境规范覆盖各环境拓扑、运行时、依赖、配置、网络、存储、数据与隔离；脚手架依据已确认架构生成并随架构变化检查同步，按职责与依赖语义匹配。测试规范覆盖层次、依赖替代、真实／模拟条件、契约、确定性、数据生命周期、框架配置、断言、并行、超时／重试、本地与 CI 入口及诊断；回归是验证目的，不另造第三套框架。工程资产分类及落点由 SDD 仓库治理唯一维护，架构规则只引用。Rule、项目设计、框架／脚手架及遵循证据分别承担约束、落实、生成／运行及证明职责；通用原则的边界遵循 FR-012。

- FR-015：可行性讨论产生的验证代码、Demo 功能代码、同场景不同算法的对比测试，以及候选技术路径探索与迭代代码，统一属于测试代码并按测试工程规范维护，保留场景、算法／路径、版本与结果的关联。功能完整、接入真实服务、验证通过或方案被选中不自动改变资产归属。已确定正式方案后的正常产品开发属于正式实现；测试代码正式采用须迁入或提取、移除模拟及实验装配并验证。资产分类由仓库治理唯一维护，架构规范引用分类并规定运行隔离，覆盖正式运行依赖链和装配的直接、间接依赖、动态加载及配置启用；测试调用正式模块仍允许。

- FR-016：业务领域负责业务规则、权威状态和流程；运维／基础设施统一承载技术流控、链路追踪、指标监控、运行诊断和进程唤醒、保活、重启、故障恢复，业务通过明确接口使用而不重复实现。业务配额与唤醒词识别等产品能力按业务语义归属，不按名称归入运维。观测保持非侵入；技术流控和进程生命周期管理按明确接口、权限及策略实施运行控制，不混用观测隔离要求，不改变业务权威归属。

- FR-017：工程资产按系统用途分类：正式程序的业务代码、通用技术模块及配套运行配置归正式实现，具体环境值由环境配置管理；部署、排障、备份和恢复操作脚本与工具归运维，测试专用连接配置归测试。架构中的基础设施职责不直接决定资产目录。探索验证以已明确的假设、候选方案、比较目标和判断指标为依据，实施入口引用该统一依据并支持已授权探索目标；测试技术规范负责原始输出、诊断及关联标识，正式报告和结论归仓库治理。现行指令按语义删除泛化的如实报告、不虚构、不夸大结果、缺少证据不判通过和局部成功不代表整体成功等 Agent 默认准则，不搬移至其他文档；范围覆盖治理、架构 Rule、专项规范、Skills、角色、模板、初始化片段、说明、工具生成文本及相应检查。保留 SDD 特有的职责分工、授权边界、产物权威、执行独立性、Review／Test Gate 判据和人工确认条件，以及系统状态、持久化回执、观测与业务隔离、正式与测试装配隔离等技术约束；工具能力边界及历史失败、未验证状态保留。

- FR-018：业务代码中，所有业务实体的持久化必须落库；日志、普通文件或仅驻留内存的缓存不能替代数据库中的业务实体持久化。该规则归架构通用约束，数据库类型、数据模型、写入时机、持久化完成判据及失败后的业务行为由项目设计明确，事务、重试与恢复机制不预设，业务状态权威仍归业务领域。

- FR-019：在现有文件内压缩治理、文档写入及观测重复条款，不通过拆文件转移篇幅；职责、授权、条件、例外及 Gate 判据保持完整，执行步骤和模板字段引用现有权威来源。按同一统计范围记录压缩前后汉字及非空白字符数。

- FR-020：架构 Review 使用 review_template.md 记录范围、检查项、依据、快照、结果、gap、修复状态与复核证据，由 sdd-doc 初审后落盘并持续更新同一记录。修复方案由 sdd-imp 自行推理并在其 Plan 维护，Review 仅引用 Task。Review 默认自动接续 imp 修复并返回复核，明确只审不修时遵守；修复保持业务逻辑及已确认架构不变，涉及业务行为、外部契约或架构决定变化、影响无法确定时暂停该项返回讨论。证据缺口由审查者补查，缺失验证代码由 imp 编写；复核通过才关闭 gap，保留初审和历史版本，Status／Plan 引用专用记录，不重复通用报告。模板随分发安装并校验缺失保护。

- FR-021：独立 Issue 记录是问题事实与处理状态的唯一正文，默认 docs/issues/<问题编号>.md，已有项目沿用实际映射；测试报告不承载问题处理流水。每项使用项目内稳定唯一编号，关联场景／AC、已有依据、复现及预期实际差异、证据与版本、影响、类型、承接者、修复 Task、处理状态及阻塞恢复条件；逐项结果引用 Issue，未测或阻塞不自动判为实现缺陷。sdd-test-loop 提供发现、交接及复验事实，sdd-doc 按 issue_template.md 落盘并持续更新同一问题记录，按 test_report_template.md 分别归并发现与复验批次事实。实现缺陷及缺失测试交 sdd-imp，证据缺口由验收执行者补查，文档矛盾交 sdd-doc，需求缺口或变更交回讨论；修复与复验沿用实际授权，不因记录 Issue 自动触发实施。imp 在 Plan 中自主维护修复方案并关联 Issue，返回改动、修复版本、局部自验证据及待复验范围，Issue 只引用 Task。修复完成记为已修改待复验，sdd-test-loop 复验通过才关闭对应缺陷；失败继续使用原编号，保留初次发现和历次修复、复验版本及证据，阻塞项注明恢复条件，所需人工确认未取得时保持待确认。非代码问题按对应处理结果和验收执行者核验记录闭环。Status／Plan 引用报告及 Issue，不复制事实与状态正文；架构 Review 继续使用专用 gap 记录。

- FR-022：新增项目技能 sdd-deploy，按用户部署、启动或重启请求执行，未指定环境默认 dev，支持明确指定的其他环境，不随代码修改完成自动触发。落地前先探测本地操作系统、工具与运行时、连接上下文、既有服务、端口和依赖；远程部署另核对目标环境。dev 优先 Docker Compose，沿用项目明确部署规范与既有配置，不绑定平台发行版、固定路径、个人仓库或集成／CI 拓扑。按实际环境验证挂载，共享依赖兼容才复用，保持项目数据与凭据隔离及持久化数据，避免影响其他项目。遵循项目及目标环境规范，自主完成环境搭建、依赖与配置准备、环境排障修复、必要构建部署和服务就绪检查，不增设授权或审批流程。优先复用并更新、重启既有服务，保持服务标识、端口和运行位置一致，避免重复实例及冲突；首次部署创建必要服务，已健康运行的启动请求复用现状。按项目既定副本与更新策略管理实例，识别归属并保留其他服务。失败先诊断与查询实际状态，按恢复策略修复，持续无进展时返回具体阻塞；只在必要信息不可获取或目标歧义时澄清。返回环境、运行版本、服务状态、访问与日志入口及环境处理结果。Main 默认执行，现有五个角色不增加；实现修复、业务验收、文档归并与 Git 交付沿用对应技能。安装清单、元数据、分发和导航同步更新。
