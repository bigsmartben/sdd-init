# SDD 工程协作职责

## 范围与需求

适用于本仓库维护的 SDD 指令、共享规则、模板与安装载荷。

- FR-001：具体需求以对应 Spec 文件为唯一正文，维护详细行为、业务规则、适用条件、异常及可执行 AC。Blueprint 定义高位抽象层级的全产品用例、关键体验、验收维度及架构职责与边界，不涉及具体需求细节；Spec 细化并追溯适用的 Blueprint 用例与验收维度，同一层级条款不重复维护。Plan 与 Task 合并为同一份可执行清单，按依赖推进并记录完成证据。
- FR-002：分发资源服务于需求整理、架构表达、实施、局部自验、缺陷评估与归因、面向用户功能的集成测试、提示词审查和 Git 交付；初始化与安装校验按这些职责维护资源清单。用户级安装器校验已安装目录时，跳过清单内 Python 源文件对应的未登记 `__pycache__` 字节码，校验其余已安装文件及全部新分发资源。
- FR-003：sdd-deliver 统一承接 Git 交付与 FR-022 的部署、启动和重启，支持单独请求与同一请求串联。Git 交付覆盖本地分支、提交、推送、GitHub／GitLab Issue、PR／MR、检查跟进及合并；支持平台托管与企业／自托管实例，按实际 remote、仓库元数据及已有认证选择连接工具、CLI 或 API。用户指定交付终点或组合路径后，Agent 在已有授权内自主完成必要步骤；仅目标歧义、范围实质变化、认证或权限缺口等必要情况交用户处理。请求提交或交付本地改动而未指定后续路径时，完成授权范围内的本地提交，返回分支和 SHA，列出适用的下一步及结束选项，等待用户选定再执行。明确只需本地提交时返回回执即结束。组合路径按已指定的顺序或项目约定执行；部署依赖前序 Git 结果时，确认该步骤完成，以回读的提交或对应制品确定部署版本，分别返回实际交付与运行结果。创建 PR／MR 不隐含合并。远端 Issue 只承载协作摘要及 Spec／报告／独立 Issue 引用，不替代需求、验证或问题处理记录正文，也不因提交代码自动新增。操作前查重并复用本任务已有对象；保护无关工作区与暂存差异，合并遵循最新提交、适用检查、审批及分支保护。超时或结果不明先查询实际状态再决定重试；返回对象链接、提交与分支及实际交付状态，区分已推送、已创建、等待检查／审批、排队／自动合并与已合并。
  分支与推送前须检查远端同步：新建用于远端交付的分支前及每次 push 前，fetch 实际源仓库和目标仓库所需引用，分别比较本地任务分支与远端同名分支、最新目标分支（如 main／develop）。新分支无 upstream 或同名远端分支仍须检查目标基线；除已确认固定基线外，落后或分叉先按项目策略安全整合、完成受影响检查再推送。普通交付授权包含必要 fetch、快进及不改写历史的同步 merge；保护无关未提交和预暂存内容，不以自动 stash、reset、强推或无参数 pull 代替判断。获取失败、历史不足、冲突未解或状态不明时不继续 push；操作前后远端再变化时重新比较并处理，持续变化返回具体阻塞。同步记录本地、远端任务及目标 SHA，push 成功不代表已基于最新主线。

- FR-004：历史证据、来源链接及第三方依赖地址保留原义与版本归属。

- FR-005：实施指令与输出模板分离。sdd-coder 依据共享实施规则承接明确且获授权的上游工单，覆盖已确认需求与架构变更、Bug 修复、Review 整改、缺失测试及已授权探索。上游在派单前定义交付目标、范围、通过判据及可执行的验收计划与方案。验收计划记录验收项、执行者和执行条件；方案记录前置条件、步骤、观察点及可观察通过判据，可引用已存在的可执行内容。用户功能、用户可感知的缺陷及用户可感知的非功能指标从用户实际操作或调用入口定义，指标引用已确认的测量条件、统计口径和阈值。架构 Review 从开发者视角按 FR-020 定义复核方案。工单同时涉及用户侧和架构判据时，分别引用各自的判据、执行者与证据。缺少必要依据时交对应上游补齐，记录受影响项及恢复条件，继续其他已就绪且获授权的事项。sdd-coder 根据上游方案制定局部自验。需对齐需求或形成需求工单时按 FR-029 接续。架构变更交付可引用已确认决定并明确可执行目标。Bug 工单沿用原 Issue，Review 整改沿用原检查项，分别见 FR-021 和 FR-020。依据已确认的目标、预期结果和实际代码制定足以开工的方案，标明影响方案或顺序的未知项，验证后再据此推进。需确认的实质取舍附可行选项、证据和影响。sdd-coder 在同一份 Plan／Task 自主管理方案与任务。Plan 承载目标与依据、改动范围、直接依赖、完成条件、状态、实际证据及交付核对。需求实施按 Spec 场景、AC 和已确认优先级拆分，将相关代码、契约、数据约束及验证映射到 Task。其他场景按其上游目标和完成条件拆分。多 Task 的 Plan 由直接依赖导出无环的执行顺序，标出共用前置及可并行项。前置条件满足且改动与共享状态不冲突时才可并行。有可单独验证的交付批次时，记录用户目标或场景、相关 Task、可观察结果和局部验证入口。简单任务允许一项，批次按实际交付组织。plan_template.md 固定输出结构，沿用当前任务或已有计划载体。阶段确认和实施授权齐备后按 Plan 执行，按已确认优先级推进就绪项，核对实际环境和依赖。约定 TDD 或需以测试证明待修缺口时，先确认测试因预期缺口失败，再实现并重跑。以代码单测为局部自验的重点，按工单性质和影响补充必要的定向检查、构建或类型检查。按 Task 和适用批次核对结果、覆盖及版本证据。Task 达到自身完成条件、局部自验通过、证据齐备且该项失败或阻塞均已解决时标记完成。本轮仅要求实施及局部自验时可据此交付结束；工单约定用户验收时，按上游方案实际取证，需要真实组件协同时按工单范围定向取证，架构整改按 FR-020 复核，Bug 关单按 FR-021 判定。交付实际改动、版本、局部验证入口和证据，逐项关联已覆盖与仍待验证的判据，并提供后续验收所需的上游方案引用、运行入口及已知准备条件。Main 核对本轮所有约定的验收项。记录失败并修复复验。未满足的前置条件阻塞其依赖项，其他已就绪且获授权的任务继续。按代码事实及验证结果原位更新方案、任务和改动位置，保留稳定编号与有效证据。问题、预期结果变化或出现需确认的实质设计取舍时，按 FR-025 对齐受影响项。coder 不主动读取 Blueprint，不承担 ARC 对齐、Code Review Rules 检查或自行扩展架构重构。Blueprint／ARC／Code Review Rules 不作为 coder 的必读输入、实施约束或完成条件，架构符合性、整改目标及复核归 Review。

- FR-006：需求到实现阶段由获授权的执行者归并 Spec 和实际证据。其他任务的正式文档归并以 sdd-documenter 角色为入口，承接原 sdd-doc 技能的职责与完整写入流程，不再分发 sdd-doc 技能。输入为已确认结论或真实执行证据及授权写入范围，纯讨论不触发落盘。按 FR-011 安排执行者，Main 直接承接时沿用同一文档写入规则。sdd-documenter 负责确认来源取证、对象路由、原位归并、关联影响分析及写后语义核对；模板负责输出结构、字段含义和填写约束，不授予设计、执行或验收权限。按变更对象和语义影响读取适用上游，不以章节结构是否变化决定是否核对。覆盖需求、蓝图、契约、时序、原型、技术调研与选型报告、测试报告、独立 Issue、Plan、指南及执行事实；缺陷事实与需求变更分别归位。技术调研与选型报告按需使用同一份模板，按问题记录比较标准、候选方案与证据、选型建议及确认结果；已确认的架构决定归 Blueprint 或项目已有 ADR，实测结果引用对应测试报告。设计文档写入时发现关联 Code Review Rules 可能过时，在回复中简短提醒，由用户决定何时更新；不新增全量检查、自动维护规则或审批。正式时序只维护设计，Review 沿用步骤引用测试报告中的证据。

- FR-007：文档输出模板统一使用 `*_template.md` 命名，模板的标题、字段、占位符和填写说明统一使用英文，sdd-documenter 的产物类型名称与模板一致；实际项目产物沿用自身名称。规则目录、说明和安装片段不冒充输出模板。正式时序只保留 `sequence_template.md`，不分发重复导航模板。验证记录统一为报告，通常使用 test_report_template.md，架构 Review 使用 review_template.md 专用结构，由 sdd-documenter 根据真实执行证据维护；Issue 使用 issue_template.md 独立维护问题生命周期；不授予测试执行权限，实际验证结果归报告，Status／Plan 引用报告并记录进度。

- FR-008：coder 按共享实施规则负责实现、测试及自动化脚本的编写修复，并通过必要的定向单元测试、构建和类型检查完成开发局部自验。validator 按任务负责用户功能集成测试（含适用的 UI 自动化、浏览器操作和 computer-use）、Bug 归因检查与定向复验、架构 Review 与整改复核，检查断言对目标行为的证明能力并报告覆盖缺口；不修改实现或测试代码。自动化是验证手段，不排除 coder 执行定向单测。需要真实组件协同、集成环境或用户入口取证时，按明确范围交 validator。Main 按任务范围协调与汇总。

- FR-009：测试报告记录一次测试活动，适用于方案可行性、开发局部自验、集成验证、业务需求验收、Bug 归因检查及复验，注明实际类型；架构一致性使用 Review 专用报告。报告必备内容为测试目标与依据、范围与计划、环境、准备与数据、执行与覆盖汇总、测试明细、关联问题与影响、测试结论与限制。章节不得静默省略，不适用说明原因，缺失注明缺口及影响；范围和标准取自已确认约定，常规准备按 FR-026 从已有依据推导，不能补造验收要求。简单任务沿用当前任务或既有载体，保留必备结构，各节仅填写本轮必要事实并精确引用已有依据，不重复展开。范围内未执行项保留并标未测或阻塞；统计与明细一致，用例通过率不替代需求覆盖，结论须有证据支持。报告只引用 Issue 与本轮影响；复验作为新批次保留，不把历史失败改为通过。Quickstart 维护操作与预期，Status／Plan 引用报告。场景按内容层级分流，不按任务名称固定落点；原型引用与确认记录由 documenter 维护，原型代码归属按 FR-010 执行；通用时序不预设业务专属概念。

- FR-010：HTML 原型用于需要界面操作的交互与体验确认；后端、库、CLI 或维护任务按实际接口、行为或变更内容确认，无此需要时不要求制作 HTML 或填写原型章节。中保真 HTML 原型归测试代码资产。产品任务执行者制作、验证并记录入口、版本、适用需求、确认状态和实测结果。原型以后续直接复用为目标，复用任务指定的现有组件和代码上下文，架构符合性由 Review 判断；实现对应需求时将选定代码迁入或提取到正式模块，移除模拟装配并补齐真实接口、权限与异常处理。正式运行依赖链与装配不得直接或间接启用原型测试运行器，必要测试与夹具保留在测试资产中。

- FR-011：以推理和最终交付质量为目标，在会话允许委派时，coder、test、review 等有对应专职执行者的复杂任务默认由专职 Agent 按完整工作批次持续执行，简单局部任务可由 Main 直接完成，部署与 Git 按各自入口的默认职责执行；不强制全角色轮转或在 coder 后固定追加 Test／Review。Main 负责目标、授权、覆盖与完成条件，协调跨角色矛盾并在授权内接续 Bug 评估、实施、集成测试及 Review 的后续工作；角色完成不等于整个任务完成。用户指定的推理强度优先；否则 Main 按子任务自身复杂度独立选择并在启动时显式指定，不直接继承主任务强度，也不在角色配置中固定；独立判断的结果可以与 Main 相同。启动方式不支持显式指定时如实说明限制。designer 仅在实质设计取舍时介入，documenter 在必要节点按工作批次归并关联证据；不因单个字段或状态更新反复委派，不将全部记录落盘作为启动已授权后续工作的前提，正式记录仍按各流程完成要求归并。角色复用原执行者，独立且有收益的工作才并行。Main 与角色交接采用最小充分上下文：目标与完成条件、授权和归属边界、必要来源引用，按职责补充输入；角色返回结论、增量差异、可复查证据与未完成项。任务交接沿用已有任务记录，说明哪些要求被替代、哪些工作未完成；不新增接管状态、接收确认流程或环境恢复协调。续派只传变化，复用有效证据，不复制完整上下文、日志或报告，不强制新增交接文档；压缩不得丢失关键约束、失败、版本与覆盖范围。Main 在缺口、矛盾、失败或相关变化时深入核查受影响部分，不重复完整分析或报告；必要独立复核和证据不得为节省 token 省略。无法委派时如实说明并推进可执行工作，要求独立审查且缺少独立执行者时保留该项阻塞。仅暂停确需新决策或外部授权的受影响项及依赖项，其余授权内工作继续；阻塞注明具体待决问题、承接者及恢复条件，不能以待后续专项代替可执行工作。

- FR-013：提供随项目分发的只读文档校验 CLI，由 sdd-documenter 在写后对明确选定的文件或目录执行。机械检查覆盖 UTF-8、代码围栏、标题层级提示、表格列数、受支持的编号声明重复、本地链接及 Markdown 锚点；输出文件、行号、规则码、级别和问题，支持文本／JSON 及稳定退出码。CLI 不访问网络、不修改文档，不推定语义一致或验收通过；未支持的语法和未检查范围明确说明，语义判断仍由 Agent 完成。

- FR-012：仓库治理统一承载 SDD、repository、governance 所指的研发治理，作为上位规范负责人与 Agent 协同、决策与授权、流程接续、工程资产及文档权威、跨流程完成与交付边界，正文为 sdd-repository-governance.md。各 Skill 维护本流程输入、执行步骤、完成判据与回执。入口按任务条件指向适用章节。下位架构规范 architecture-rules.md 定义可落实到系统与代码并可审查的架构原则、范式和约束；开发者与验证者的协作归治理，正式实现与测试实现的依赖、装配和运行隔离归架构。需求和架构讨论保持宽松，不设固定流程、模板填报或架构规范符合性门禁。用户明确要求写入 Blueprint 时，sdd-documenter 按已确认内容及模板整理并检查内容一致性，不依赖架构规范、不自动补齐规范映射。sdd-init 维护抽象架构原则；目标仓库仅在用户要求生成或更新时，由 sdd-documenter 按已确认 Blueprint 与契约归并 Code Review Rules。仅 Review 使用项目规则检查实现；架构落地的判断、整改目标及复核专属 Review，不能通过共享规则、角色或模板转交 coder；Review 聚焦架构落地一致性及 Code Review Rules 执行，不审阅 Spec 内容，不检查业务需求覆盖或进行业务行为验收。业务模块仍属于架构检查对象，按职责、状态所有权、依赖和接口等架构约束判定；映射与遵循证据归审查记录。Blueprint 表达项目设计，ADR 记录具体取舍，Review 检查遵循；不新增设计或 Blueprint Skill；表达方法和工作流程不充当架构规范本体。SSOT 要求同一作用域内同一事实有一个权威来源，副本和派生数据的用途明确。通用架构原则限于已确认条款，不额外引入 SOLID 等原则。资产归属与默认落点由仓库治理统一维护。治理索引逐项定位初始化器及项目 Skill 的输入与回执，以及相应产物载体。

- FR-014：架构规范按“通用约束＋专项约束”组织：通用约束覆盖模块职责、接口、依赖方向、状态权威、运行边界及业务／基础设施分工；专项约束覆盖可观测性（含日志）、环境、工程骨架、测试工程与自动化四项。通用约束是架构规范内部章节，不另立系统架构规范；目标项目的实际模块、协作与部署由 Blueprint 表达。业务禁止依赖日志、指标等观测数据及观测工具实现需求功能，业务状态、流程和计费由业务接口与权威数据承载。观测不得拥有或修改权威业务状态，可记录业务接口提供的状态事实或快照供观测与评测读取，仍遵守日志保存边界。观测范围、保存政策与日志契约按项目 Blueprint 和契约确定，已要求的记录须能核对触发条件、内容、保存边界和失败处理；环境规范覆盖各环境拓扑、运行时、依赖、配置、网络、存储、数据与隔离。工程骨架按已确认的 Blueprint 创建或调整工程目录、模块和 package，落实模块职责、接口和依赖边界。Blueprint 变更后同步受影响的工程结构及相关生成模板。手工搭建与工具生成的骨架均按 Blueprint 检查，Review 根据本轮影响范围记录适用性和依据。测试工程与自动化规范覆盖正式实现与测试实现隔离、测试层次、依赖替代、真实／模拟条件、契约、确定性、数据生命周期、框架配置、断言、并行、超时／重试、本地与 CI 入口及诊断；回归是验证目的，框架与运行入口按项目设计分工，避免无依据的职责重复。工程资产分类及落点由 SDD 仓库治理唯一维护，架构规范只引用。Code Review Rule 表达约束，项目设计明确架构决定，工程骨架落实模块结构，框架支撑运行，遵循证据证明落地情况；通用原则的边界遵循 FR-012。目标仓库生成或更新规则时，依据已确认的 Blueprint、契约及实际运行路径选用适用架构约束。每轮 Review 按本轮变更及跨模块影响确定适用项目规则并取证，核对新增或受影响路径是否缺少规则映射。已要求但尚未实现的能力仍纳入范围；证据不足记 UNVERIFIED，契约冲突记 BLOCKED，涉及未决产品或架构取舍时交回讨论。每条 Code Review Rule 具有稳定标识、设计依据、适用条件、取证路径和违规判据；同义项原位归并，归属未决时保留待决。

- FR-015：可行性讨论产生的验证代码、Demo 功能代码、同场景不同算法的对比测试，以及候选技术路径探索与迭代代码，统一属于测试代码并按测试工程规范维护，保留场景、算法／路径、版本与结果的关联。功能完整、接入真实服务、验证通过或方案被选中不自动改变资产归属。已确定正式方案后的正常产品开发属于正式实现；测试代码正式采用须迁入或提取、移除模拟及实验装配并验证。资产分类由仓库治理唯一维护，测试工程与自动化规范引用分类并规定运行隔离；正式入口、模块依赖、动态加载或运行配置变更时，核对正式运行的直接、间接依赖及实际装配。测试可以调用正式模块。

- FR-016：业务领域负责业务规则、权威状态和流程；运维／基础设施统一承载技术流控、链路追踪、指标监控、运行诊断和进程唤醒、保活、重启、故障恢复，业务通过明确接口使用而不重复实现。业务配额与唤醒词识别等产品能力按业务语义归属，不按名称归入运维。观测保持非侵入；技术流控和进程生命周期管理按明确接口、权限及策略实施运行控制，不混用观测隔离要求，不改变业务权威归属。

- FR-017：工程资产按系统用途分类：正式程序的业务代码、通用技术模块及配套运行配置归正式实现，具体环境值由环境配置管理；部署、排障、备份和恢复操作脚本与工具归运维，测试专用连接配置归测试。架构中的基础设施职责不直接决定资产目录。探索验证以已明确的假设、候选方案、比较目标和判断指标为依据，实施入口引用该统一依据并支持已授权探索目标；测试技术规范负责原始输出、诊断及关联标识，正式报告和结论归仓库治理。现行指令按语义删除泛化的如实报告、不虚构、不夸大结果、缺少证据不判通过和局部成功不代表整体成功等 Agent 默认准则，不搬移至其他文档；范围覆盖治理、架构原则、专项规范、Skills、角色、模板、初始化片段、说明、工具生成文本及相应检查。保留 SDD 特有的职责分工、授权边界、产物权威、执行独立性、Review／Test Gate 判据和人工确认条件，以及系统状态、持久化回执、观测与业务隔离、正式与测试装配隔离等技术约束；工具能力边界及历史失败、未验证状态保留。

- FR-018：单一事实来源（SSOT）包含业务实体持久化约束。对需要持久化的业务实体，项目 Blueprint 与契约明确权威存储、写入职责、写入完成判据、写入失败处理及恢复要求。业务领域拥有权威状态，观测记录仅供观测使用。

- FR-019：在现有文件内压缩治理、文档写入及观测重复条款，不通过拆文件转移篇幅；职责、授权、条件、例外及 Gate 判据保持完整，执行步骤和模板字段引用现有权威来源。按同一统计范围记录压缩前后汉字及非空白字符数。

- FR-020：架构 Review 依据目标仓库适用的 Code Review Rules 与 Blueprint，使用 review_template.md 以检查项为审查、推进、交接和跟踪的唯一单位；每项维护依据、对象、初审发现、Task 引用、复核证据和当前状态，保留初审及历次事实，不另建独立差异清单或问题生命周期。尚未检查的项明确标为待检查、初审未执行；对当前项检查后符合直接 PASS，可修复偏差无需等待全部项初审或总 Gate，立即按实际授权接续；实现偏差沿用原检查项形成整改工单，记录适用规则、偏差证据、整改目标、涉及位置、预期结果和须保持的行为。sdd-review-code 在该项定义开发者视角的验收方案，写明适用架构约束、检查对象和路径、检查条件、取证方法及通过判据。coder 按明确的整改目标实施并提交局部证据，架构判断留在 Review，修复方案只由 coder 在 Plan 维护。默认自动接续授权内整改；复杂整改可拆多项 Task，同一 Task 可关联多个检查项，各项分别由原审查者在整改版本上按原检查项的方案复核，通过才关闭，失败返回对应 Task。原审查者负责架构装配和依赖取证，可引用适用的用户功能集成证据；角色复用及例外按 FR-011，逻辑逐项闭环不要求逐项新建 Agent 或逐命令派工。证据缺口由审查者补查，缺失验证代码由 coder 编写；涉及业务逻辑、外部契约、架构决定变化或影响无法确定时，仅暂停受影响项及依赖并回讨论，明确只审不修时遵守。Gate 汇总适用检查项，不以 FAIL 停止授权内修复；未受影响证据经影响分析后复用。sdd-documenter 随检查批次落盘并持续更新同一记录，Status／Plan 引用专用记录，不重复通用报告。旧记录保留原义及编号，不自动迁移；模板随分发安装并校验缺失保护。

- FR-021：独立 Issue 记录是问题事实与处理状态的唯一正文，默认 docs/issues/<问题编号>.md，已有项目沿用实际映射。使用项目内稳定唯一编号，关联场景／AC、已有依据、复现及预期实际差异、证据与版本、影响、类型、承接者、修复 Task、处理状态及阻塞恢复条件。Issue 登记不授予修复或复验权限；只验收和只评估等授权限制随交接保留。
  - sdd-bugfix 接收用户报告或验收发现的疑似缺陷，从已确认的预期、实际行为、触发条件、环境、版本、影响及复现证据判定是否为缺陷。提出候选原因及可区分的观测预测和排除条件，在修复前以定向检查或可直接证明因果的代码路径验证。证据不足则继续取证或记录缺口和恢复条件。原因有证据支持且修复获授权时，沿用原 Issue 派单给 sdd-coder，给出要恢复的行为、已验证原因和证据、影响、修复边界及通过判据。用户可感知的缺陷以原 Issue 的用户操作或调用入口、复现条件、步骤、可观察结果和必要回归组织验收，可引用可证明等价的场景。归因证据随工单交接。sdd-bugfix 到派单为止，不修改实现或测试代码，不做修复后复验或关单。
  - sdd-coder 在同一份 Plan／Task 自行制定和更新实施方案、改动位置及任务拆分，关联原 Issue 及归因证据。修复后交回实际改动、修复版本、局部自验证据和仍待验证的判据。定向检查实际证明原故障或等价场景已恢复且必要回归通过时，局部证据可满足单任务的完成判据。发现归因反证时暂停该项，带原编号及新证据退回 sdd-bugfix 重新归因。
  - 原 Issue 的关单依据取自修复版本上实际通过的原场景或等价场景、必要回归及所需人工确认。局部证据满足全部条件时，sdd-documenter 据此关闭原 Issue。单独请求复验已有修复且可用局部检查满足判据时，由 sdd-validator 执行，简单检查可由 Main 执行，独立性按 FR-011；沿用原 Issue，在指定修复版本取证并交 sdd-documenter，不开启实施、不修改实现或测试代码。需真实组件协同的判据纳入明确的集成范围后，由 sdd-test-loop 验证本轮纳入的原故障或相关回归。缺证时保持待复验或阻塞，注明缺口及恢复条件，待人工反馈时保持待确认。故障仍在或引入回归时沿用原编号，按证据退回归因或实施阶段。Issue 关闭与整轮 Test Gate 分别按各自覆盖判定，复用适用版本和范围的证据。
  - sdd-documenter 按 issue_template.md 归并原 Issue 状态与处理历史，按 test_report_template.md 分别记录发现、归因检查、局部自验和复验的事实及实际版本；报告只引用 Issue 与批次影响，不维护处理流水。Status／Plan 引用报告及 Issue。未测或阻塞不自动判为缺陷；缺失测试交 sdd-coder，验收证据缺口由验收执行者补查，文档矛盾交 sdd-documenter，需求缺口或变更交回讨论。非代码问题按对应处理结果和验收执行者核验记录闭环。架构 Review 继续使用专用检查项记录。

- FR-022：sdd-deliver 按用户部署、启动或重启请求执行，未指定环境默认 dev，支持明确指定的其他环境，不随代码修改完成自动触发。落地前先探测本地操作系统、工具与运行时、连接上下文、既有服务、端口和依赖；远程部署另核对目标环境。dev 优先 Docker Compose，沿用项目明确部署规范与既有配置，不绑定平台发行版、固定路径、个人仓库或集成／CI 拓扑。按实际环境验证挂载，共享依赖兼容才复用，保持项目数据与凭据隔离及持久化数据，避免影响其他项目。遵循项目及目标环境规范，自主完成环境搭建、依赖与配置准备、环境排障修复、必要构建部署和服务就绪检查，不增设授权或审批流程。优先复用并更新、重启既有服务，保持服务标识、端口和运行位置一致，避免重复实例及冲突；首次部署创建必要服务，已健康运行的启动请求复用现状。按项目既定副本与更新策略管理实例，识别归属并保留其他服务。失败先诊断与查询实际状态，按恢复策略修复，持续无进展时返回具体阻塞；只在必要信息不可获取或目标歧义时澄清。返回环境、运行版本、服务状态、访问与日志入口及环境处理结果。Main 默认执行，现有五个角色不增加；实现修复和业务验收沿用对应技能，文档归并沿用 documenter 角色，组合交付按 FR-003 执行。安装清单、元数据、分发和导航同步更新。

- FR-023：项目初始化及升级承接 Blueprint ARC-008，采用单项目互斥与失败可恢复机制。同一项目已有安装操作时拒绝后来的操作；写前校验冲突不修改目标资源。预检快照与写入前内容不一致时停止，保留外部修改。写入失败恢复本次触及的文件并保留无关修改；进程异常终止后，下次 init 先处理未完成操作再进行新安装。恢复遇到外部修改、损坏记录或 I/O 失败时保留恢复记录，报告受影响路径与恢复入口并阻止继续覆盖。该机制不承诺跨文件瞬时原子切换。

- FR-024：承接 Blueprint ARC-009，初始化器及项目共享治理脚本移除 start、record、attest、check、finish、commit 旧命令及专属实现，不保留兼容入口或自动迁移机制；初始化器保留 inspect／init，项目共享脚本保留只读 inspect，独立 doc_check.py 保留，Git 交付由 FR-003 规定。历史 Spec、Status、证据及基线保持原义与内容，后续工作通过现行 Skills 与角色执行。

- FR-025：人与 Agent 协同以意图对齐为首要规则。必须呈现对用户意图的理解并请求确认，不以推断代替确认；已有确认沿用，新增或变化内容重新对齐。由用户决策的需求与方案分开讨论、分别确认。均待定时先需求、后方案，需求到实现按 FR-029 的节点与对象执行。沟通语言与适用视图按[意图对齐](../../source/project/.agents/sdd/references/visual-confirmation.md#意图对齐)执行。

- FR-026：用户功能集成测试范围明确时，由 sdd-test-loop 按指定版本和环境从用户操作或调用入口验证真实组件协同、业务结果及本轮纳入的用户可感知非功能指标。指标沿用已确认的测量条件、统计口径和阈值，按验收方案记录实际测量。UI 验收限于中保真，覆盖信息结构、页面布局、操作路径、交互反馈和业务状态，排除纯视觉样式和像素还原。sdd-test-loop 执行前复用上游工单提供的验收文档，按实际版本、环境及已确认场景／AC、适用契约补齐本轮运行信息，沿用 Quickstart 结构。直接发起集成测试且没有上游工单时，按已有依据复用或准备可执行指南。执行者可自行推导常规数据、边界取值和顺序，保留依据和覆盖，沿用已确认的范围和判据。文档提供适用版本、环境、入口、起始数据、步骤、关键观察点及必要的复位方法，交付时提供文档或可访问链接。正式落盘由 sdd-documenter 按需归并，实际执行及人工反馈归 Test Report。按版本、环境及覆盖复用有效证据，补验未覆盖项。Test Gate 仅在指定版本和环境下本轮判据全部满足，且必要证据和必需的人工验收反馈齐备时判为 PASS。疑似缺陷按授权交 sdd-bugfix，新增或修改测试代码交 sdd-coder。常规准备不改变现有实现、验证、文档与决策职责。
  - 核对验收产品范围、目标版本、测试环境、主要用户路径、已确认规格、本轮目标及前次证据。首次实测前设唯一的常规人工确认点，集中确认验收产品范围、目标版本、测试环境和主要用户路径中尚未明确的内容。启动指令和已有确认中明确的内容直接沿用，四项均明确时，完成常规准备即可实测。常规测试数据、异常与边界覆盖、执行顺序及取证方法由执行者决定，沿用已确认判据。
  - 执行中，验收范围变化、拟改测其他版本或环境、业务判据需补齐、调整或消除冲突，需要补充操作授权，或数据选择涉及新增业务含义或不可逆影响时，只将受影响项交 Main 对齐。暂停受影响项及其依赖，其他已授权且就绪的场景继续。判据明确而实测不符时，按原判据记录失败及证据。
  - 准备验收时标明确需用户实际操作或主观判断的场景，说明操作步骤和所需反馈。报告单列人工待验、实际反馈及其对 Test Gate 的影响。必要反馈尚缺时，记录待验状态和恢复条件。

- FR-027：通用 Skill、角色、规则、模板和脚本只在用户级共享目录保留一套。未初始化仓库在 SDD Skill 中只发现 sdd-init。项目运行 sdd-init 后，以本地目录链接发现分发清单中的工作流 Skill，通过项目配置相对引用五个角色，仓库保留可提交的启用导航和引用。用户级升级沿用稳定共享路径，已链接项目重新加载后使用新版，旧受管 sdd-spec 和 sdd-coder 随共享包更新移除。sdd-develop 承接需求交付，独立实施工单使用共享实施规则。共享包由 sdd-deliver 取代 sdd-commit 与 sdd-deploy，sdd-documenter 承接文档归并，旧受管 sdd-doc 技能随共享包更新移除。首次接入和重跑均使用同一 init。目标项目自行清理遗留文件；清理后一次 init 即可接入并同步导航和角色托管块，或补建缺失的本地链接。项目正文及托管块外的配置保持原样。当前同名资源或配置冲突在写入前报告。项目事务恢复覆盖新建链接及本次写入的引用。

- FR-028：sdd-review-prompt 审查提示词的冗余、无关上下文和规则歧义。规则表追溯来源、职责、授权、例外与 Gate，任务 DAG 表达场景的可观察决策和必要依赖。默认只审查，按授权修订与复验。精简以关键行为保持一致及关键决策稳定为验收目标，Token 与读取量作为辅助数据。

- FR-029：sdd-develop 负责交付一个可独立验收、可集成的需求单元。Main 在用户明确发起新增能力、需求变更、接续已确认需求或未完实现时选择本入口。按实际就绪步骤接续，复用已有有效确认、权威资料及适用证据。只讨论、只写规格或暂缓实施时，在用户限定的终点结束。
  - 本阶段固定两个常规人工确认节点，用户只确认交付范围、主流程和主要体验。A 为需求落盘前确认，适用于新需求和需求变更。按需调研和制作中保真原型，依据目标、项目约定及既有行为推导异常、边界、失败反馈、恢复行为及验收覆盖。A 确认后依 FR-006 原位归并权威 Spec／AC，保留稳定编号及适用的固定版本原型引用。B 为交付实施前确认，在进入实施前呈现用户可理解的交付目标、范围、主流程、主要体验及就绪状态。主流程、主要体验或交付范围变化时在相应节点重新对齐。已有有效确认覆盖本轮时直接沿用。实施方案、接口实现、代码结构、Task 拆分、边缘场景及测试方法由 Agent 自主决定。末尾依据实际证据判定交付。必要外部授权与跨阶段决定交 Main。
  - 按 FR-005 沿用原工单或当前任务记录，固化或引用适用 Spec／AC、必要契约、须保持的行为及点对点验收计划与方案。列明验收项、执行者与执行条件，从用户操作或公开调用入口给出前置条件、步骤、观察点和通过判据。用户可感知非功能指标引用已确认的测量条件、统计口径和阈值。Skill 识别适用的架构约束并在工单直接引用，架构符合性及整改复核仍按 FR-020。实施执行者调查代码，在同一份 Plan／Task 记录方案、直接依赖、待查前提及局部验证入口。B 就绪后在授权内实施代码、测试及配套配置，完成局部自验。
  - 按 FR-011 与 FR-031 显式安排需求规格及原型、代码调查及实施、验收环境准备或排障、逐 AC 验收等专业工作。跨文档疑点按需安排 FR-030 的只读审查。Skill 依据项目实际要求安排独立验收，以本轮 AC 及直接受影响行为为覆盖范围，按需运行真实组件，复用适用于当前版本、环境、范围及判据的证据。本轮实现问题在本阶段修正并复验。历史独立缺陷、范围外改进、架构冲突或缺项及跨阶段事项附证据、影响、缺项和恢复条件交 Main。仅暂停受影响项及其依赖。
  - 完整交付须满足需求已确认归并、约定实现完成、局部验收与必要回归通过、实际版本和证据可追溯，以及集成入口及准备条件明确。全功能点集成测试、独立缺陷处理、架构 Review、纯技术重构及发布按 FR-031 由 Main 协调。

- FR-030：只读文档一致性审查角色 [sdd-doc-consistency](../../source/maintenance/agents/sdd-doc-consistency.toml) 仅作为源码保留。源码仓的 Codex 加载与目标项目分发均排除该角色。审查对象限于 sdd-init 所接入工作流中的技能及其委派产出的项目文档，如 Spec、Blueprint、技术选型、Plan、验收和测试记录，按本轮指定范围审查；AGENTS.md、Skill／角色指令、共享治理规则及运行时提示词本身不属于审查或整改对象，索引及治理的权威归属条款可按需作为定位和判断依据。上层决定触发与本轮范围，不加入需求、缺陷或实施等流程交接或门禁；该审查不替代写后语义与机械核对，清理由维护者按已确认的具体清单执行。按指定文档主题、编号或疑点，从索引定位权威正文与直接引用；无显式链接时在指定目录按编号、术语及已知同义词搜索，只读取命中和影响判断所需片段，复用 doc_check.py 与 --read，证据足够即止，缺少决定性依据列为未核实。沿用既有权威归属，判断同一对象、条件、版本及时点下的冲突，同义多处维护的现行正文冗余，以及断开、过时或错位的引用，核对所引条款、版本、环境及覆盖能否支持结论。保留摘要、操作提示、独有条件和例外、旧版本证据及历史。回执说明范围、位置、实际差异、影响、权威依据、建议及待核实项。删除候选须核对正文承接、独有语义、事实、追溯与直接引用；删除整份文档还须确认其无独立历史或证据用途。未确认的内容不修改或裁决。

- FR-031：每个 Skill 在授权范围内完成本阶段的执行、取证、修正及复验。可使用任何合格来源的项目资料、工单、版本和证据。Skill 按能力显式安排执行者，交接目标、授权、写入范围、必要来源和完成判据。角色直接使用项目资料与共享规则。Skill 无跨技能执行依赖，跨阶段事项交 Main，未授权阶段由用户显式发起。同一请求明确授权的多个阶段由 Main 按顺序和就绪情况协调。仓库级 Blueprint 持续设计与演化。需求到实现交付可独立验收、可集成的需求单元。多个需求集成后执行集成测试及用户指定的缺陷修复。发布前架构 Review 与技术重构保持已确认业务需求及行为，重构后的待发布版本须再次通过集成测试。

## 验收条件

| ID | 条件与预期 |
|---|---|
| AC-001 | 需求、计划、实施和验收的输入、产物与完成条件由各自职责定义，能够在本地项目中执行。 |
| AC-002 | 分发内容与资源清单一致，构建及新安装成功，引用可解析。运行已安装的 Python 脚本生成字节码后，同版本重装和新版本升级均成功；定制、缺失和其他额外文件仍触发安装保护，分发资源中未登记的字节码触发校验失败。 |
| AC-004 | sdd-coder 在实施前读取 Plan 模板并输出任务清单，阶段所需确认及实施授权齐备后直接执行，由实施执行者管理 Plan。模板随分发安装可用，导航可达，支持单项修复、有依赖的多项任务和可单独验证的交付批次。需求场景及适用契约、数据约束可追溯到 Task 的完成条件。核对多 Task 的 DAG 与直接依赖一致，未验证前提在使用前有检查，任务或批次有可观察结果和局部检查入口。上游工单提供目标、范围、判据及可执行验收方案；用户侧判据从用户操作或调用入口描述，架构判据从开发者视角定义。coder 引用上游方案，以代码单测为局部自验重点，逐项记录实际版本的证据覆盖与待验判据。核对只实施并自验即可结束、约定用户验收仍须按方案取证、架构整改仍须原审查者复核，以及同一工单包含两类判据时各自留证。测试先行场景能证明预期缺口并在实施后重跑，交付核对实际改动和验证覆盖。清单能区分未执行、失败、阻塞与完成证据。前置检查失败时记录失败与证据，依赖项标阻塞，已就绪且获授权的任务继续。按证据更新同一 Plan 并保留编号。无 Blueprint 时可交付明确需求、Bug 工单或缺失测试；Bug 工单说明要恢复的行为及依据，具体实施方案和拆分归 coder；Review 检查项以明确整改目标交接。coder、coder、治理和 Plan 不要求读取 Code Review Rules、ARC 覆盖或架构判定，不主动扩展重构；Review 仍负责架构检查与整改复核。 |
| AC-003 | sdd-deliver 支持独立的 Git 交付、独立部署及组合请求，实施或文档写入本身不触发 Git 交付。后续路径未指定时完成授权内的本地提交，返回分支、SHA、适用选项及结束选项，选定前无后续写入或部署；明确只提交时直接结束。覆盖提交后推送并部署、合并后部署，已授权路径无需再次确认，依赖的 Git 结果未完成时暂停部署，实际部署版本与已核验的 Git 结果对应。GitHub 与 GitLab 均能选择正确平台／实例／仓库；覆盖只建 Issue、创建或更新 PR／MR、合并及失败恢复，企业／自托管和 fork 的源目标不混淆。已授权链路的分支、提交、push 及请求创建无需逐项询问；无新改动仍可推进未完成的远端步骤。已有对象不重复创建，无关修改保留，目标歧义和认证缺口只请求必要输入。新分支首次 push、本地 main 过期、远端同名分支分叉、fork 的 upstream 目标前进、fetch 失败、冲突及推送期间并发更新均有明确处理；用刷新后的两组提交关系判定同步，不因无 upstream、工作区干净或 push 成功而跳过目标检查。固定基线例外保持原约定，普通同步不重复询问、不隐式改写历史。合并前核对最新 head、CI／审批及保护规则，head 变化复核影响，排队不报已合并，保护阻塞不绕过；普通授权不包含强推、删除或修改仓库权限。Skill、平台指引、角色、治理及安装导航一致，链接及分发检查通过；真实双平台操作与模型行为评测分别记录实际验证范围。 |
| AC-005 | Blueprint 的高位用例与验收维度由 Spec 细化且可追溯，不在蓝图维护具体需求细节或重复验收条款；documenter 对只改语义、不改结构的写入仍核对适用上游，保留有效条件、例外及稳定编号。 |
| AC-006 | sdd-documenter 承接原 sdd-doc 技能的触发条件、完整写入及语义核对流程，覆盖直接文档任务及其他流程交接；例如将已确认的在线超时从 5 秒改为 10 秒时，原位更新并保留离线例外、同步受影响引用。纯讨论不触发落盘，Main 直接承接时采用同一文档写入规则。契约模板不赋予 documenter 新设计权限；正式时序入口一致且不复制实际结果；测试执行事实归报告，缺陷处理归独立 Issue，Status／Plan 引用，只有确认需求变化才改 Spec；原型、实验与执行证据有明确读取及质量核对入口。技术调研与选型模板随共享资源分发，sdd-documenter 按对象定位并按需使用，区分待确认建议与已确认决定，引用架构决定及实测结果的权威正文。设计文档写入中发现关联 Code Review Rules 可能过时时回复简短提醒，规则更新时间由用户决定；不新增全量检查、自动维护规则或审批。 |
